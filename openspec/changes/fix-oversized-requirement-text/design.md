## 决策 1：把说明移进 scenario，而不是压缩正文

**做法**：`四特征重排` 正文只保留"这条要求是什么"（三条陈述，124 字符），
"与历史产物的关系"（含表格与四条 MUST）移进 `#### Scenario: 历史产物的特征数与当前不同`。

**为什么不是压缩正文**：那三条 MUST（跨版本误用 / 不得加兼容层 / 复算用 v2 代码状态）
每一条都有独立的违反形式，压缩会丢掉其中一条。而 scenario 本来就是放
"具体情形与边界"的地方——OpenSpec 的警告原文也是这么说的。

**代价**：那条 scenario 变成了一个"事实陈述"而非"行为断言"
（WHEN 读 v2 结果 / THEN 它们不同构）。这在形式上是别扭的：scenario 本该描述
系统行为，而这里描述的是数据事实。

**为什么接受**：备选是把这三条 MUST 拆成一个**新的 requirement**
（`Requirement: 跨版本产物的处置`）。那样形式更干净，但会：
- 新增一条 requirement，改变 `memory-retrieval` 的要求数（11 -> 12）
- 而这条 requirement 的标题是新的，不受 MODIFIED 匹配键约束

**所以这是个真实的取舍，我选了"形式别扭但改动最小"**。
若要形式干净，应在**下一次**动 `memory-retrieval` 时顺手拆出去，
而不是在本修正变更里附带结构改动。

## 决策 2：`全部特征关闭` 保留场景名，改内容

**约束**：OpenSpec 的 MODIFIED **不允许丢弃已有场景**。实测报错：

```
MODIFIED "四特征重排" omits scenario(s) the current spec still has:
"全部特征关闭". ... archive refuses to drop them.
```

**所以"删掉一个错误场景"这件事，在 MODIFIED 里做不到。**

| 方案 | 结果 |
|---|---|
| 删掉场景 | `validate` 直接报错，归档会拒绝 |
| 保留名字 + 内容改为"此状态不可构造" | ✅ 可行，但名字与内容不符 |
| 把整个 requirement 改成 REMOVED 再 ADDED | 会丢掉这条 requirement 的历史，且 REMOVED 的语义是"能力被删除"，不是"改个场景" |

**选第二个**，并在场景正文里写明"场景名沿用旧名"及原因。
**名字与内容不符这件事必须显式登记**——否则下一个人会以为内容写错了。

## 决策 3：把"归档前要跑 validate --all"写进 proposal 而不是本变更的 tasks

**为什么**：那是**流程**问题，不是本变更的交付物。写进 tasks 会让它随归档消失；
写进 proposal 的"附"节，归档后仍可在 `changes/archive/` 里检索到。

**而这正是本次漏检的根因**：`validate <change>` 只校验 delta 结构，
不校验归档后的 spec。**两个命令管的是不同的东西，而流程里只跑了一个。**
