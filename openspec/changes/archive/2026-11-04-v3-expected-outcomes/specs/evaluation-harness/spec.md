## ADDED Requirements

### Requirement: 能看得到当前装置产物的门禁，必须写明红的归因

当一条门禁读取当前装置的产物时，它"红了意味着什么" MUST 被写成可执行的断言，
MUST NOT 只写"预期通过"。

**"预期通过"不够**：造完数据看到红色时，人需要知道**该改什么**。

#### Scenario: 归因必须分档，且每档绑定一条门禁

- **WHEN** 有多条门禁会验同一代产物
- **THEN** 每条门禁 MUST 有一个归因档位（`apparatus` / `data`）
- **AND** 归因表 MUST 恰好覆盖这些门禁，不多不少

**实测三档**（`sample` 数据集，v3 装置）：

| 门禁 | 归因 | 红了说明 | 该去查什么 |
|---|---|---|---|
| `F19b` | `data` | 某条 implicit 的 gold 没被召回 | 召回路径 / 查询措辞 |
| `F20` | `apparatus` | condition 又回到加权里 | 排序代码 |
| `F24` | `data` | 数据太难或太简单 | 数据本身 |

#### Scenario: 归因必须由行为证明，不能凭判据的名字推断

- **WHEN** 断言某条门禁的归因是 `data`
- **THEN** MUST 构造"数据被破坏"的场景，证明它真的会红
- **AND** MUST NOT 只凭"它读的是数据"或"它名字里有 gold"来分类

**实测反例**：曾把 `F19b` 归为"结构必然"（因为它只读 implicit 的 rank）。
实测发现正好相反——构造一条 `rank=None`，它立刻红：

```
F19b: applicable=True passed=False
      1 条 implicit 从未被召回：['ledger-q3']
```

**根因**：`F19b` 判"召回是否成功"，而**召回不依赖排序装置**。
这正是它被归为"照跑"的理由，也**恰恰是它不可能是结构必然的理由**。

#### Scenario: "结构必然"必须与"恒真"区分开

- **WHEN** 某条门禁在某装置下的期望值是结构决定的（如 v3 下 `F20` 的 drop 必为 0）
- **THEN** MUST 构造一个与该结构矛盾的输入，证明门禁真的会红
- **AND** MUST NOT 让判据退化成"签名匹配就通过"

**实测**（`F20`）：

```
v3 签名 + drop=0     -> passed=True   "掉幅 +0.0000"
v3 签名 + drop=0.5   -> passed=False  "掉幅 +0.5000 不为 0"
```

**"必然为 0"的来源**是 `ablate()` 在 v3 下两次跑出相同 ranks，
**不是**"签名是 v3 所以判据自动通过"。后者会让这条门禁变成恒真断言。

#### Scenario: 归因表与发现方式表必须分开

- **WHEN** 新增一条能读取当前装置产物的门禁
- **THEN** MUST 同时更新"发现方式"表与"归因"表
- **AND** 两张表 MUST 各自有独立断言

| 表 | 判什么 |
|---|---|
| 发现方式（`DISCOVERED_GATES`） | 哪些门禁看得到该装置的产物 |
| 归因（`RED_ATTRIBUTION`） | 它们红了各自意味着什么 |

**为什么分开**：合并成一张表时，改动会同时影响两件事而断言只覆盖其一。
分开之后，"谁能看到 v3"变了会红在发现方式表，"归因写错"会红在归因表。

#### Scenario: 归因要写进 detail，不是只写进测试

- **WHEN** 门禁红
- **THEN** 它的 `detail` MUST 说明归因方向

**实测要求**：

| 门禁 | detail 必须含 |
|---|---|
| `F20`（v3 下掉幅不为 0） | "condition 又参与了加权" |
| `F24`（低于基线） | "基线" |
| `F24`（高于上限） | "太容易" |

**为什么**：造完数据看到红色时，人先看的是 detail，不是测试文件。
detail 只说"掉幅 0.5000"不够——它没说该去改哪。
