## 决策 1：空组返回 `None`，不返回 `0.0`

**做法**：返回类型从 `dict[str, float]` 改为 `dict[str, float | None]`。

**为什么不是"省略该键"**：省略会让 `dict["relation_cross"]` 抛 `KeyError`，
而 `None` 让调用方必须显式写 `if x is None`——**两种都会被迫处理，
但 `None` 的语义更清楚**（"这个轴存在，但没有数据"vs"这个轴不存在"）。

**为什么 `0.0` 最危险**：它是一个**合法的基线值**。
读代码的人看到 `0.0` 会想"随机命中率是 0，所以任何命中都是好的"，
于是任何实测值都通过……**不，反了**：`ratio <= baseline` 才报红，
而 `0.0` 意味着"只要 ratio > 0 就通过"。

**等等，这需要核实**：`0.0` 的实际后果是"容易通过"还是"容易红"？

- 判据是 `if ratio <= baseline_seh1: 红`
- baseline = 0.0 时，`ratio <= 0` 才红 -> **ratio=0 才红**，其余都通过
- 所以 `0.0` 让判据**变宽松**，不是变严

**我上一轮在 proposal 里写"任何实测值都会报红"是错的。** 正确的是
"任何 ratio > 0 的值都会通过"，即 **空轴伪装成"最容易达标"的轴**。

**这个方向仍然危险**，只是危险的方式不同：它让一个**没有数据**的轴
看起来"全部达标"。若报告按轴聚合，cross 轴会显示"0 条不达标"。

## 决策 2：上限必须加回来，但语义变了

**v2 的上限**：`ratio < 0.9999`，语义是"指标没有区分力"（装置 + 数据）。

**v3 的上限**：同样是 `ratio < 0.9999`，但语义只剩"数据太容易"。

**为什么 v3 仍然需要它**：v3 数据约束里有"每 subject 至少一个单值 relation"。
单值 relation 意味着 `n_competitors = 1`，池大小 2，`ratio` 很容易满分。
**只有下限会把"随便排都对的池"判为合格。**

**代价**：v3 数据若确实只有小池，F24 会红。那是正确的——
它说明"这份数据测不出排序能力"。

## 决策 3：v3 的数据侧保留，但登记为恒真

**保留的理由**：它防的是"池大小退化成 1"。
若某天 `n_competitors` 全为 0（所有 relation 单值），
派生 within 会是空组（基线 `None`），而如果实现有 bug 让它算成 1.0，
这条会红。

**登记为恒真的理由**：不写会让读者以为"数据侧 + 结果侧"都在验。
实际只有结果侧有判别力。

**spec 里写成 scenario 而不是注释**：注释会被删，scenario 不会
（`openspec validate` 会检查）。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| `float \| None` 让类型变复杂 | 调用方必须处理，这是有意的 |
| 上限让 v3 的 F24 更严 | 那是正确的：满分说明数据太容易 |
| 数据侧恒真但仍保留 | 显式登记为"防形状退化"，不是"当前在验" |

## 不做的事

- **不改 `axis_baseline()`**：v2 口径保留
- **不改 `F24` 的 v2 分支**
- **不造 v3 数据**
