# Design: 冲突判定状态机

动机见 `proposal.md`，行为契约见 `specs/conflict-resolution/spec.md`。
本文只讲怎么做与为什么。

## Context

C2 提供了能表达六种状态迁移的存储层，但**没有任何东西决定该写什么**。
`insert` 遇到同键 ACTIVE 只会抛 `ActiveExists`，把判断责任推给调用方。

C1 留下一个必须在这里解决的问题：官方指标奖励"把两个冲突答案都报出来"，
导致 naive-rag 的 88% 里有 66 个百分点是虚的。写路径上的正解是
**必须做出唯一裁决，不允许默认"两个都留"**。

可复用的既有能力：`memory/llm/`（SSE 收拢 + 响应缓存）、
`memory/store/`（不变量与状态机）、`memory/eval/`（bootstrap）。

## Goals / Non-Goals

**Goals**

- 六类判定**完备且可解释**：任何输入都有确定出口，且能说清为什么
- 规则优先，模型只在**唯一一处**兜底，且该处贡献可被单独测量
- 判定质量用**人工确认**的标签衡量，机器标签不冒充结论

**Non-Goals**

- 不做检索、不做作答（C4 / C5）
- 不做多轮对话的意图理解：本变更只处理"单条候选事实"
- 不做自动回溯修复已被错误取代的历史
- 不做领域本体构建：别名表是手写的小词表，不是知识图谱

## Decisions

### D1. 六类而不是三类

mem0 的模型是 `ADD / UPDATE / DELETE / NOOP` 四类。它的两个问题：

- `UPDATE` 把"补充"和"取代"混为一谈，丢掉了"旧值仍然成立"这个信息
- `DELETE` 是破坏性的，与 C2 的审计要求冲突

我们的六类把这两件事拆开：

| 类 | 旧值是否仍成立 | 是否产生新版本 | 存储动作 |
|---|---|---|---|
| `NOOP` | 是（完全相同） | 否 | 无写入，只记事件 |
| `ADD` | — | 是（首版） | `insert` |
| `MERGE` | **是**（只是不完整） | 是 | `supersede` + `reason=补充` |
| `SUPERSEDE` | 否 | 是 | `supersede` |
| `CONFLICT` | 既有值仍 ACTIVE | 是（CONFLICTED） | `mark_conflict` |
| `BRANCH` | 是（条件不同） | 是 | `insert`（条件不同） |

**为什么 `MERGE` 与 `SUPERSEDE` 用同一个存储动作**：两者在存储层的效果相同
（旧条目关闭、新条目 ACTIVE），差别在**语义**与**审计原因**。合并进存储层会让
`valid_to` 的语义变模糊，而分开记录 `reason` 才能让时间线讲清楚"这是补充还是改主意"。

### D2. 规则严格有序，且顺序被测试锁定

```
1. 同键无 ACTIVE            → ADD
2. 完全相同（值/条件/权威）  → NOOP
3. 条件不同                  → BRANCH
4. 新值包含旧值              → MERGE
5. 权威更低                  → CONFLICT
6. 权威相当或不低 + 确认新状态 → SUPERSEDE
7. 其余                      → CONFLICT（兜底）
```

**顺序为什么是这样做**：

- 第 2 条必须在第 4 条之前：`"pnpm"` 不包含于 `"pnpm"`？实际上包含，若顺序反了，
  完全相同的值会先被判成 `MERGE`，产生一个无意义的新版本。
- 第 3 条必须在第 5 条之前：条件不同是**并存**，不该因为权威低就变成冲突。
  "开会我喜欢早上"（用户自述）与"写代码我喜欢深夜"（用户自述）权威相同，
  若条件检查放在后面，会被误判为 `CONFLICT`。
- 第 4 条必须在第 5 条之前：权威更低的**补充**仍是有价值的补充，
  不该因为权威低就丢掉。"用户说 pnpm，工具推断 pnpm+workspace" 应该合并。

**为什么需要"顺序锁定测试"**：规则表是一串 `if`，重排不会报错，只会静默改变行为。
加一条测试断言"多规则同时匹配时取第一条"，改动顺序会让它失败。

### D3. "是否陈述新状态"只在这一处用模型

规则能处理值的包含关系，但处理不了**语义**：

- `"我们这个仓库现在改用 npm 了"` → 新状态
- `"我们用 npm"` → 可能在重复旧状态

判断依据先走正则（覆盖绝大多数中文表达），未命中才调模型。

**为什么不用模型兜底一切**：模型调用不可复现（虽然 C1 已缓存），且慢。
更重要的是，**如果模型参与主要判定，就无法回答"不用模型会差多少"**。
把模型限制在一个二分类上，消融实验才有意义。

**模型输出的处理**：只接受能解析为布尔的输出；解析失败视为"无法确认"，
走 `CONFLICT` 兜底并标记 `change_source = "failed"`。
不重试、不猜测——猜错的代价是静默覆盖用户事实。

### D4. 归一化宁可不猜

别名表是手写小词表。未登记的表述**保留原值**并标记 `normalized = false`。

**为什么不像某些系统那样用 embedding 聚类自动归并**：自动归并的错误是静默的，
且不可解释。一旦把两个不同的主体并到一起，后续所有判定都建立在错误前提上，
且很难从结果看出来。

**代价**：同一概念的两种说法若未登记，会被当成两条独立事实。
这是**可接受的失败模式**——它表现为"记忆里有两份"，而不是"记忆里错了一份"。

### D5. 判定结果是一等对象，不是布尔值

```python
@dataclass(frozen=True)
class Decision:
    kind: DecisionKind
    rule: str                 # 命中的规则名，用于解释与归因
    key: NormalizedKey        # 归一化后的键
    existing_id: str | None   # 被比较的既有条目
    change_source: ChangeSource   # rule / llm / disabled / failed
    normalized: bool          # 是否走了别名表
    existing_value: str | None    # CONFLICT 时用来生成追问
    candidate_value: str
```

**为什么 `rule` 必须记下来**：C1 的教训是"分数高但不知道为什么"。
有了 `rule`，任何一个错误判定都能归因到具体规则，而不是笼统的"模型不行"。

### D6. 场景集分 dev / test，标签分 proposed / confirmed

- 60 条：dev 40 / test 20
- 六类各 10 条（保证稀有类有样本）
- 每条带 `label_status`，脚本生成的初始值一律 `proposed`

**为什么必须区分**：我可以用规则生成"期望标签"，但那是**循环论证**——
用规则生成的标签去测规则，必然接近 100%。所以：

1. 场景的**文本**由我手写（覆盖真实表达）
2. **期望标签**由人工确认，确认前标记 `proposed`
3. 指标只在 `confirmed` 上作为验收依据

**承认的局限**：n=20 的 test 集，单类只有 3~4 条。macro-F1 的方差会很大。
报告必须同时给逐类区间与样本数，且明确标注"小样本，结论强度有限"。

### D7. 标注工具是脚本，不是表格

`evals/tools/label.py` 提供三个子命令：

```
list   --status proposed          列出待确认条目
confirm --id <id> --label SUPERSEDE --labeler alice
kappa  --a alice --b bob          计算 Cohen's κ
```

**为什么不做成 CSV 手工编辑**：容易出现格式错误、遗漏、以及"改了但没记录谁改的"。
脚本强制记录 `labeler` 与时间戳，κ 才能算得出来。

### D8. 判定与存储分离

`ConflictResolver.decide()` 只返回 `Decision`，不写库；
`ConflictResolver.apply()` 接收 `Decision` 并调用存储。

**为什么分开**：判定质量（D6）需要在不写库的情况下批量跑；
而端到端测试需要真实写入。分成两个方法后，两者互不干扰。
也避免"评测时把测试数据写进了生产库"这类事故。

## Risks / Trade-offs

| 风险 | 应对 |
|---|---|
| 规则顺序被无意改动 | 顺序锁定测试：多规则同时匹配的用例断言命中第一条 |
| 别名表太小导致归一失败 | 未登记时保留原值并标记，报告里统计 `normalized=false` 的比例 |
| LLM 兜底不稳定 | 走 C1 的响应缓存；`--no-llm` 消融给出"不用模型差多少" |
| 60 条太少，macro-F1 方差大 | 报逐类样本数与区间；结论强度明确标注；不宣称"显著优于" |
| 人工确认进度慢阻塞验收 | `proposed` 子集也可跑，分数单独列出；D6 只在 `confirmed` 上生效 |
| `MERGE` 的"包含关系"判定过于简单 | 只做字符串包含与词集包含两种；复杂的语义合并留给人工 `CONFLICT` |
| 条件 BRANCH 与无条件的事实如何共存 | C2 已保证条件不同的条目互不冲突；读路径的选择留给 C4 |

## Migration Plan

不适用：新增模块，无既有数据需要迁移。

若别名表后续扩充，**已写入的条目不会自动重新归一**。这是刻意的：
静默改写历史比留下不一致更危险。需要时通过 `timeline` + 手动 `retract` 处理。

## Open Questions

- 场景集里"中文为主还是英文为主"？**已定：中文为主**，因为目标用户是中文用户，
  且 C2 的 FTS 已按中文 bigram 实现。英文表达各留 2 条作为对照。
- `MERGE` 的包含判定是否要做词形还原？**v1 不做**，只做精确包含与词集包含。
  词形还原引入的误判比它解决的多。
