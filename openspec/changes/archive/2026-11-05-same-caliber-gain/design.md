## 决策 1：剔除必然命中时，基线必须同步重算

**这是我上一轮算错的地方。**

我写"lexical 0.83 vs 随机 0.67，增益 +0.17"，用的是**全量**的分子分母。
而"必然命中"（空间 = 1）的基线是 `1/1 = 1.0`。

它同时抬高 SEH@1 与基线：

```
sample 全量：   SEH@1 = 5/6 = 0.8333，基线 = 0.6667，增益 +0.1667
sample 剔除后： SEH@1 = 3/4 = 0.7500，基线 = 0.5000，增益 +0.2500
```

**剔除后增益更大**，因为被剔除的 2 条 case 在抵消时净贡献为负
（它们的命中率 1.0 与基线 1.0 相同，但它们把剩下的基线拉高了）。

**所以"剔除"这个动作必须同时作用于分子与分母**，
只剔一半会让结论偏向"增益很小"。

## 决策 2：绝对分数与相对增益是两个问题

**旧结论**："threeway 比 lexical 差"（因为 0.30 < 0.83）。

**同口径之后**：

| subject | lexical 增益 | threeway 增益 | 差距 |
|---|---|---|---|
| `sample` | +0.2500 | **+0.2167** | **0.0333（相当）** |
| `billing` | +0.4167 | **−0.0278** | **0.4445（真差距）** |

**`sample` 上 threeway 的绝对分只有 40%，但相对增益只差 13%。**
它绝对分低是因为**基线低 6 倍**（0.0833 vs 0.5000）。

**所以"结论 5"要改**：

> 不是"三路融合让 top-1 变低"（绝对分数），
> 而是"`sample` 上相对增益相当，`billing` 上为负"。

## 决策 3：基线差异归因到排序空间，不是"RRF 算错了"

| 配置 | 排序空间 | 基线 |
|---|---|---|
| lexical | **1–4 条** | 0.4167（billing 剔除后） |
| threeway | **9–12 条** | 0.1111 |

**`mean(1/空间)`**：空间越小，基线越高。

**threeway 把整个池拉进排序**，而 lexical 只拉 1–4 条。
**lexical 的"强过滤"本身就是有效的排序信号**——
它把 9 条 pool 砍到 1–4 条，剩下的大概率包含 gold。

**所以"融合稀释"的精确机制**：

```
不是 RRF 算错了
而是 threeway 的候选集大了 3 倍，其中大部分是噪声
而 lexical 的强过滤等价于一层有效的预排序
```

**这解释了为什么加特征救不了**：问题在候选集大小，不在特征。

## 决策 5：HANDOFF 锚点是防御性修正，不是 bug 修复

**用户的判断需要修正**：他说锚点会因数字变化而 `IndexError`。

**实测**：

```
测试用的锚点： '真正该看的数字：'
含数字吗：    False

模拟 347 -> 400：
  '真正该看的数字：'    -> OK
  '真正该看的数字：347' -> IndexError
```

**锚点本身不含数字，所以 347 变 400 时不会断。**

**真正的风险**是标题格式改成"### 347 个 Scenario"这种**数字前置**形式——
那时 `"真正该看的数字："` 会找不到。

**所以这是防御性修正**，改法：

```python
# 旧
text.split("真正该看的数字：")[1]
# 新
text.split("### 真正该看的数字")[1]
```

**用 `###` 前缀锚定小节**，这样标题里数字怎么变都不影响。

**为什么仍值得做**：与之前"锚点不写死章节号"是同一类修正，
而且代价只有两行。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 同口径表更复杂，读者可能只看绝对分 | 两种口径并列，且标注旧对比"不能直接读" |
| "相当"这个词需要阈值 | 写成 `|差| < 0.05`，并给出实际差 0.0333 |
| threeway 剔除后 n 不变（无必然命中） | 明确写出 n 相同，说明剔除对它无影响 |

## 不做的事

- **不改融合规则**：同口径表已指出原因（候选集大小），改融合需要单独变更
- **不加特征**：问题不在特征
- **不测 cosine**
- **不造 v3 数据**
