## 决策 1：撤销"候选集太大"这个解释

**我上一轮写的是**："threeway 把整个池拉进排序，基线因此低 5 倍。
这是'融合稀释'的精确机制。"

**实测否决了它**：裁剪候选集会让增益**单调变差**。

| N | `sample` 增益 | `billing` 增益 |
|---|---|---|
| 1 | **−0.8000** | **−0.8333** |
| 3 | −0.0333 | −0.2500 |
| 5 | +0.1000 | −0.1167 |
| 全量 | **+0.2167** | **−0.0278** |

**为什么裁剪会变差**：`增益 = SEH@1 − 基线`。
裁剪让基线从 `1/9` 跳到 `1/1`（涨 9 倍），而 `SEH@1` 最多涨到 1——
**基线涨得比命中率快**。

**所以"候选集大小"是一个描述性事实（基线低确实因为它），
但不是可操作的改进方向。**

## 决策 2：真正的原因是"重排无法改变融合顺序"

**gold 明明在前 3 名**：

| subject | 位置分布 | rank ≤ 3 | top-1 |
|---|---|---|---|
| `sample` | `[1,1,2,2,2,3,3,4,4,8]` | **7/10** | 2/10 |
| `billing` | `[1,1,2,2,2,2,2,3,3,3,3,6]` | **11/12** | 2/12 |

**billing 有 11/12 在前 3，却只有 2/12 排第一。**

**而重排动不了它们**：

```
base = rrf_norm(fusion_score)   严格单调
-> 按 base 排序 == 按融合分排序 == 融合顺序
```

**实测确认**：`base-only` 的 top-1 == 融合 rank-1 率，**两者完全相同**（2/10、2/12）。

**所以"重排的上限 = 融合顺序的 rank-1 率"**。
要突破它，重排层必须有一个**不与融合顺序单调相关**的特征。

## 决策 3：cosine 是唯一有证据的候选

| 量 | `sample` | `billing` |
|---|---|---|
| cosine top-1 | **0.9000** | **0.8333** |
| threeway `SEH@1` | 0.3000 | 0.0833 |
| "只有 cosine 最高" | 4/10 | 2/12 |

**它不是"追平 lexical"，而是在更大的候选集上取得更高命中**。
上一轮我说"cosine 只能追平"是错的——**我比较了两个不同的候选集**
（lexical 的 6/9 条 vs 全融合的 10/12 条）。

## 决策 4：泄漏检查的三条判据

| 判据 | 为什么需要 |
|---|---|
| 均值差 | 断层（> 0.5）说明几乎所有 case 都被分开 |
| 唯一最高比例 | 接近 100% 说明单特征解决全部 |
| 分布重叠 | `min(gold) < max(dist)` 说明有交错 |

**实测**：

| subject | 差 | 唯一最高 | 重叠 |
|---|---|---|---|
| `sample` | +0.1673 | 9/10 | ✅ 0.4692 < 0.5770 |
| `billing` | +0.1156 | 10/12 | ✅ 0.4517 < 0.6431 |

**三条都过**，所以是"真信号"。

**为什么要写成三条而不是一条**：

- 只看均值差：会漏掉"差很小但完全没有重叠"的情况（分布窄而分离）
- 只看唯一最高：会漏掉"gold 均值明显高但方差很大"的情况

## 决策 5：不现在加 cosine

**理由**：加它需要四步，每步都是独立决策：

| 步 | 内容 | 需要决定 |
|---|---|---|
| 1 | 让 v3 产物记录 cosine | 进 `features_by_tag` 还是独立字段 |
| 2 | 进 `FeatureScores` | 第五个字段？还是替换 `condition`？还是替换 `status`？ |
| 3 | 预注册权重 | 现有 4 组是三项结构，加第四项要重新预注册 |
| 4 | 泄漏检查写成断言 | 本变更已做（但只在 v2 数据上） |

**本变更只做第 4 步**（把泄漏检查写成断言），因为它是**前置条件**：
若检查不过，后面三步都不该做。

## 决策 6：替换 `status` 而不是加第四项

**用户提的方案，我认同**。

`status` 已被证明恒为常数（池内方差 0/10、0/12），它占 0.3 权重是**空的**。

```
现状：RerankWeights(base=0.4, authority=0.3, status=0.3)
提案：RerankWeights(base=0.4, authority=0.3, cosine=0.3)
```

**结构不变（三项，和为 1）**，只是把空权重换成有信号的。
这比"加第四项"改动小，且 `PREREGISTERED_WEIGHTS` 的四组结构不用变。

**但 `status` 不能删**：它在 `FeatureScores` 里是**观测事实**（记录候选的状态），
只是不该参与加权。这与 `condition` 的处理一致。

**这个决策不在本变更范围**，只是记录。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| cosine 的泄漏检查只在 v2 数据上做过 | 明确写"一次测量"，v3 数据要重做 |
| 位置分布可能随数据变化 | 写成断言，变了会红 |
| 裁剪方案被否决，但可能有人重新提出 | 把 N 与增益的关系写成断言 |

## 不做的事

- **不加 cosine 特征**
- **不改产物格式**
- **不定 v3 数据**
- **不改融合规则**
