# evaluation-harness Specification

## Purpose
定义评测骨架的行为契约：如何加载基准数据、如何运行一条基线、如何计算指标与置信区间，
以及如何保证同一份输入在重复运行时给出完全相同的数字。它不关心记忆系统内部实现，
只关心"同一把尺子"是否可信、可复现、可归因。

## Requirements

### Requirement: 基准数据加载

系统 SHALL 能从 FactConsolidation 格式的数据集中加载样本，并保留每条事实的原始序号。
加载器 MUST 支持按长度子集（6K / 32K / 64K / 262K）与单跳/多跳（SH / MH）筛选。

#### Scenario: 加载 6K 单跳子集
- **WHEN** 调用方指定 `length=6k` 且 `hop=sh`
- **THEN** 返回的样本数大于 0，且每条样本包含有序事实列表与对应问题、标准答案

#### Scenario: 序号被保留
- **WHEN** 一条样本含 5 条事实
- **THEN** 每条事实携带其在原文中的位置序号，且序号在样本内单调递增

#### Scenario: 不存在的子集
- **WHEN** 调用方指定一个数据集不包含的长度子集
- **THEN** 系统报出明确错误，列出可用子集，而不是返回空列表

#### Scenario: 数据文件缺失
- **WHEN** 指定的数据集文件不存在
- **THEN** 系统报错并给出下载地址，且**不自动联网下载**（保证离线可复现）

### Requirement: 基线运行器

系统 SHALL 提供三种可独立运行的基线：`no-memory`、`full-context`、`naive-rag`。
每次运行 MUST 产出一份结构化结果，包含每条样本的预测、是否命中、以及 token 用量。

#### Scenario: 三种基线均可运行
- **WHEN** 对同一数据集分别运行三种基线
- **THEN** 各产出一份结果 JSON，且三者使用完全相同的样本集合与顺序

#### Scenario: 结果包含逐样本记录
- **WHEN** 查看任一基线结果
- **THEN** 其中包含每条样本的 id、预测答案、是否命中、以及输入/输出 token 数

#### Scenario: 未知基线名
- **WHEN** 调用方指定一个未注册的基线名
- **THEN** 系统报错并列出所有可用基线名

#### Scenario: 基线共享同一生成路径
- **WHEN** 三条基线处理同一条样本
- **THEN** 它们使用完全相同的系统提示词与生成函数，唯一差别是喂入上下文的构造方式

#### Scenario: 系统提示词不得泄露解法
- **WHEN** 检查任一条基线发出的系统提示词
- **THEN** 其中不包含"编号大者更新""取最新"之类提示冲突消解规则的措辞，
  否则基线会免费获得被测方法的核心思路，导致比较失去意义

### Requirement: 答案匹配指标

系统 SHALL 实现 `substring_exact_match`：去除首尾空白、做 NFKC 归一并折叠大小写后，
标准答案作为预测答案的子串出现即为命中。

#### Scenario: 完全一致
- **WHEN** 标准答案为 `"Paris"`，预测为 `"Paris"`
- **THEN** 判定命中

#### Scenario: 大小写与空白差异
- **WHEN** 标准答案为 `"paris"`，预测为 `"  Paris  "`
- **THEN** 判定命中

#### Scenario: 预测包含额外说明
- **WHEN** 标准答案为 `"Paris"`，预测为 `"The answer is Paris."`
- **THEN** 判定命中

#### Scenario: 空预测
- **WHEN** 预测为空字符串或 null
- **THEN** 判定未命中，且不抛异常

#### Scenario: 空标准答案
- **WHEN** 标准答案为空字符串或仅含空白
- **THEN** 系统明确报错，因为空标准答案无法用于子串匹配

#### Scenario: 中文答案
- **WHEN** 标准答案为 `"北京"`，预测为 `"北京。"`
- **THEN** 判定命中

#### Scenario: 数字前缀的已知误判
- **WHEN** 标准答案为 `"42"`，预测为 `"421"`
- **THEN** 判定为命中——这是该指标口径的已知弱点，由测试显式锁定，
  不允许被"顺手优化"成词边界匹配，否则与官方分数不可比

### Requirement: 配对 bootstrap 置信区间

系统 SHALL 用配对重采样计算指标差异的 95% 置信区间，重采样次数默认 10000，
随机种子可配置。

#### Scenario: 全部命中
- **WHEN** 100 条样本全部命中
- **THEN** 返回的准确率为 1.0，区间为 `[1.0, 1.0]`

#### Scenario: 各占一半
- **WHEN** 100 条样本中恰好 50 条命中
- **THEN** 返回的准确率为 0.5，且置信区间覆盖 0.5

#### Scenario: 同种子可复现
- **WHEN** 用相同种子连续计算两次
- **THEN** 两次返回的区间端点完全相同

#### Scenario: 两组配对的差异
- **WHEN** 传入两组一一对应的逐样本结果
- **THEN** 返回两组准确率之差及其置信区间，而非两个独立区间

#### Scenario: 配对比独立更窄
- **WHEN** 两组结果高度正相关且差异极小时
- **THEN** 配对区间必须显著窄于把两组当独立样本得到的区间

### Requirement: 可复现性保证

系统 SHALL 在缓存完整时保证同一输入产生完全相同的指标数值。
任何 LLM 或 embedding 调用 MUST 经过磁盘缓存，且在缓存命中时 MUST NOT 发起网络请求。

#### Scenario: 热缓存下重跑
- **WHEN** 完成一次运行后，以相同参数再次运行
- **THEN** 两次的结果 JSON 逐位相同，且第二次的网络调用数为 0

#### Scenario: 缓存完整性校验
- **WHEN** 执行缓存检查命令且两类缓存均完整
- **THEN** 退出码为 0

#### Scenario: 缓存缺失或不完整
- **WHEN** 任一缓存不存在、为空或含损坏条目
- **THEN** 退出码非零，并指出是哪一类缓存的哪个条目出了问题

#### Scenario: 冷缓存首次运行
- **WHEN** 缓存为空时运行
- **THEN** 系统仍能产出结果，并明确记录本次产生了多少次网络调用

### Requirement: 运行追踪

系统 SHALL 在每次运行中把每个样本的处理过程写成 JSONL 事件，字段至少包含
样本 id、阶段名、耗时、输入输出 token 数、网络调用数、以及错误类型（若有）。

#### Scenario: 事件可追溯
- **WHEN** 完成一次运行
- **THEN** 输出的 JSONL 中每条样本至少有一条事件，且事件可通过样本 id 关联到结果 JSON

#### Scenario: 失败样本不被静默丢弃
- **WHEN** 某条样本在处理中抛出异常
- **THEN** 该样本在结果中标记为错误并记录错误类型，而不是从结果集中消失

#### Scenario: 未知阶段被拒绝
- **WHEN** 写入一个未定义的阶段名
- **THEN** 系统立即报错，而不是接受任意字符串导致后续聚合报表漏数据

### Requirement: 分类质量的度量

系统 SHALL 为多类别判定任务提供：逐类混淆矩阵、macro-F1、以及逐类的配对 bootstrap 区间。
指标 MUST 对类别不均衡稳健，且 MUST NOT 只报总体准确率。

#### Scenario: 六类混淆矩阵
- **WHEN** 对一批判定结果计算质量
- **THEN** 输出 6×6 混淆矩阵，行是人工确认的期望类别，列是系统给出的判定

#### Scenario: macro-F1 不偏向多数类
- **WHEN** 某个类别只有 3 条样本且全部判错，其余类别全对
- **THEN** macro-F1 因该类的 0 分而明显下降，而不是被总体准确率掩盖

#### Scenario: 逐类区间
- **WHEN** 报告某一类的 F1
- **THEN** 同时给出该类的样本数与 bootstrap 区间，样本数过少时明确标注区间不可靠

#### Scenario: 单类无样本
- **WHEN** 某个类别在评估集中没有样本
- **THEN** 该类在矩阵中显示为 0 样本，且不计入 macro-F1 的分母，
  而不是被当作 0 分拉低整体

#### Scenario: 同种子可复现
- **WHEN** 用相同种子重复计算
- **THEN** 混淆矩阵与全部区间逐位相同

#### Scenario: 标注不一致的条目单列
- **WHEN** 两名标注者的标签不一致
- **THEN** 这些条目在报告中单列，且不静默采用任意一方

### Requirement: 检索质量的度量

系统 SHALL 为检索任务提供 SEH@K、SRS 与四类失败归因，并 MUST 同时给出
样本数与配对 bootstrap 区间。系统 MUST 记录每次评估中各召回路径的返回条数，
使"路径参与测量"与"路径空转"可区分。

#### Scenario: SEH@K 的定义
- **WHEN** 计算某 K 值的 SEH
- **THEN** 标准答案位于前 K 条的比例即为该值，取值在 [0, 1]

#### Scenario: SRS 的定义
- **WHEN** 计算 SRS
- **THEN** 按标准答案的排名归一化到 [0, 1]，排名第 1 得 1.0，
  完全未召回得 0.0，且 MUST 与 SEH@K 分开报告

#### Scenario: K 大于结果总数
- **WHEN** K 超过实际返回条数
- **THEN** 按实际返回条数计算，不把缺失位置算作命中

#### Scenario: 区间与样本数
- **WHEN** 报告任一检索指标
- **THEN** 同时给出样本数与 bootstrap 区间；样本数过少时明确标注

#### Scenario: 配对比较
- **WHEN** 比较两个检索配置
- **THEN** 用配对 bootstrap 在同一批查询上比较，而非两次独立采样

#### Scenario: 召回路径的返回条数被记录
- **WHEN** 完成一次检索评估
- **THEN** 结果中包含每条召回路径各自的返回条数，而不只是融合后的候选数

#### Scenario: 路径空转必须可见
- **WHEN** 某条召回路径被调用但返回 0 条
- **THEN** 该事实出现在结果中，且报告中不得把该次评估描述为"三路都参与了排序"

#### Scenario: 无 gold 的 case 必须单独计数
- **WHEN** 样本中存在没有 `gold_item_id` 的 case
- **THEN** 这些 case MUST 单独计数，且 MUST 从召回类指标的分母中排除

#### Scenario: 比例区间必须说明方法与适用性
- **WHEN** 报告给出任何比例区间
- **THEN** MUST 同时说明所用方法与样本量；样本量小时 MUST 说明该方法在此规模下的适用性

### Requirement: 路径贡献的可测性

系统 SHALL 能给出"全部召回路径开启"与"仅开启部分路径"两种配置的指标对比，
使新增路径是否有贡献成为可观测事实，而不是靠"是否被调用"推断。

#### Scenario: 配置对比
- **WHEN** 在同一数据集上分别运行"三路全开"与"只开词面"
- **THEN** 输出两组指标及其配对差异区间，而不是只给单组分数

#### Scenario: 差异为零也是一种结论
- **WHEN** 两种配置的指标完全相同
- **THEN** 报告中明确写出"新增路径在该数据上没有可观测贡献"，
  不得省略该对比、也不得把它记作通过

#### Scenario: 单路基线不因多路接入而改变
- **WHEN** 只开启词面路径并重跑历史数据集
- **THEN** 每条 case 的排名与历史归档结果逐位相同，
  证明新增路径没有改动既有排序逻辑

### Requirement: 结果文件记录逐条特征分

检索评测的结果文件 MUST 为每条 case 记录三个排序特征：`base`、`authority`、`status`，置于 `features` 子对象。

`condition` MUST 单独记录在 `condition_score` 字段（数值或 `null`），不得放进 `features`。
它不参与排序，但它的分布是判断"条件是否可被查询侧获得"的唯一依据。

#### Scenario: 每条 case 的 features 含三个键

- **WHEN** 一次评测产生 N 条 case
- **THEN** 每条 case 的 `features` 恰好含 `base` / `authority` / `status` 三个数值字段

#### Scenario: condition_score 独立记录

- **WHEN** 一次评测产生 N 条 case
- **THEN** 每条 case 都含 `condition_score` 字段，值为数值或 `null`

#### Scenario: 字段缺失时拒绝写出

- **WHEN** 任一 case 的 `features` 缺键，或缺 `condition_score` 字段
- **THEN** 评测 MUST 报错，不得写出缺字段的结果文件

#### Scenario: gold 未召回时两侧同时表达

- **WHEN** 某条 case 的 gold 没有进入重排候选集
- **THEN** `features` MUST 为 `null`，**且** `features_by_tag` 里 MUST 不含 gold 的 tag

- **AND** MUST NOT 用 `{}` 表示未召回：`{}` 是"存在但没有键"的对象，与"不存在"无法区分

#### Scenario: 特征分足以复现名次

- **WHEN** 用结果文件中记录的 `features` 与当次权重重新计算得分并排序
- **THEN** 每条 case 的名次与记录中的 `rank_after_rerank` 完全一致

### Requirement: 结果产物的分区

评测产物 MUST 按来源分区存放，不得混在同一层。每个分区 MUST 在**分区清单**里显式登记，
并写明**由哪条检查负责**。

分区清单 MUST 与磁盘一致，两个方向都要断言：

| 方向 | 违反形式 |
|---|---|
| 清单覆盖磁盘 | 新增 `results/foo/` 而未登记 -> **必须失败** |
| 磁盘覆盖清单 | 登记了 `features/` 却从不创建 -> 允许（预留），但 MUST 写明"尚不存在" |

**不得用"一个文件属于几个分区"作为判据**：文件系统保证一个文件只能在一个目录里，
所以"互斥"在这个设计里没有可被违反的形式，是一条恒真约束。

#### Scenario: v2 档案只统计顶层

- **WHEN** 统计 v2 档案的分类数与总数
- **THEN** MUST 只统计 `results/*.json` 顶层，**不含任何子目录**

- **AND** 该数量 MUST 作为历史事实固定，不随新版本产物增长而改写

#### Scenario: v3 产物独立指纹

- **WHEN** `results/v3/` 出现结果文件
- **THEN** 每个文件 MUST 带指纹，且 MUST NOT 与 v2 档案的指纹相同

- **AND** 指纹相同 MUST 视为"这批结果是旧代码跑的"，而不是"指纹校验太严"

#### Scenario: 历史对照物不得并入当前批

- **WHEN** `results/archive/` 下的文件带指纹
- **THEN** 其指纹 MUST NOT 与当前批相同

- **AND** 它们 MUST NOT 被登记进当前批的指纹清单——**并入会让"当前批同源"这个断言失效**

#### Scenario: 未知分区必须拒绝

- **WHEN** `results/` 下出现未登记的子目录
- **THEN** 校验 MUST 失败，而不是静默忽略

- **AND** 判据 MUST NOT 依赖"该目录里恰好有 json"：空目录出现时也 MUST 失败，
  否则"目录存在但为空"是一个不可见的过渡状态

#### Scenario: 分区未就绪时的空转必须可见

- **WHEN** 某分区尚无文件，其校验无法执行
- **THEN** 该校验 MUST 跳过，且跳过消息 MUST 非空并写明"这不代表已通过"

- **AND** MUST 另有独立测试在临时目录上证明**同一判据会失败**，
  否则"空转"与"检查从不生效"在输出上无法区分

- **AND** "该独立测试存在"这件事本身 MUST 被断言——它被删掉时，
  主校验的跳过就重新变成永久跳过

#### Scenario: 有文件时不得跳过

- **WHEN** 某分区**已经有文件**
- **THEN** 该分区的主校验 MUST NOT 跳过；MUST 给出通过或失败

- **AND** 跳过条件 MUST 依赖**传入的目录**，MUST NOT 依赖某个全局常量所指向的真实目录。
  否则会出现"传临时目录时正常、生产路径上不跑"

- **AND** 判据 MUST 断言"分区非空时动作是 `run` 或 `fail` 之一"，
  MUST NOT 只断言"跳过消息非空"——后者在"检查根本没跑"时也成立

- **AND** 双向覆盖：本 scenario 管"分区有文件 -> 检查必须跑"；
  "文件 -> 必须被某分区覆盖"是另一条（见「未知分区必须拒绝」）

**为什么这条独立存在**：`skip` 与 `pass` 在 CI 输出里几乎一样（都是通过信号）。
而"检查没跑"有三种原因，处置完全不同：

| 原因 | 例子 | 处置 |
|---|---|---|
| 数据不存在 | v3 空目录 | 合理，允许 skip |
| 路径写错 | `dev.jsonl.jsonl` | 缺陷，必须红 |
| **条件写宽** | "依赖真实目录"而非"依赖传入目录" | **缺陷，且最隐蔽** |

第三种在你传临时目录时表现正常，只在生产路径上不跑——**本项目已出现过两次第一种误判、一次第三种雏形**。

### Requirement: 门禁的适用域

读结果文件的门禁 MUST 区分**两件不同的事**，且 MUST 分别回答：

| 问题 | 必须由什么回答 |
|---|---|
| 当前代码是哪一代装置？ | 一个**显式常量**（MUST NOT 从产物推） |
| 这份文件能不能回答当前装置的问题？ | **常量与文件签名的比较** |

**只有当判据依赖装置时**才返回"不适用"；判据不依赖装置的门禁 MUST 照常执行。

#### Scenario: 判据依赖装置的门禁返回不适用

- **WHEN** 某门禁的判据依赖排序装置，且文件签名**不等于** `CURRENT_APPARATUS`
- **THEN** 门禁 MUST 返回 `applicable=False`，`passed` MUST 为 False

#### Scenario: 判据不依赖装置的门禁照常执行

- **WHEN** 某门禁的判据与排序装置无关
- **THEN** 它 MUST 照常执行并给出**通过或失败**

#### Scenario: 装置签名只读结构事实

- **WHEN** 需要判断一份结果文件由哪个装置产生
- **THEN** 签名 MUST 由文件自身的结构决定

- **AND** MUST NOT 依赖 `apparatus` 之类的常量字段

#### Scenario: 分类写宽时必须被抓住

- **WHEN** 有人把"判据不依赖装置"的门禁也判成"不适用"
- **THEN** MUST 有测试会红

#### Scenario: 当前装置必须识别为适用

- **WHEN** 断言"当前装置是哪一代"
- **THEN** MUST 比较 `CURRENT_APPARATUS` 与**当前代码实际产出的签名**

- **AND** MUST NOT 只断言常量值

#### Scenario: 判据依赖装置不等于判据失效

- **WHEN** 某门禁的判据在 v3 下的**期望值**变了
- **THEN** MUST 在 v3 下给出**新的期望值并执行**

#### Scenario: 门禁必须能发现所有分区的产物

- **WHEN** 结果文件位于任何**已登记分区**
- **THEN** 门禁 MUST 能发现它

- **AND** 文件发现 MUST NOT 依赖文件名前缀

#### Scenario: 找不到文件必须显式区分三件事

- **WHEN** 门禁没有找到可用的结果文件
- **THEN** MUST 区分：分区为空（`applicable=False`）/
  有文件但不匹配（`passed=False`）/ 有匹配文件（执行判据）

- **AND** 前两种 MUST NOT 返回 `passed=True`

#### Scenario: 不适用在账本里必须与失败分开

- **WHEN** 汇总一次 `run_all()` 的结果
- **THEN** MUST 分别报 **通过 / 不适用 / 未通过** 三个数

- **AND** `不适用` MUST NOT 计入 `未通过`

- **AND** 结果文件的每条 check MUST 含 `applicable` 字段

#### Scenario: 判据没有主语时必须判失败，不判不适用

- **WHEN** 装置匹配、文件可读，但数据形状让某条判据**没有对象**
- **THEN** `passed` MUST 为 False，`applicable` MUST 保持 True

#### Scenario: 测试判据必须与账本三态一致

- **WHEN** 某测试检查"未通过项是否被分类"
- **THEN** 它 MUST 用 `applicable and not passed`，MUST NOT 用 `not passed`

- **AND** 必须有证伪证明：删真失败 -> 红；删不适用 -> 不红

#### Scenario: 历史判定与当前判定必须分开标注

- **WHEN** 某测试读**冻结的结果文件**做出判定
- **THEN** 测试名与 docstring MUST 写明它验的是**哪一代装置**

- **AND** MUST NOT 使用 `actually_fails` 这类默认"现在"的措辞

#### Scenario: 读冻结文件时不得假设三态字段存在

- **WHEN** 某测试读**冻结的 v2 文件**（`v2-*-gates.json`）
- **THEN** 它 MUST 只用该文件实际拥有的字段

- **AND** MUST NOT 用 `applicable` 做判据——**那份文件没有这个字段**

- **AND** 实测：`v2-sample-gates.json` 与 `v2-billing-gates.json`
  的 `checks[*]` 键只有 `[code, detail, passed, title]`

**为什么**：那些文件由 v2 装置产出，那时只有两态。
用三态判据读会 `KeyError`，或更糟——静默把缺失当成 `False`。

- **AND** 三态判据只适用于**当前 `run_all()` 的返回值**，不适用于冻结文件

### Requirement: A 轴饱和判据的分母

`F24`（A 轴 `SEH@1` 不得满分）的分母 MUST 是**已评分**的 A 轴 case 数，
MUST NOT 是全部 A 轴标注数。

未评分的 case（池不足 K 被跳过、`rank_after_rerank` 为 `None`）
MUST 从分母中排除。

#### Scenario: 未评分 case 不计入分母

- **WHEN** 某 subject 的 A 轴有 10 条标注，其中 6 条因池不足被跳过
- **THEN** 分母 MUST 为 4，MUST NOT 为 10

#### Scenario: 三路配置下的数字不变

- **WHEN** 结果文件里全部 A 轴 case 都被评分
- **THEN** 修改前后 `SEH@1` MUST 相同

#### Scenario: 低报必须可被看见

- **WHEN** 存在一份单路配置的结果文件，其 A 轴有未评分 case
- **THEN** MUST 有测试断言其 `SEH@1` 用正确口径计算

- **AND** 该测试 MUST 用**单路**文件

#### Scenario: 结果侧未跑不得算作通过

- **WHEN** `F24` 没有找到任何结果文件
- **THEN** `passed` MUST 为 False

- **AND** 若该代产物尚无（分区为空），MUST 返回 `applicable=False` 并说明

#### Scenario: 两个池大小必须分别命名

- **WHEN** 计算轴归属或随机基线
- **THEN** MUST 使用对应的量：

  | 量 | 定义 | 用途 |
  |---|---|---|
  | `n_competitors` | 池中与 gold **同 relation** 的候选数（不含 gold） | 轴派生 |
  | `ranking_pool_size` | 实际参与排名的候选数（含 gold） | 随机基线 `1/N` |

- **AND** `ranking_pool_size` MUST 从竞争集定义取，
  MUST NOT 由 `n_competitors + 1` 推算

- **AND** 实测例外（全部是 C 轴）：`ledger-q11/q12`（`n=0, cs=12`）、
  `billing-c1/c2/c3`（`n=2, cs=9`）

#### Scenario: 随机基线必须按派生轴分组

- **WHEN** 计算某装置的随机基线
- **THEN** 轴归属 MUST 由池结构派生，MUST NOT 读数据集的标注字段

- **AND** 基线 MUST 用 `ranking_pool_size` 的 `1/N`

- **AND** 现有 v2 数据的验收值：

  ```
  axis_baseline_derived(sample) ==
      {"relation_within": 0.3000, "relation_cross": 0.0833}
  ```

- **AND** `relation_cross` MUST 是 `1/12`，MUST NOT 是 `1/1`

#### Scenario: 空轴必须返回缺失值，不得返回 0

- **WHEN** 某个派生轴没有任何查询
- **THEN** 该轴的基线 MUST 为 `None`（或缺席），**MUST NOT 为 `0.0`**

- **AND** 调用方 MUST 显式处理 `None`

**为什么**：`0.0` 作为基线意味着"随机命中率是 0"，于是任何实测值
（哪怕也是 0）都会 `ratio <= baseline` 而报红——
**"没有数据"会伪装成"基线是 0"**。

- **AND** 实测：`billing` 的 `relation_cross` 是空组（三个 relation 全多分支），
  MUST 返回 `None`

#### Scenario: v3 下的判据是"比随机好"

- **WHEN** `F24` 在 v3 装置下执行
- **THEN** 结果侧 MUST **同时**满足两档：

  | 档 | 判据 | 违反形式 |
  |---|---|---|
  | 下限 | `ratio > baseline` | 排序比随机还差 |
  | 上限 | `ratio < ceiling`（`0.9999`） | **数据太简单** |

- **AND** MUST NOT 只设下限：v3 数据要求"每 subject 至少一个单值 relation"，
  而单值 relation 意味着池可能很小（`n_competitors=1` -> 池 2），
  `ratio` 容易满分——**只设下限会放行"数据太简单"**

- **AND** 上限在 v3 下的语义是**数据难度**，不是装置语义：
  v2 里满分意味着"指标测不到区分能力"（装置与数据都有关），
  v3 里满分只说明"这份数据太容易"

#### Scenario: v3 的数据侧恒真必须被登记

- **WHEN** `F24` 在 v3 下检查数据侧（基线是否饱和）
- **THEN** MUST 在代码注释与本节写明：**该判据在 v3 下恒真**

- **AND** 理由：派生 within 的池大小 `= n_competitors + 1 >= 2`，
  基线最大 `1/2 = 0.5`，永远小于 `0.9999`

- **AND** MUST 保留该判据：它防的是"池大小退化成 1"这个形状退化
  （`n_competitors` 全为 0 时基线变 1.0）

- **AND** 真正有判别力的是结果侧（下限 + 上限），MUST NOT 让读者以为两段都在验

#### Scenario: 标注与派生的不一致必须被报告

- **WHEN** 报告某 subject 的轴统计
- **THEN** MUST 报"标注与派生不一致 N/M"

- **AND** 该数字 MUST NOT 依赖门禁使用哪套轴

- **AND** 实测基线：`sample` 0/12、`billing` **3/12**

### Requirement: 报告的统计数字必须有单一来源

报告里的统计数字 MUST 由一个可被程序读取的函数产出
（`evals/tools/recount_specs.compute()`），MUST NOT 由测试断言硬编码的字面量。

**测试的判据 MUST 是"文档里写的是 spec 算出的数"**，
MUST NOT 是"文档里写的是测试里的字面量"。

#### Scenario: 测试从 compute() 读值

- **WHEN** 某测试要验证报告里的统计数字
- **THEN** 它 MUST 调 `compute()` 取值，并与**文档内容**比对

- **AND** MUST NOT 在测试里写 `assert total == 282` 这类字面量——
  那会让"文档"与"测试"成为两个真相来源

#### Scenario: 文档写错必须被抓到

- **WHEN** 报告里的某个数字被写错（与 spec 算出的不符）
- **THEN** MUST 有测试变红，且消息指出**期望值与实际值**

- **AND** 该判据 MUST 经过证伪：改错 Scenario 合计、改错四类百分比、
  改错四类合计，三种都必须红

#### Scenario: 数字必须分三类，不得一刀切

- **WHEN** 把统计数字改成"自动读取"
- **THEN** MUST 按下表分类处理：

  | 类型 | 特征 | 处置 |
  |---|---|---|
  | **A. 纯计算** | 分子与分母都能从 spec 算出 | 读 `compute()` |
  | **B. 分子人工 + 分母计算** | 分子是人工结论 | **只自动分母**；分子 MUST 是显式常量 |
  | **C. 纯文案** | 是说明，不是数字 | 保留字面 |

- **AND** MUST NOT 把 B 类当作 A 类处理——那会让"人工结论"伪装成"自动算出"

#### Scenario: B 类的分子必须是显式常量

- **WHEN** 某个统计数字的分子是人工判断的结果
- **THEN** 该分子 MUST 是一个**具名常量**（例如 `MANUAL_MAPPING_ROWS = 3`），
  MUST NOT 是 f-string 里的字面量

- **AND** 具名常量 MUST 带注释说明"为什么它不能算"

**为什么**：实测 `recount_specs.py` 里 5 个分子全是 f-string 里的字面量
（`f"| 符号存在 | 1/{total_must} ..."`）——读者看不出那个 `1` 是人工填的。
把它们改成具名常量之后，"这不是算出来的"变成可见的事实。

- **AND** 实测这些分子不能算的理由：

  | 分子 | 含义 | 为什么不能算 |
  |---|---|---|
  | `1` | "符号存在"= 1 条 | 与 `has_fn` 巧合相等，但定义是"能在 src 里 exists" |
  | `0` | "行为符合"= 0 条 | 人工判定"没有任何测试验证行为" |
  | `3` | "人工映射表"= 3 行 | 数 HANDOFF 表格行 -> 测试依赖文档 -> 循环 |
  | `3` | "Scenario 分母"= 3 | 人工登记者"有几个 scenario 有映射测试" |

#### Scenario: 统计脚本必须可被 import

- **WHEN** 测试需要读统计数字
- **THEN** 脚本 MUST 暴露一个返回结构化数据的函数

- **AND** 该函数 MUST 接受根目录作为**参数**（不是模块常量）——
  否则测试无法在临时目录上验证它

- **AND** 实测：本变更前脚本只有 `main()` 打印字符串，
  `from evals.tools.recount_specs import compute` 抛 `ImportError`

### Requirement: 统计断言的判据必须限定范围

当报告里同一个格式的字符串出现多次时，断言 MUST 限定在它对应的那一节之内，
MUST NOT 扫全文。

**"扫全文"在数字不同时会通过，但那只是巧合**——它没有验证"这一节写对了"。

#### Scenario: 同一格式字符串出现多次

- **WHEN** 报告里 `| **合计** | **N** |` 这类格式出现多次（MUST 表 / Scenario 表 / 要求数）
- **THEN** 验证其中一处的断言 MUST 先切出它所在的那一节

- **AND** MUST NOT 直接 `assert f"..." in text`

**为什么**：实测三处 `| **合计** | **N** |` 分别在 §0.6 的 MUST 表、
Scenario 表、要求数。两条断言都扫全文，所以：

| 构造 | 结果 |
|---|---|
| Scenario 真值 220 / 文档写 219；MUST 真值 220 / 文档写 220 | **通过**（被 MUST 表顶替） |

**Scenario 表写错了，而断言因为另一节的数字而通过。**

#### Scenario: 限定范围后必须仍能抓到错误

- **WHEN** 用同一个构造（Scenario 表写错、另一节数字相同）
- **THEN** 限定范围后的断言 MUST **红**

- **AND** 该判据 MUST 经过证伪：修之前通过、修之后红

#### Scenario: 两个同源的量必须交叉断言

- **WHEN** 同一个事实有两个来源（一个是扫描算出，一个是手写常量）
- **THEN** MUST 有断言要求两者相等

- **AND** 实测：`four_way.has_fn.n`（扫描算出）与
  `MANUAL_SYMBOL_EXISTS_ROWS`（手写常量）都是 1，
  但**没有任何断言保证它们相等**

- **AND** 若 spec 新增一条"实现 foo"，`has_fn` 变 2 而常量仍 1，
  三层表显示 `1/214`、四类表显示 `2/214`，**两处数字不一致而无人发现**

#### Scenario: 验证脚本可用的断言不得污染输出

- **WHEN** 某测试要验证统计脚本可用
- **THEN** 它 MUST 调 `compute()` 并断言其返回值，MUST NOT 调 `main()`

- **AND** `main()` 只证明"没抛异常"，且会把整份报告打印到 stdout——
  在 `-q` 下看不出来，而那正是问题

- **AND** 判据 MUST 包含内部一致性：四类之和 == 总数

### Requirement: 门禁的产物来源必须登记且可从源码复算

当门禁读取 `results/` 下的产物时，它读哪个文件、用什么方式发现
MUST 被登记成可执行的事实，MUST NOT 只写在文档或注释里。

**"谁在读文件"必须能从源码复算**：手写的清单会漂移，本项目已实测到三处。

#### Scenario: 登记的读法必须等于源码的读法

- **WHEN** 登记表声明某条门禁读某个文件
- **THEN** MUST 有断言用 AST 从 `check_v2_dataset.py` 派生出该门禁实际读什么
- **AND** 派生的结果 MUST 与登记逐条相等
- **AND** MUST **含空集**：派生说某条不读文件，登记里就不能有它

**为什么不能用"登记的文件都存在"代替**：那只能抓到"文件没了"，抓不到
"登记写的是另一个文件"。实测 `L6b` 登记成 `a3-with-dedup.json`，而它实际读
`a3-lexical-vector-adjacency.json`——两个文件都存在，所以存在性检查全绿。

#### Scenario: 派生必须递归跟进模块内 helper

- **WHEN** 门禁经模块内 helper 间接读文件（`F19b`/`F20` 经 `_ablation_for_subjects`）
- **THEN** 派生 MUST 跟进这些 helper
- **AND** MUST NOT 只看 check 函数体

**为什么**：只看函数体会漏掉 `F19b`/`F20`，而它们恰好是**能看到 v3** 的那一族。

#### Scenario: 发现方式决定能否看到分区，必须分开登记

- **WHEN** 某条门禁用 `_load_run(name)` 或直接拼 `ROOT/"results"/"<name>"` 读文件
- **THEN** 它 MUST 登记在"写死路径"那一族
- **AND** 该族 MUST 被断言为**看不到** `results/<zone>/` 的产物

- **WHEN** 某条门禁用 `result_files(pattern)` 读文件
- **THEN** 它 MUST 登记在"发现式"那一族
- **AND** `pattern` MUST NOT 带装置版本前缀（如 `v2-`）

**为什么前缀是错的**：`result_files()` 扫 `results/` 顶层 + `ZONE_NAMES`，
前缀是装置的事、由 `apparatus_signature` 判断。带 `v2-` 前缀的登记
会在 v3 产物出现时**匹配不到**，于是"有人重跑就自动失效"的机制不触发。
实测：旧方式 `glob("v2-*")` 找到 2 个且看不到 v3；新方式 `result_files("*")`
找到 4 个且看到 v3。

#### Scenario: 门禁数量断言必须分组

- **WHEN** 断言 result-side 门禁的条数
- **THEN** MUST 同时断言总数（7）与两族各自的条数（4 / 3）

**为什么**：只断言总数时，把一条从写死组挪到发现组不会红——
但它的**适用域**完全变了（从"看不到 v3"变成"看得到"）。

### Requirement: 产物选择必须优先当前装置

当同一类产物存在多个装置签名的版本时，门禁 MUST 优先选择签名等于
`CURRENT_APPARATUS` 的那一份，MUST NOT 取"排序后的第一个"。

#### Scenario: 当前装置产物存在时不得被判为跨装置不适用

- **WHEN** `results/` 下同时存在 v2 与 v3 的同类产物
- **THEN** `_ablation_for_subjects` MUST 返回签名等于 `CURRENT_APPARATUS` 的那份
- **AND** 相应门禁 MUST **执行判据**，MUST NOT 报"由 v2 装置产物"

**实测**：旧实现 `for path in candidates` 取第一个匹配的，而 `sorted()` 让
`v2-sample-...` 排在 `v3-sample-...` 前面，于是：
`F20` 拿到 v2 文件 -> 判"跨装置不适用" -> **v3 产物被遮蔽**。

**为什么"排序后的第一个"必然错**：`results/` 顶层永远有 v2 产物，
所以只要有同类 v2 文件，v3 产物就永远轮不到。

#### Scenario: 没有当前装置产物时保持旧行为

- **WHEN** 所有候选产物的签名都不等于 `CURRENT_APPARATUS`
- **THEN** MUST 取第一个匹配的
- **AND** 相应门禁的跨装置判定 MUST 照常生效

**为什么不能改成"没有就报空"**：那会把"这代还没数据"变成"失败"，
与三态语义冲突。

#### Scenario: 遮蔽的证伪必须让结论真的改变

- **WHEN** 验证"v3 产物不被遮蔽"
- **THEN** 判据 MUST 是"放 v3 产物后该门禁的 `(applicable, passed)` 改变了"
- **AND** MUST NOT 是"`result_files()` 的返回值里包含 v3 路径"

**为什么**：`result_files()` 返回了 v3，`_ablation_for_subjects` 仍可能选 v2。
**"能发现文件"与"用了那个文件"是两件事**——实测过前者为真、后者为假。

### Requirement: 文档里的门禁计数必须能从源码复算

当文档陈述"几条门禁读 `results/`""几条能看到某个分区"时，
这些数字 MUST 有断言要求它们等于从源码派生的结果，
MUST NOT 只是写在文档里由人维护。

#### Scenario: 读文件的门禁数变化时必须被发现

- **WHEN** 新增一条读 `results/` 的门禁，或让已有的门禁改变发现方式
- **THEN** 文档里对应的计数 MUST 变红

- **AND** 断言 MUST 从源码派生，MUST NOT 从文档反向推断

**为什么**：这些数字是给读者回答"造完 v3 数据谁来验"的。
上一轮读代码得出的答案是"6 条"，实际 7 条；再读一次得出"4 条写死"，
而登记表里写的是另外两个文件名。**凡是没有断言守着的数字，都会漂移。**

#### Scenario: 两族必须互补且覆盖全部读文件的门禁

- **WHEN** 断言写死路径族与发现式族
- **THEN** MUST 断言两族无交集
- **AND** MUST 断言两族并集 == 全部读文件的门禁集合
- **AND** MUST 断言"能看到分区"的集合 == 发现式族

**为什么**：只断言各自条数时，把一条从写死组挪到发现组不会红——
但它的适用域完全变了。并集/交集断言能抓到这种"条数没变、性质变了"的改动。

### Requirement: 分项计数必须逐行复算，不得只验合计

当文档用表格按能力（或其他维度）拆分某个总数时，每一行的数字
MUST 与计算函数逐个比对，MUST NOT 只断言合计。

**合计断言抓不到分项错误**：合计对时分项写错，合计断言**必然通过**。

#### Scenario: 分项写错而合计不动必须被发现

- **WHEN** 把某张按能力拆分的表里一行的数字改错，合计保持不变
- **THEN** 必须有断言变红
- **AND** 红的时候 MUST 指出是哪张表、哪个能力、写的是多少、真值是多少

**实测三处**（都是这个形态，都曾经全绿）：

| 表 | 写错的行 | 合计 | 结果 |
|---|---|---|---|
| MUST/SHALL 行表 | `evaluation-harness` 64，实际 143 | 226 一直对 | 三条断言全绿 |
| Scenario 表 | 98 改成 97 | 300 不动 | 三条断言全绿 |
| 要求数表 | `evaluation-harness` 13，实际 18 | 59 是**对的** | 无任何断言 |

#### Scenario: 分项之和必须等于该表声明的合计

- **WHEN** 表格里同时有分项与合计
- **THEN** MUST 断言 `sum(分项) == 合计`

**为什么需要两条而不是一条**：

| 检查 | 抓什么 | 能被单独违反吗 |
|---|---|---|
| 逐行 == `compute()` | 某行数字写错 | ✅ 改一行 |
| `sum(分项) == 合计` | 少了/多了一行，或合计被手改 | ✅ 删一行 / 改合计 |

**不要加第三条"合计 == `compute()` 总和"**：它在前两条都通过时**必然成立**
（逐行全对 → 分项和 == `compute()` 总和；再等于合计 → 合计 == 总和），
所以**永远不会被单独违反**。那是恒真断言，不是判据。
本项目已有明确纪律：判据必须能与意图一起被违反。

**实测**：要求数表的分项之和是 54、合计 59 —— 第二条抓它；
把每行都改成正确值后，`sum` 自然等于 `compute()` 总和，第三条无事可做。

#### Scenario: 定位表格必须用表头，不能用字符串包含

- **WHEN** 从一个 Markdown 小节里取某张表
- **THEN** MUST 先按表头定位该表，再解析它的行
- **AND** MUST NOT 用 `f"| `{name}` | {value} |" in section`

**两个实测原因**：

1. **同节有多张两列表**：§0.6 里既有 MUST/SHALL 行表又有四类细分，
   只按"两列 + 反引号"筛会同时抓到，导致 MUST 表被读成四类表的数字
   （实测 `conflict-resolution` 被读成 35 而不是 9）。
2. **加粗写法不统一**：文档里同时存在 `` | `cap` | 30 | `` 与
   `` | **`cap`** | **30** | ``。字符串匹配要枚举所有组合，
   实测漏掉了 `retrieval-apparatus` 那一行。
3. **`in section` 会被别处的数字顶替**：正文里出现同一个数字也会通过。

### Requirement: 产物缺失的语义必须按产物族区分

不同产物族的"缺失"含义不同，处置 MUST 不同，且该映射 MUST 被断言固定。

| 产物族 | 缺失的含义 | 处置 |
|---|---|---|
| 一次性实验产物（`a3-*.json`） | **那次实验没做** | `applicable=True, passed=False`（失败） |
| 每代产物（`v2-*` / `v3-*`） | **这代还没数据** | `applicable=False`（不适用） |

#### Scenario: 一次性实验产物缺失必须判失败

- **WHEN** `results/a3-*.json` 不存在
- **THEN** 读它的门禁 MUST 判 `applicable=True, passed=False`
- **AND** MUST NOT 判成不适用

**为什么**：把 `a3-*.json` 缺失判成"不适用"，等于把"实验没做"
从失败列表里移出去——**用不适用掩盖没检查**，正是本项目一直在防的形态。

**实测当前行为**（`results/` 为空目录）：

```
L6a: applicable=True  passed=False  "缺少 a3-lexical-vector-adjacency.json"
L6b: applicable=True  passed=False  "缺少 a3-lexical-vector-adjacency.json"
L6c: applicable=True  passed=False  "缺少真实运行结果 a3-..."
L8:  applicable=True  passed=False  "缺少 a3-with-dedup.json"
```

#### Scenario: 每代产物缺失必须判不适用

- **WHEN** `results/` 下没有任何同类产物（既无 v2 也无 v3）
- **THEN** 读它的门禁 MUST 判 `applicable=False`
- **AND** MUST NOT 判成失败

**为什么两者必须配对写**：只写"一次性产物缺失要红"，
读者会以为"所有缺文件都该红"；只写"每代产物缺失要不适用"，
读者会以为可以给 `_load_run` 加三态。**两句话合起来才是完整映射。**

#### Scenario: "不改"的决定必须写成断言

- **WHEN** 评审确认某个"看起来该改"的行为其实是正确的
- **THEN** MUST 把它写成断言，MUST NOT 只写进文档或口头结论

**为什么**：否则下一个人会重新提出同样的改法。本变更的
`test_fixed_path_gates_fail_when_artifact_missing` 就是为此存在——
它不是因为"这里可能有 bug"，而是因为"这里曾经被误判为 bug"。

**证伪**：把那 4 条门禁改成"缺文件 -> 不适用"，该断言变红
（"L6a 在 a3-*.json 缺失时被判成**不适用**"）。

### Requirement: 能看得到当前装置产物的门禁，必须写明红的归因

当一条门禁读取当前装置的产物时，它"红了意味着什么" MUST 被写成可执行的断言，
MUST NOT 只写"预期通过"。

**"预期通过"不够**：造完数据看到红色时，人需要知道**该改什么**。

#### Scenario: 归因必须分档，且每档绑定一条门禁

- **WHEN** 有多条门禁会验同一代产物
- **THEN** 每条门禁 MUST 有一个归因档位（`apparatus` / `data`）
- **AND** 归因表 MUST 恰好覆盖这些门禁，不多不少

**实测三档**（`sample` 数据集，v3 装置）：

| 门禁 | 归因 | 红了说明 | 该去查什么 |
|---|---|---|---|
| `F19b` | `data` | 某条 implicit 的 gold 没被召回 | 召回路径 / 查询措辞 |
| `F20` | `apparatus` | condition 又回到加权里 | 排序代码 |
| `F24` | `data` | 数据太难或太简单 | 数据本身 |

#### Scenario: 归因必须由行为证明，不能凭判据的名字推断

- **WHEN** 断言某条门禁的归因是 `data`
- **THEN** MUST 构造"数据被破坏"的场景，证明它真的会红
- **AND** MUST NOT 只凭"它读的是数据"或"它名字里有 gold"来分类

**实测反例**：曾把 `F19b` 归为"结构必然"（因为它只读 implicit 的 rank）。
实测发现正好相反——构造一条 `rank=None`，它立刻红：

```
F19b: applicable=True passed=False
      1 条 implicit 从未被召回：['ledger-q3']
```

**根因**：`F19b` 判"召回是否成功"，而**召回不依赖排序装置**。
这正是它被归为"照跑"的理由，也**恰恰是它不可能是结构必然的理由**。

#### Scenario: "结构必然"必须与"恒真"区分开

- **WHEN** 某条门禁在某装置下的期望值是结构决定的（如 v3 下 `F20` 的 drop 必为 0）
- **THEN** MUST 构造一个与该结构矛盾的输入，证明门禁真的会红
- **AND** MUST NOT 让判据退化成"签名匹配就通过"

**实测**（`F20`）：

```
v3 签名 + drop=0     -> passed=True   "掉幅 +0.0000"
v3 签名 + drop=0.5   -> passed=False  "掉幅 +0.5000 不为 0"
```

**"必然为 0"的来源**是 `ablate()` 在 v3 下两次跑出相同 ranks，
**不是**"签名是 v3 所以判据自动通过"。后者会让这条门禁变成恒真断言。

#### Scenario: 归因表与发现方式表必须分开

- **WHEN** 新增一条能读取当前装置产物的门禁
- **THEN** MUST 同时更新"发现方式"表与"归因"表
- **AND** 两张表 MUST 各自有独立断言

| 表 | 判什么 |
|---|---|
| 发现方式（`DISCOVERED_GATES`） | 哪些门禁看得到该装置的产物 |
| 归因（`RED_ATTRIBUTION`） | 它们红了各自意味着什么 |

**为什么分开**：合并成一张表时，改动会同时影响两件事而断言只覆盖其一。
分开之后，"谁能看到 v3"变了会红在发现方式表，"归因写错"会红在归因表。

#### Scenario: 归因要写进 detail，不是只写进测试

- **WHEN** 门禁红
- **THEN** 它的 `detail` MUST 说明归因方向

**实测要求**：

| 门禁 | detail 必须含 |
|---|---|
| `F20`（v3 下掉幅不为 0） | "condition 又参与了加权" |
| `F24`（低于基线） | "基线" |
| `F24`（高于上限） | "太容易" |

**为什么**：造完数据看到红色时，人先看的是 detail，不是测试文件。
detail 只说"掉幅 0.5000"不够——它没说该去改哪。

### Requirement: `F24` 报告增益大小，不得设目标区间

`F24` 在 v3 下的结果侧 detail MUST 同时写出实测值、派生基线、以及两者的差。
MUST NOT 引入"目标区间"（如 `0.5 < ratio < 0.9`）。

#### Scenario: detail 必须能直接读出增益

- **WHEN** `F24` 的结果侧执行了
- **THEN** detail MUST 含 `实测 <hit>/<n>=<ratio>`
- **AND** MUST 含 `派生 within 基线 <baseline>`
- **AND** MUST 含 `差 <gain:+.4f>`

**为什么三个都要**：只报 `ratio` 时，"等于基线"与"远高于基线"
会写成一模一样的句子——那是两条相反的结论。

**实测**（v3 装置跑 v2 数据）：

| subject | baseline | ratio | 差 |
|---|---|---|---|
| `sample` | 0.3000 | 0.3000 | **+0.0000** |
| `billing` | 0.2778 | 0.0833 | **−0.1944** |

`sample` 的差为 0 是**结论**，不是"数据缺了基线"。
若 detail 只写 `ratio=0.3000`，读者无法把它与基线 0.3000 联系起来。

#### Scenario: 失败时也必须报增益

- **WHEN** `F24` 的结果侧判红（高于上限或低于基线）
- **THEN** detail MUST 仍然含差额

**为什么**："太容易"时的差值是 `+0.7222`——那是**数据有多容易**的量化。
只在通过时报，红的时候读者仍要手算。

#### Scenario: 负差值的负号必须保留

- **WHEN** `ratio < baseline`
- **THEN** detail MUST 写成 `差 -0.1944`，MUST NOT 写成 `差 0.1944`

**为什么**：`−` 与 `+` 是两条相反的结论（排序比随机差 vs 好）。
格式化必须用 `+.4f`（带符号），不能用 `.4f`。

#### Scenario: 不得引入目标区间

- **WHEN** 有人想"让这条门禁更严格"
- **THEN** MUST NOT 加 `target_low` / `target_high` / `TARGET_*` 之类的常量
- **AND** 该禁止 MUST 有断言守着

**为什么定区间会诱导改数据**：

| 做法 | 后果 |
|---|---|
| 定 `0.5 < ratio < 0.9` | 造数据时为让 ratio 落进区间而调难度 —— 为达标回头改数据 |
| 先造出来再看 | ratio 落进哪里都接受 —— 上限 `0.9999` 失去约束力 |

**报告差值不会诱导改数据**：它不判"落在哪"，只陈述"增益多少"。

#### Scenario: 这条限制本身必须可被违反

- **WHEN** 在 `F24` 的函数体里加 `TARGET_LOW = 0.5`
- **THEN** `test_f24_has_no_target_range` MUST 红

**为什么需要**：否则"不得设区间"只是一句话。
断言读的是 `F24` 函数体的源码文本，`TARGET_` 任一出现即红。

### Requirement: v3 排序特征的能力边界必须可复算

v3 的三个排序特征（`base` / `authority` / `status`）各自"能提供什么信号"
MUST 被写成可执行的断言，MUST NOT 只写在报告或注释里。

**实测边界**（v2 数据，v3 装置）：

| 特征 | 性质 | 判据 |
|---|---|---|
| `status` | 恒为常数 | 池内方差 == 0 |
| `base` | 等于融合顺序 | `rrf_norm` 严格单调 |
| `authority` | 分层过滤器 | 同层逆序 == 0 |

#### Scenario: status 在候选池内必须有方差，否则必须登记它恒为常数

- **WHEN** 检查 `status` 特征
- **THEN** MUST 断言"池内方差 == 0"这个事实，或断言它有方差
- **AND** 声明"恒为常数"时 MUST 同时指出它占的权重是空的

**实测**：

```
记忆库的 status 取值：sample {'ACTIVE'}  billing {'ACTIVE'}
候选池内 status 有方差：0/10、0/12
uniform 里 status 权重 0.3 -> 净效为空
```

**为什么不直接删掉这个权重**：删权重是装置变更（HARKing 风险），
登记"它现在是空的"是事实陈述。两者不同。

#### Scenario: base 必须被证明等价于融合顺序

- **WHEN** 用 `base` 作为排序特征
- **THEN** MUST 断言 `rrf_norm` 严格单调
- **AND** 由此得出"按 base 排序 == 按融合顺序排序"

**实测**：

```
输入 [0.0, 0.1, 0.5, 1.0, 2.0, 5.0]
输出 [0.0, 0.02, 0.1, 0.2, 0.4, 1.0]   严格递增
```

**为什么这条重要**：它把"base-only 的 ratio = 0.20"从
"base 是负贡献"纠正为"融合顺序本身的 top-1 率"。
前者会让人以为"去掉 base 更好"，而剥掉 base 等于剥掉裁决规则本身。

#### Scenario: authority 必须是过滤器，不是信号

- **WHEN** 只在 authority 上排序（base=0, status=0）
- **THEN** MUST 断言"同一 authority 层内部，相对顺序与融合顺序完全一致"
- **AND** MUST NOT 把 auth-only 的增益解释为"authority 选中了 gold"

**实测**：22 个 case（sample 10 + billing 12），**同层逆序 0 个**。

**这意味着**：authority 的全部作用是**把低 authority 的项推到高层之后**，
层内裁决仍由融合顺序完成。

**若同层逆序 > 0**：说明 authority 内部还有额外信号（比如浮点精度差异），
那时"过滤器"这个结论要重核。

### Requirement: 数据侧 MUST NOT 制造 authority 与 gold 的相关性

v3 数据 MUST NOT 为了提高排序增益而让 `authority` 与 gold 相关。
该禁止 MUST 有断言守着。

**为什么这是最重要的一条**：它是"为达标造数据"的新形态——
不是改分数，而是**改数据结构让某个特征变得决定性**。

#### Scenario: gold 不得是唯一的最高 authority

- **WHEN** 检查任意 subject 的任意 case
- **THEN** "gold 的 authority 严格高于池内所有其他项"的 case 数 MUST 为 0

**实测 v2**：`sample 0/10`、`billing 0/12`。

**为什么它是泄漏**：若 gold 唯一最高，auth-only 直接 = 1.0，
任务退化成"选权威最高的那个"，一个特征解决全部。

#### Scenario: gold 与干扰项的平均 authority 不得有系统差

- **WHEN** 计算 `mean(authority of gold)` 与 `mean(authority of distractors)`
- **THEN** 两者之差 MUST 满足 `|差| < 0.05`

**实测 v2**：

| subject | gold mean | distractor mean | 差 |
|---|---|---|---|
| `sample` | 0.8660 | 0.8904 | **−0.0244** |
| `billing` | 0.9433 | 0.9221 | **+0.0213** |

两个都在阈值内。**sample 上 gold 甚至更低**——它不是靠权威赢的。

#### Scenario: 这条禁止必须可被违反

- **WHEN** 构造一份数据，让 gold 的 authority 是池内唯一最高
- **THEN** 上述两条断言 MUST 红

**为什么需要**：否则"不得制造相关性"只是一句话。
证伪的具体形式见 tasks.md §4。

#### Scenario: v3 的 authority 与 v2 的 condition 处在同一个位置

- **WHEN** 设计 v3 数据
- **THEN** MUST NOT 让 `authority` 成为"与 gold 同向的元数据先验"

**v3 的 `authority` 与 v2 的 `condition` 是同一位置上的同一个东西**：
一个与 gold 同向的元数据先验。

| 装置 | 先验 | 后果 |
|---|---|---|
| v2 | `condition` 匹配 | 几乎自动第 1，实测 `SEH@1 = 1.0000` |
| v3（若按"让 authority 有区分度"造数据） | `authority` 更高 | 同样会退化成单特征决定 |

**区别在于可发现性**：`condition` 是显式的查询条件，
而 `authority` 看起来像"合理的排序信号"——**因此更难发现**。

**所以这条禁止必须写成断言**，而不是"注意不要"。

### Requirement: 百分比必须标注分母，不同分母不得直接比较

当报告用百分比陈述"某配置比另一配置好/差"时，
MUST 同时写出分母，且 MUST NOT 用不同分母的百分比直接相减。

#### Scenario: 同一指标有多个分母时必须全部写出

- **WHEN** 某指标的分子与分母随配置而变（如"已召回"的 case 数不同）
- **THEN** MUST 写出所有相关分母下的数值
- **AND** MUST 明确哪一种用于"端到端"、哪一种用于"组件本身"

**实测三个分母**（`F24`/结论 5 同型）：

| 分母 | sample lexical | sample 三路 | billing lexical | billing 三路 |
|---|---|---|---|---|
| 全部派生 within | 5/10 = 0.5000 | 3/10 = 0.3000 | 8/12 = 0.6667 | 1/12 = 0.0833 |
| 已召回 | 5/6 = 0.8333 | 3/10 = 0.3000 | 8/9 = 0.8889 | 1/12 = 0.0833 |
| **配对（都召回）** | **5/6 = 0.8333** | **3/6 = 0.5000** | **8/9 = 0.8889** | **1/9 = 0.1111** |

**只写"0.8333 vs 0.3000"是错的**：两个分母不同（6 vs 10），相减没有意义。

#### Scenario: 配对比较是"组件质量"的唯一可比口径

- **WHEN** 要比较两个配置的排序/重排质量
- **THEN** MUST 只比较"两个配置都召回了 gold"的 case
- **AND** MUST 把它与"端到端"口径分开报

**为什么两者都要报**：
- 只报端到端：把"召回少"算到"重排差"头上
- 只报配对：掩盖"三路召回更全"这个优点

### Requirement: 融合稀释的结论必须与"多路召回有害"区分

当报告陈述"三路融合让 top-1 低于单路"时，
MUST 同时陈述"三路召回率更高"，且 MUST 明确两者方向相反。

#### Scenario: 必须同时报召回与精度

- **WHEN** 陈述融合稀释
- **THEN** MUST 同时给出召回数与配对 top-1

**实测**：

| 指标 | lexical 单路 | 三路 | 方向 |
|---|---|---|---|
| 召回（gold 在池内） | 6/10 | **10/10** | **变好** |
| top-1 精度（配对） | 0.8333 | 0.5000 | **变差** |

**若省略这个限定**，读者会把 `0.8333 → 0.5000` 读成"该砍掉 vector 路"。
而正确的读法是：**召回层变好了，融合层的排序没跟上。**

#### Scenario: 这条限定必须有断言守着

- **WHEN** 文档缺少"不是多路召回有害"这句限定
- **THEN** 必须有测试变红

**为什么**：限定句是最容易被"精简"掉的部分，
而它正是防止错误行动（砍掉某一路）的唯一屏障。

### Requirement: 报告数字的复算不得新增结果文件

当新增报告结论需要新的测量数据时，
MUST NOT 在 `results/` 顶层新增文件（顶层必须保持 48 个）。

#### Scenario: 复算用现场重跑

- **WHEN** 某条结论需要新的测量
- **THEN** MUST 写成现场重跑的测试
- **AND** MUST NOT 写成新的 `results/*.json`

**为什么**：`results/*.json` 顶层 48 个是分区约束的一部分。
新增一个文件会破坏"顶层永远 48 个"这条断言，而它守的是分区纪律。

**embedding 走缓存**，所以现场重跑不产生 API 调用。

#### Scenario: 复算数字必须与文档逐项比对

- **WHEN** 测试现场重跑得到数字
- **THEN** MUST 与文档里的数字逐项比对（计数，不是只有比例）

**为什么用计数**：计数（`5/6`）比小数（`0.8333`）更能定位问题——
若是 `n` 变了、还是分子变了，一眼可分。

### Requirement: 文档结构的断言必须匹配表格行，不得用关键词包含

当断言"文档里必须有某一行"时，
MUST 解析表格行的单元格，MUST NOT 用 `"关键词" in section`。

#### Scenario: 关键词会在整行被删后仍然通过

- **WHEN** 断言 `"配对" in section`
- **THEN** 若 §6 里 `"配对"` 出现 8 次（标题、正文、表格），
  删除表格那一行后断言**仍然通过**

**这是本项目反复出现的"字符串包含"顶替形态。**
实测过：抽掉表格的 `| **配对（都召回）** |` 那一行，用关键词断言全绿。

**正确判据**：切出那张表，解析每行首列，断言目标字符串是**某个单元格的完整内容**。

**为什么括号要包含在内**：`| 已召回 |` 是 `| 已召回 | 5/6 ... |` 的前缀，
单独匹配前者会与"三路全召回"那行混淆。

### Requirement: 结论必须区分"现象"与"机制归因"

当报告陈述"配置 A 比配置 B 差"时，
若存在多个机制都能产生同样的结果，MUST 显式声明"机制未区分"，
且 MUST 列出这些机制。

#### Scenario: 未区分机制时必须写明

- **WHEN** 报告陈述某个下降
- **THEN** MUST 说明该下降的可能机制，若未区分则 MUST 明写"机制未区分"

**实测**：结论 5 的 `0.8333 → 0.5000` 有两个可能机制：

| 机制 | 处置 |
|---|---|
| 融合规则（RRF 稀释） | 改融合 |
| vector 召回质量（cosine 排序） | 改召回 |

**两者处置完全不同，而现象完全相同。**

#### Scenario: 未区分的原因必须写明

- **WHEN** 声明"机制未区分"
- **THEN** MUST 说明**为什么**不能区分

**实测**：区分它们需要 cosine 分，而现有 15 份冻结产物都没有记录：

```
v2-billing-lexical-vector-adjacency.json   features_by_tag 为空
含 cos/similar 的字段：无
```

**若不写原因**，读者会以为"还没做"，而实际是"当前产物格式做不到"。

#### Scenario: 累加值必须标明，不得被读成单条

- **WHEN** 报告引用 `path_returns.<path>` 这类顶层聚合值
- **THEN** MUST 说明它是累加值
- **AND** MUST 给出单条 case 的量级

**实测**：

| 产物 | 顶层 `vector` | 单条 case | `pool_size` |
|---|---|---|---|
| `a3-lexical-vector-adjacency.json` | 462 | 14 | 14 |
| `v2-billing-lexical-vector-adjacency.json` | 108 | 9 | 9 |

**单条 case 的 `path_returns.vector` 恒等于 `pool_size`**：vector 路返回整个池。

**误读的代价**：以为"vector 返回海量噪声"，从而去压缩召回——
而它返回的就是全部候选，没有可压缩的东西。

### Requirement: 产物断言与文档断言必须分开

当某个事实同时体现在"产物"与"文档"两处时，
MUST 分成两条断言，MUST NOT 用一条断言声称覆盖两者。

#### Scenario: 只读产物的断言不得声称覆盖文档

- **WHEN** 断言函数名声称"文档写了 X"（如 `test_report_documents_...`）
- **THEN** 它 MUST 真的读文档
- **AND** MUST NOT 只读产物

**实测的坑**：本轮先写了一条 `test_report_documents_vector_returns_whole_pool`，
**但它只读产物**。删掉文档里"返回了整个池"那句话，断言不会红——
**名字声称覆盖的内容无人守**。

#### Scenario: 两条断言必须各自能被单独违反

- **WHEN** 拆分产物断言与文档断言
- **THEN** 改文档 MUST 只让文档断言红
- **AND** 改产物 MUST 只让产物断言红

**验证方式**：

| 构造 | 文档断言 | 产物断言 |
|---|---|---|
| 删掉文档里那句话 | **红** | 绿 |
| 改产物里一个值 | 绿 | **红** |

**若两者同时红或同时绿**，说明它们没有真正分开。

### Requirement: 词面重叠的分析必须区分"未召回"与"未排对"

当用"query 与 gold 的文本重叠"解释检索得分时，
MUST 把 case 分成三类，MUST NOT 合并计算。

| 组 | 含义 | 能否用重叠解释 |
|---|---|---|
| A | 召回了 gold **且** top-1 | ✅ |
| B | 召回了 gold 但未 top-1 | ✅（对照） |
| C | **没召回 gold** | ❌ 与重叠无关 |

#### Scenario: 未召回的 case 不得混进重叠统计

- **WHEN** 计算"命中的 case 的重叠率"
- **THEN** MUST 排除"没召回 gold"的 case

**实测后果**：`sample` 的 4 条 implicit 查询（q3/q4/q7/q8）
**bigram 全为 0 且全部未召回**。若把它们混进"未命中组"，
未命中组的均值会被 0 拉低，从而**夸大**重叠的解释力。

**实测数据**：

| subject | A 组 | B 组 | C 组（未召回） |
|---|---|---|---|
| `sample` | 5 条，均值 0.1937 | 1 条，0.0400 | **4 条，均值 0.0000** |
| `billing` | 8 条，均值 0.1353 | 1 条，0.1562 | 3 条，均值 0.0104 |

### Requirement: 重叠能否解释 top-1 必须逐 subject 检验，不得合并

当用"词面重叠"解释 top-1 时，
MUST 对每个 subject 单独做检验，MUST NOT 用合并数据得出统一结论。

#### Scenario: 样本量小时必须做置换检验

- **WHEN** 每组的 n 小于 10
- **THEN** MUST 用置换检验，MUST NOT 只看均值差

**实测（精确置换，穷举全部组合）**：

| subject | A 组均值 | B+C 组均值 | 均值差 | 双侧 p |
|---|---|---|---|---|
| `sample` | 0.1937 | 0.0100 | +0.1837 | **0.0079** |
| `billing` | 0.1353 | 0.0741 | +0.0612 | **0.1091** |

**两个 subject 结论相反**：`sample` 显著，`billing` 不显著。

#### Scenario: 不得写成"lexical 高分 = 数据太容易"

- **WHEN** 陈述"lexical 的高分来自词面重叠"
- **THEN** MUST 先确认每个 subject 都支持这个说法

**实测反例**：`billing` 的 8 条 top-1 里有 **3 条 bigram < 0.05**：

| case | bigram | 为什么重叠低却命中 |
|---|---|---|
| `billing-c1` | 0.0357 | query「发票币种是怎么规定的？」vs gold「国内客户的发票一律开人民币」——共享"发票"的**语义**，不是字面片段 |
| `billing-c2` | 0.0345 | query「税务申报是按什么分的？」vs gold「华北的客户在北京税局申报」——共享"申报" |
| `billing-a3` | 0.0488 | query「德国那边的账怎么开」vs gold「欧洲客户走欧元发票」——**德国↔欧洲** |

**这是语义相关，不是词面重叠。** 所以 `bigram` 作为"数据是否太容易"的指标**不够**——
它会漏掉语义相关的命中。

#### Scenario: 低重叠的命中不算"数据太容易"

- **WHEN** 某 case 的 bigram 很低却 top-1
- **THEN** MUST NOT 把它算作"数据太容易"的证据

**为什么**：低重叠 + 命中说明模型抓到了**语义**，那是真实能力的一部分。
把它算作"数据简单"会让人去加难度，而实际是能力。

**反过来说**：若**全部** top-1 都是高重叠（如 `sample` 的 5/5 ≥ 0.05），
那才支持"这份数据的 top-1 主要由词面决定"。

### Requirement: `bigram` 指标的局限必须登记

当用 `bigram Jaccard` 度量"query 与原文的相似度"时，
MUST 登记它抓不到"语义相关但字面不同"。

#### Scenario: 指标的漏检必须可举例

- **WHEN** 声明 `bigram` 能代表"词面重叠"
- **THEN** MUST 给出它漏检的实例

**实测**：`billing-c1`（0.0357）、`billing-c2`（0.0345）、`billing-a3`（0.0488）
三个 case 都是**语义相关但字面重叠低**。

**这与 `L3` 的关系**：`L3` 用 bigram 上限 0.50 防"query 抄原文"。
它防的是**抄**，不是**语义相关**。两者不冲突，但不能互相替代。

### Requirement: 置换检验的对照组必须只含"可比"的样本

当用置换检验比较两组时，
对照组 MUST 只含与实验组在**同一维度**上可比的样本，
MUST NOT 混入因其他原因取低值的样本。

#### Scenario: "未召回"不得混入"未排对"的对照组

- **WHEN** 比较"词面重叠能否解释 top-1"
- **THEN** 对照组 MUST 只含"召回了 gold 但未 top-1"的 case
- **AND** MUST NOT 含"没召回 gold"的 case

**实测后果**：`sample` 的 4 条 implicit 全部未召回且 bigram = 0。
把它们混进对照组：

| 口径 | 对照均值 | 均值差 | p |
|---|---|---|---|
| A vs (B+C)（污染） | 0.0080 | +0.1857 | **0.0079** |
| A vs B（正确） | 0.0400 | +0.1537 | **0.3333** |

**p 从 0.3333 掉到 0.0079，而"显著"这个结论就是从这里来的。**

#### Scenario: 代码注释说"单独报"时，实现必须真的单独报

- **WHEN** 代码里有一条注释声明某组如何处置
- **THEN** 紧邻的实现 MUST 与该注释一致
- **AND** 若不一致，MUST 视为缺陷（而非注释过时）

**实测的原始代码**：

```python
# A 组与 B 组做检验（C 组与重叠无关，单独报）
b_vals = list(groups["B"].values())
_, p = _perm_test(a_vals, b_vals + list(groups["C"].values()))
```

**注释说"单独报"，下一行把 C 混进了对照组。**

**为什么它骗过了证伪**：证伪只看断言红不红。
而断言红是因为**代码算出了显著的 p**，不是因为它验证了注释。
**没有任何机制检查注释与实现是否一致。**

### Requirement: 统计断言必须断言具体值，不能只断言方向

当断言某个检验统计量（p 值、区间、比例）时，
MUST 断言具体数值（带容差），MUST NOT 只断言方向（`< 0.05` / `> 0.05`）。

#### Scenario: 方向断言会让"极端值"通过

- **WHEN** 断言 `p > 0.05`（不显著）
- **THEN** `p = 0.06` 与 `p = 0.99` 都通过

**但它们是两件不同的事**：前者是"接近显著"，后者是"完全无关联"。

**正确做法**：

```python
assert measured["sample"]["p"] == pytest.approx(0.3333, abs=1e-3)
assert measured["billing"]["p"] == pytest.approx(0.7778, abs=1e-3)
```

**为什么精确 p 可断言**：置换检验是**精确检验**，p = k/组合数 是离散确定的，
不依赖随机种子，重复运行得同一个值。

### Requirement: 排序空间必须与池大小分开

当解释"top-1 率"时，
MUST 区分"池大小"（全部候选）与"进入排序的候选数"（排序空间），
MUST NOT 用池大小作为随机基线的分母。

#### Scenario: 随机基线的分母是排序空间，不是池大小

- **WHEN** 计算"随机排序的 top-1 概率"
- **THEN** MUST 用 `1 / 排序空间`
- **AND** MUST NOT 用 `1 / 池大小`

**实测**：

| subject | 池大小 | lexical 排序空间 | 1/池 | **1/空间** |
|---|---|---|---|---|
| `sample` | 12–14 | 0–2 | 0.0833 | **0.6667** |
| `billing` | 9 | 0–4 | 0.1111 | **0.6111** |

**用 1/池 会把随机基线低估 8 倍**，于是"lexical 0.83 vs 随机 0.08"这个对比
看起来增益 +0.75，而实际是 **+0.17**。

#### Scenario: 排序空间 = 1 的 top-1 不是排序能力

- **WHEN** 某 case 的排序空间为 1
- **THEN** 它的 top-1 MUST 视为"必然命中"，不计入排序能力
- **AND** 报告 MUST 给出"剔除必然命中后"的数值

**实测**：

| subject | 报告值 | 空间=1 的条数 | 剔除后 | 随机基线 |
|---|---|---|---|---|
| `sample` | 0.8333 | **2**（q9, q10） | **0.7500** | 0.6667 |
| `billing` | 0.8889 | **3**（a5, a8, c2） | **0.8333** | 0.6111 |

**空间 = 1 意味着池里只有 gold 一条进了融合——不是"排得准"，是"没得选"。**

### Requirement: 订正必须保留旧结论并标注错因

当发现已发布的结论有错时，
MUST 保留旧结论并标注"这是错的、错在哪、为什么没被发现"，
MUST NOT 静默删除或只改正文。

#### Scenario: 读者会相信表格，不会相信订正说明

- **WHEN** 只改正文而在别处加一行"已更正"
- **THEN** 读者会读到两个矛盾的数，并相信**有公式和组合数的那个**

**所以订正必须写在**：错值出现的那一节内，且紧邻正确值。

#### Scenario: 必须写明"为什么没被发现"

- **WHEN** 记录一次订正
- **THEN** MUST 说明当时的证伪为何没有抓到

**本次的答案**：证伪时断言确实红了，但红是因为**代码算出了显著 p**，
不是因为**注释被验证**。**证伪检查代码行为，不检查注释。**

**写下这条的价值**：它把"下一次怎么防"从"更仔细"变成"知道这个形态存在"。

### Requirement: 增益必须在同一集合上同时计算分子与基线

当报告"某配置的 top-1 高于/低于随机基线"时，
MUST 在**同一批 case** 上同时计算命中率与基线，
MUST NOT 用不同集合的分子分母相减。

#### Scenario: 剔除必然命中时，基线也必须重算

- **WHEN** 从统计中剔除"排序空间 = 1"的 case
- **THEN** 基线 MUST 也在剔除后的集合上重算
- **AND** MUST NOT 沿用全量基线

**实测后果**：

| subject | 全量增益 | **剔除后增益** |
|---|---|---|
| `sample` | +0.1667 | **+0.2500** |
| `billing` | +0.2778 | **+0.4167** |

**剔除后增益反而更大**——因为必然命中的基线是 `1/1 = 1.0`，
它同时抬高分子与基线，**抵消后把增益压小了**。

#### Scenario: 两个配置的分母不同时，绝对分数不可直接相减

- **WHEN** 比较两个配置的 SEH@1
- **THEN** MUST 先确认两者的分母是同一集合
- **AND** 若不，MUST 改用同口径（都剔除必然命中，或都不剔除）

**实测**：

| 量 | 分子 | 分母 | 含必然命中 |
|---|---|---|---|
| lexical 0.8333 | 5 | 6 | **2 条** |
| threeway 0.3000 | 3 | 10 | 0 条 |

**分母不同（6 vs 10），且一个含必然命中**——`0.83 vs 0.30` 这个对比同时混了两种偏差。

### Requirement: 相对增益与绝对分数必须分开报告

当比较两个配置时，
MUST 同时给出绝对分数与相对增益（`SEH@1 − 基线`），
MUST NOT 只用绝对分数下结论。

#### Scenario: 绝对分低不等于增益低

- **WHEN** 某配置的 SEH@1 明显低于另一配置
- **THEN** MUST 比较两者的**相对增益**，而非只有绝对分

**实测**：

| subject | 配置 | SEH@1 | 基线 | **增益** |
|---|---|---|---|---|
| `sample` | lexical（剔除后） | 0.7500 | 0.5000 | **+0.2500** |
| `sample` | threeway | 0.3000 | 0.0833 | **+0.2167** |
| `billing` | lexical（剔除后） | 0.8333 | 0.4167 | **+0.4167** |
| `billing` | threeway | 0.0833 | 0.1111 | **−0.0278** |

**`sample` 上 threeway 的绝对分只有 lexical 的 40%，但相对增益相当**
（+0.2167 vs +0.2500）。它绝对分低是因为**基线低 6 倍**（0.0833 vs 0.5000）。

**`billing` 上才是真正的差距**：lexical +0.4167，threeway **−0.0278**。

#### Scenario: 基线差异必须归因到排序空间

- **WHEN** 两个配置的基线差异很大
- **THEN** MUST 指出基线的定义是 `mean(1/排序空间)`，并给出两个空间

**实测**：

| 配置 | 排序空间 |
|---|---|
| lexical | **1–4 条** |
| threeway | **9–12 条**（整个池） |

**threeway 把整个池都拉进排序**，lexical 只拉 1–4 条。
**lexical 的"强过滤"本身就是一种有效的排序信号**——
这才是"融合稀释"的精确机制，而不是"RRF 算错了"。

### Requirement: 旧对比不得删除，必须标注"不能直接读"

当修正一个已发布的对比时，
MUST 保留旧对比并标注它为什么不能直接读，
MUST NOT 只替换成新表。

#### Scenario: 读者会重新发现旧数字并误用

- **WHEN** 把 `0.83 vs 0.30` 直接替换成同口径表
- **THEN** 下一个人从 git 历史或旧报告里看到 `0.83 vs 0.30` 时，
  会以为那是可用的对比

**所以旧对比必须留着，并紧跟一条标注**：说明它混了两种偏差
（分母不同 + 一方含必然命中）。

### Requirement: 重排的上限必须由融合顺序决定

当报告"重排提升了排序"时，
MUST 同时给出"gold 在融合顺序中的位置分布"与"base-only 的 top-1"，
MUST NOT 只给最终 `SEH@1`。

#### Scenario: base-only 的 top-1 必须等于融合 rank-1 率

- **WHEN** 只用 `base` 一个特征排序
- **THEN** 其 top-1 MUST 等于"gold 在融合顺序中排第 1 的比例"

**实测**：

| subject | 融合 rank-1 率 | base-only top-1 |
|---|---|---|
| `sample` | 2/10 = 0.2000 | **2/10 = 0.2000** |
| `billing` | 2/12 = 0.1667 | **2/12 = 0.1667** |

**两者必须完全相同**，因为 `base = rrf_norm(fusion_score)` 是严格单调变换。

**若不等**，说明 base 引入了并列或额外信息，"等于融合顺序"这个结论要重核。

#### Scenario: 上升空间必须被量化

- **WHEN** 报告 `SEH@1` 低
- **THEN** MUST 同时给出 gold 在融合顺序中的位置分布
- **AND** MUST 说明"有多少 gold 在前 N 名"

**实测**：

| subject | 位置分布 | 中位数 | rank ≤ 3 | 实际 top-1 |
|---|---|---|---|---|
| `sample` | `[1,1,2,2,2,3,3,4,4,8]` | **3** | **7/10** | 0.2000 |
| `billing` | `[1,1,2,2,2,2,2,3,3,3,3,6]` | **2** | **11/12** | 0.1667 |

**`billing` 有 11/12 在前 3 名，却只有 2/12 排到第 1**——
**这说明上升空间很大，而重排没有利用它。**

### Requirement: 候选集裁剪方案必须用增益验证，不得只用绝对分

当提出"缩小候选集以提高精度"时，
MUST 用"增益 = `SEH@1` − 基线"验证，MUST NOT 只看 `SEH@1`。

#### Scenario: 裁剪会让基线上升得比命中率更快

- **WHEN** 只保留融合顺序的前 N 条
- **THEN** 必须报告"每个 N 下的增益"

**实测**：

| N | `sample` 增益 | `billing` 增益 |
|---|---|---|
| 1 | **−0.8000** | **−0.8333** |
| 3 | −0.0333 | −0.2500 |
| 5 | +0.1000 | −0.1167 |
| 全量 | **+0.2167** | **−0.0278** |

**增益随 N 单调递增**：裁剪越严格，基线上升越快。

**原因**：裁剪"保留前 N 条"会把 gold 排除在外。

**所以"候选集太大"不是主因**——裁剪它会让结果更差。

### Requirement: 新增排序特征前必须做泄漏检查

当考虑把某个量（如 cosine）作为排序特征时，
MUST 先检查它与 gold 的关系是否构成泄漏，检查结果 MUST 写成断言。

#### Scenario: 三个判据缺一不可

- **WHEN** 检查某个候选特征是否泄漏
- **THEN** MUST 同时给出：

| 判据 | 泄漏的形态 | 正常形态 |
|---|---|---|
| gold 与干扰项的均值差 | 断层（> 0.5） | 有差但重叠 |
| gold 是"唯一最高"的比例 | 接近 100% | 明显低于 100% |
| 分布是否重叠 | **不重叠** | `min(gold) < max(dist)` |

**实测（cosine）**：

| subject | gold 均值 | dist 均值 | 差 | 唯一最高 | 重叠 |
|---|---|---|---|---|---|
| `sample` | 0.5836 | 0.4163 | **+0.1673** | **9/10** | ✅ |
| `billing` | 0.6585 | 0.5429 | **+0.1156** | **10/12** | ✅ |

```
sample   gold 最小 0.4692 < dist 最大 0.5770
billing  gold 最小 0.4517 < dist 最大 0.6431
```

**三条都符合"真信号"而非"泄漏"。**

#### Scenario: 重叠判据是必要条件

- **WHEN** `min(gold) >= max(distractor)`
- **THEN** 该特征 MUST 视为泄漏嫌疑

**为什么**：完全不重叠意味着该特征能 100% 区分 gold 与干扰项——
那不是"排序能力"，是"标签泄漏"。

**实测两个 subject 都有重叠**，所以不构成泄漏。

#### Scenario: 一次测量不算证据

- **WHEN** 给出泄漏检查的数字
- **THEN** MUST 写成断言并由测试守护
- **AND** MUST 记录"这是一次测量"

**为什么**：`+0.1673` 只在当前 embedding 模型与当前数据上成立。
换模型或改数据都会变，而那时"不是泄漏"这个结论需要重新验证。

### Requirement: 候选特征必须在"非 gold 项"上验证排序信息

当评估某个量能否作为排序特征时，
MUST 在**排除 gold 之后**的候选集上验证它是否仍能产生有意义的排序，
MUST NOT 只用"gold vs 干扰项"的比较。

#### Scenario: "gold 检测器"能通过所有 gold-vs-干扰项的判据

- **WHEN** 某特征是"gold 检测器"（只能区分 gold 与其余，其余之间持平）
- **THEN** 均值差 / 唯一最高 / 分布重叠三条判据**全部通过**

**所以需要第四条判据**，它只看干扰项之间。

#### Scenario: 秩相关是决定性判据

- **WHEN** 检验 cosine 在干扰项之间是否有排序信息
- **THEN** MUST 计算"干扰项的 query-cosine"与"该干扰项与 gold 的 cosine"的秩相关

**若相关为正**：cosine 在非 gold 项上也有意义 → 真排序信号
**若相关接近 0**：cosine 只在 gold 上跳高 → gold 检测器

**实测**：

| subject | rho 均值 | rho 中位数 | 正相关 case | top-1 一致率 |
|---|---|---|---|---|
| `sample` | **+0.750** | +0.750 | **8/10** | **7/10** |
| `billing` | **+0.500** | **+1.000** | **9/12** | **9/12** |

**结论：未发现 gold 检测器特征。**

#### Scenario: 极差对比不足以判定

- **WHEN** 只比较 `gap`（gold − 最强干扰）与 `spread`（干扰项内部极差）
- **THEN** MUST 说明它只能提供"可疑"，不能提供"结论"

**实测**：

| subject | gap 均值 | spread 均值 | gap/spread 中位数 |
|---|---|---|---|
| `sample` | +0.1453 | 0.0657 | 2.24 |
| `billing` | +0.0943 | 0.0427 | 4.11 |

**若只看这个，会得出"像 gold 检测器"的结论**——而秩相关推翻了它。

**为什么极差不可靠**：它被单个离群值放大，
即使干扰项之间大部分持平，一个离群值就能让 spread 看起来不小。

### Requirement: "未发现反例"不得写成"已证明"

当样本量不足以支撑某个结论时，
MUST 写成"未发现 X"，MUST NOT 写成"证明不是 X"。

#### Scenario: n 小时 rho 只能取少数离散值

- **WHEN** 每个 case 只有 2 个干扰项
- **THEN** rho 只能取 `+1` 或 `-1`（二元），统计力很弱

**实测**：`billing` 的 12 个 case 全是 `n_dist = 2`，
rho 只有 9 个 `+1`、3 个 `-1`。

**`sample` 的 4 个 case 有 3 个干扰项**，rho 可取 `±1` 或 `±0.5`，稍好但仍小。

**所以必须写**：

| 说法 | 可否 |
|---|---|
| "未发现 gold 检测器特征" | ✅ |
| "证明 cosine 是真排序信号" | ❌ |

**两者的区别**：前者是"当前证据不支持那个假设"，
后者是"已排除那个假设"——而 n=2 做不到后者。

#### Scenario: 报告必须登记样本量局限

- **WHEN** 报告给出这个检验的结果
- **THEN** MUST 同时写出 `n_dist` 与"统计力弱"

**为什么**：读者会拿这个结论去支撑"添加 cosine"这个决定。
若不写局限，他会以为那是强证据。

### Requirement: 排序特征的噪声边界必须被实测

当某个量作为排序特征参与名次计算时，
MUST 实测它的输入噪声对名次的影响，MUST NOT 只引用"非确定性存在"这类定性描述。

#### Scenario: 噪声只在缓存未命中时出现

- **WHEN** 同一文本两次调用 embedding
- **THEN** MUST 分别记录"缓存命中"与"缓存未命中"两种情形

**实测**：

| 情形 | 结果 |
|---|---|
| 缓存命中 | `max|diff| = 0.00e+00`，`cos = 1.0000000000` |
| 缓存未命中 | `cos = 0.9971`（约 4.36°） |

**这个区分决定了"重跑能否复现"**：
`run_retrieval` 走缓存，所以重跑同一份数据是逐位相同的。
噪声只在首次生成缓存时进入，之后被冻结。

#### Scenario: 向量噪声必须换算到"分"的尺度

- **WHEN** 两个同文本向量 `cos = 0.9971`
- **THEN** MUST 实测它对 `cos(query, candidate)` 的影响
- **AND** MUST NOT 直接把 `0.9971` 当作"分的噪声"

**实测**（旋转候选向量 4.36°，30 个样本）：

| 量 | 值 |
|---|---|
| `|Δcos|` 均值 | **0.0019** |
| `|Δcos|` P95 | **0.0051** |
| `|Δcos|` 最大 | **0.0061** |

**夹角越大，敏感度越高**（`sin(角度差) × θ`）：

| 夹角 | 均值 | 最大 |
|---|---|---|
| 40–70° | 0.0020 | **0.0061** |
| ≥ 70° | 0.0016 | 0.0021 |

### Requirement: 不稳定阈值必须大于实测的最大噪声

当定义"名次可能不稳定"的阈值时，
MUST 让阈值大于实测的最大噪声，MUST NOT 让阈值落在噪声区间内。

#### Scenario: 阈值卡在噪声边界上等于判据本身抖动

- **WHEN** 实测最大噪声是 `0.0061`
- **AND** 阈值取 `0.006`
- **THEN** 该阈值**小于**最大噪声——判据会在自己的边界上抖动

| 阈值 | 与噪声最大值的关系 | 判定 |
|---|---|---|
| 0.006 | 小于 0.0061 | ❌ |
| **0.01** | **1.6 倍** | ✅ |

**所以本变更采用 0.01。**

### Requirement: 敏感度必须归因到 tie 紧密度，不是池大小

当解释"某 subject 对噪声更敏感"时，
MUST 用 `cosine_gap`（gold − 最强干扰），MUST NOT 用池大小。

#### Scenario: 池更小的 subject 反而更稳定

- **WHEN** 比较两个 subject 的噪声敏感度
- **THEN** MUST 给出各自的 `cosine_gap` 最小值

**实测**：

| subject | 池大小 | 正 gap 最小值 | 与噪声 0.0061 之比 |
|---|---|---|---|
| `billing` | **9**（更小） | **0.0447** | **7.3×** |
| `sample` | **12–14**（更大） | **0.0136** | **2.2×** |

**池更小的 `billing` 反而更稳定**——所以"池小所以名次间隔小"这个推理不成立。

**真正决定敏感度的是**：gold 与最强干扰项的 cosine 差有多小。

### Requirement: 排错的 case 必须与"不稳定的 case"分开计数

当统计 `cosine_gap` 时，
MUST 把"负 gap（cosine 已经排错）"与"正 gap 但太小（可能不稳定）"分开。

#### Scenario: 负 gap 不是噪声问题，是能力问题

- **WHEN** `cosine_gap < 0`
- **THEN** MUST 归为"排错"，MUST NOT 归为"不稳定"

**实测**：

| subject | 正 gap 最小值 | `gap < 0.01` | 负 gap（排错） |
|---|---|---|---|
| `sample` | 0.0136 | **0** | **1**（`ledger-q2` −0.0542） |
| `billing` | 0.0447 | **0** | **2**（`c3` −0.0429、`a2` −0.0402） |

**两者处置相反**：
- 不稳定 -> 记录并排除出结论
- 排错 -> 那是 cosine 本身的能力边界，不能排除

**若把负 gap 也计入"不稳定"，会得出"13% 的 case 不稳定"这种误导性数字。**

### Requirement: 未来实施的字段必须现在就登记

当某项测量会支撑一个即将实施的变更时，
MUST 现在就把所需的观测字段登记下来，MUST NOT 留作"将来的改进"。

#### Scenario: `cosine_gap` 是解释名次稳定性的唯一依据

- **WHEN** cosine 参与排序
- **THEN** 产物 MUST 记录每条 case 的 `cosine_gap`
- **AND** MUST 记录 `cosine_unstable`（`gap < 0.01`）

**已有先例**：

| 字段 | 含义 | 是否已有 |
|---|---|---|
| `tie_at_top1` | 重排后 top-1 是否并列 | ✅ |
| `tie_resolved_by` | 用什么破并列 | ✅ |
| **`cosine_gap`** | **gold 与最强干扰的 cosine 差** | ❌ |
| **`cosine_unstable`** | **`gap < 0.01`** | ❌ |

**`cosine_gap` 与 `tie_at_top1` 是同一个概念**：
都记录"这个名次有多稳"。只是一个用分差、一个用并列。

#### Scenario: 必须有一条"稳定 case 子集"的验收

- **WHEN** cosine 参与排序后跑验收
- **THEN** MUST 比较"稳定 case 的 `SEH@1`"与"全部 case 的 `SEH@1`"

**若不相等**，说明不稳定 case 影响了结论——
那时的 `SEH@1` 不是一个可复现的数字。

**本变更不实施这条验收**（因为 cosine 尚未参与排序），
但必须把它写进报告，作为装置变更的验收项。

### Requirement: 稳定性验收必须用扰动，不得用"子集分数相等"

当验证"某特征的名次在输入噪声下是否稳定"时，
MUST 构造噪声范围内的扰动并检查名次是否翻转，
MUST NOT 用"排除不稳定 case 后分数是否等于全集"。

#### Scenario: "子集分数相等"有两种失效方式

- **WHEN** 排除"不稳定"的 case 后比较 `SEH@1`
- **THEN** 若"不稳定"包含**负 gap**（已排错），子集只剩命中项 -> `SEH@1 = 1.0` -> **永远红**
- **AND** 若"不稳定"只含噪声带且**噪声带为空** -> 子集等于全集 -> **恒真**

**实测**：

| 读法 | sample | billing | 失效方式 |
|---|---|---|---|
| 含负 gap | 9/9 = **1.0000** vs 0.9000 | 10/10 = **1.0000** vs 0.8333 | **永远红** |
| 只算噪声带 | 集合 == 全集 | 集合 == 全集 | **恒真** |

**读法 1 的逻辑错误**：排除已经排错的 case，等于"先把错的删掉再报准确率"。

#### Scenario: 扰动检验才是"稳定性"该问的问题

- **WHEN** 验证稳定 case 的名次稳定性
- **THEN** MUST 对每条 case 的分数加 `±噪声上界` 的扰动并重算 top-1

**实测**（`±0.0061`，300 次）：

| subject | 稳定 case | 扰动次数 | 翻转 | 噪声 / 最小 gap |
|---|---|---|---|---|
| `sample` | 9 | 2700 | **0** | **0.45** |
| `billing` | 10 | 3000 | **0** | **0.14** |

**5700 次扰动，0 次翻转。**

**扰动的是"分"不是"向量"**：这是保守近似——
真实扰动对每条候选的影响取决于夹角（`sin(角度差) × θ`），
而按分统一扰动覆盖了最坏情况。

### Requirement: 量化"坏"的字段必须是三态，不是布尔

当某个量有两种不同性质的"坏"时，
MUST 用三态（或更多）表达，MUST NOT 用布尔值把它们压成一个。

#### Scenario: 负 gap 与噪声带是两种不同的"坏"

- **WHEN** 记录 cosine 的稳定性
- **THEN** MUST 用 `cosine_band` 三态，MUST NOT 用 `cosine_unstable` 布尔

| 区间 | `cosine_band` | 含义 | 处置 |
|---|---|---|---|
| `gap >= 0.01` | `stable` | 噪声下不翻转 | 可用于结论 |
| `0 <= gap < 0.01` | `noise` | 可能翻转 | 记录并排除 |
| `gap < 0` | **`negative`** | **cosine 已排错** | **不能排除，那是能力边界** |

**实测负 gap**：

| subject | 条数 | case | gap |
|---|---|---|---|
| `sample` | **1** | `ledger-q2` | −0.0542 |
| `billing` | **2** | `billing-a2` | −0.0402 |
| `billing` | | `billing-c3` | −0.0429 |

**若用布尔值**，会得出"`billing` 有 3/12 = 25% 不稳定"（若含负 gap 与噪声带），
或"17% 不稳定"（只含负 gap 但叫它不稳定）——**两种都是错的**。

### Requirement: 权重命名必须与语义一致

当给一组预注册权重命名时，
MUST 让名字反映权重的实际形态，MUST NOT 用暗示"平均"的名字命名"只开一项"的权重。

#### Scenario: `(0,0,1)` 不得命名为 `uniform`

- **WHEN** 某组权重是 `(0, 0, 1)`
- **THEN** MUST NOT 命名为 `uniform`
- **AND** MUST 命名为 `cosine_only` 或 `single_signal` 这类语义准确的名字

**为什么**：`uniform` 暗示"各项权重相等"，而 `(0,0,1)` 是"只有一项"。

**还有一个冲突**：`disabled_weights()` 的语义是"只开 base = `(1,0,0)`"。
若 `(0,0,1)` 成为 `uniform`，"全关"与"只开 cosine"会混淆。

| 权重 | 建议名 | 理由 |
|---|---|---|
| `(0,0,1)` | **`cosine_only`** / `single_signal` | 只有一项有信号 |
| `(0.2,0.2,0.6)` | **`mixed`** | 不等权但有退路 |

### Requirement: 所有召回路径 MUST 只返回 ACTIVE

本项目的三条召回路径 MUST 只返回 `Status.ACTIVE` 的条目。
该契约 MUST 有断言守着，且断言 MUST 覆盖"路径级"而非"数据级"。

#### Scenario: 三条路径的过滤位置不同，但语义必须一致

- **WHEN** 检查召回路径的 ACTIVE 过滤
- **THEN** MUST 逐条验证每一路

| 路径 | 过滤位置 |
|---|---|
| `lexical` | 包装 `search_text`，它只返回 ACTIVE |
| `vector` | SQL `WHERE i.status = 'ACTIVE'` |
| `adjacency` | SQL `AND status = 'ACTIVE'` + Python 二次过滤 |

#### Scenario: "数据里只有 ACTIVE"不等于"路径会过滤"

- **WHEN** 断言"召回路径只返回 ACTIVE"
- **THEN** MUST 构造一个**含非 ACTIVE 的 store** 并调用路径
- **AND** MUST NOT 只用"现有数据集的 status 集合 == {ACTIVE}"

**实测反例**：`test_v3_capability_boundary.py:140` 断言记忆库的 status 全是 ACTIVE。
但那只证明**这份数据**没有非 ACTIVE 条目——
若某条路径去掉了过滤，它仍然通过（因为没有非 ACTIVE 可返回）。

**所以必须构造非 ACTIVE**。

#### Scenario: 非 ACTIVE 条目必须有向量，否则测试不成立

- **WHEN** 验证 `vector` 路径的 ACTIVE 过滤
- **THEN** MUST 给非 ACTIVE 条目也写入向量
- **AND** MUST NOT 只给 ACTIVE 写

**为什么**：若非 ACTIVE 没有向量，"它们没被召回"可能只是因为没向量，
而不是因为 status 过滤——测试会假绿。

### Requirement: 行为断言与源码断言的分工必须写明

当同一契约同时由行为断言与源码断言覆盖时，
MUST 写明各自覆盖哪一层，MUST NOT 让读者以为一条覆盖全部。

#### Scenario: 行为断言守不住 Python 二次过滤

- **WHEN** 删掉 `adjacency.py` 的 Python 二次过滤
  (`if item.status is Status.ACTIVE`)
- **THEN** 行为断言**仍然通过**（SQL 已经过滤了）
- **AND** 只有源码断言会红

**实测**：

| 删掉什么 | 行为断言 | 源码断言 |
|---|---|---|
| `vector.py` 的 SQL 过滤 | **红** | **红** |
| `adjacency.py` 的 Python 过滤 | **绿** | **红** |

**这个"绿"本身是结论，不是缺陷**：
行为断言只覆盖 SQL 层，Python 层由源码断言守。

**若不写清分工**，人会以为"一条行为断言守住了两层"——
而一层被删掉时不会有任何提示。

### Requirement: 恒常数字段不得作为排序特征

当某个特征在候选池内恒为常数时，
MUST NOT 让它参与加权，MUST NOT 把它作为"观测事实"保留在 `features` 里。

#### Scenario: 恒 1.0 的字段没有可审计的内容

- **WHEN** 某特征在池内恒为 1.0
- **THEN** MUST 删除它，MUST NOT 只把权重归零

**与 `condition` 的区别**：

| 字段 | 池内取值 | 有信息吗 | 处置 |
|---|---|---|---|
| `condition` | 0.0 / 0.5 / 1.0（有方差） | ✅ | **保留为审计字段** |
| `status` | 恒 1.0（无方差） | ❌ | **删除** |

**`condition` 有方差，所以"审计"有内容可审计。**
`status` 无方差，保留它只是留一个恒等常量。

#### Scenario: 删除必须有先例与前提

- **WHEN** 删除一个特征
- **THEN** MUST 指出同类先例与删除前提

**先例**（`rerank.py` 的 docstring 已记录）：

| 特征 | 删除理由 |
|---|---|
| `temporal_validity` | 所有召回路径只返回 ACTIVE，恒为 1.0 |
| `recency` | 场景文件没有时间字段，全部同一 `BASE_TIME` |
| **`status`** | **同 `temporal_validity`** |

**前提**：所有召回路径只返回 ACTIVE（由本变更的断言守）。

**若前提破裂**（某条路径返回非 ACTIVE），`status` 会有方差，
那时它应该重新成为特征。
