# A 轴到底测了什么：条件直通、固定加成与两轴不可比

> 数据来源：`results/v2-sample-condition-ablation.json`（ledger）、
> `results/v2-billing-condition-ablation.json`（billing）。
> 每个数字都能从这两份 JSON 复算。

## 0. 一句话

**A 轴的 `0.9000` / `1.0000` 不是"条件区分能力"，是"base 排序 + 一个恒定的加成"。**
只报加成后的数字，会让人以为条件区分做得很好。

## 1. 缺陷：`query_condition` 是答案的副本

`evals/datasets/v2_adapter.py` 把 `query.query_condition` 直接映射成
`row["condition"]`，而造数据时该字段被填成 `gold.condition` 的逐字副本。

| 数据集 | A 轴查询 | `query_condition == gold.condition` |
|---|---|---|
| `sample` | 10 | **10/10** |
| `billing` | 9 | **9/9** |

于是 `condition_match` 对 gold 恒为 1.00、对兄弟恒为 0.00：

| 数据集 | gold 取值 | 兄弟取值 |
|---|---|---|
| `sample` | `{1.0}` | `{0.0}`（24 条兄弟） |
| `billing` | `{1.0}` | `{0.0}`（18 条兄弟） |

**这与 C4 缺陷 1（`query = row["text"]`）同型**，只是从文本字段换到了条件字段：
两者都是"把答案的一半写进了查询"。

### 1.1 implicit 的"隐含"只存在于文本

```
ledger-q3   字段='夜间'      文本含条件词=False   "半夜两点告警响了，该把谁叫起来看？"
ledger-q7   字段='赶进度'    文本含条件词=False   "这周要赶着交，先扔哪测一下？"
billing-a5  字段='华东'      文本含条件词=False   "杭州和南京的分部，报税归口在哪？"
billing-a9  字段='预付'      文本含条件词=False   "先付钱的那种，账期怎么算？"
```

协议 §3.3 说 implicit 是"A 轴难度的真正来源"。**对系统而言它从未生效**——
系统读的是结构化字段，不是自然语言文本。

## 2. `condition_match` 在 v2 上退化为字符串相等

把全部 19 个不同的 `condition` 值两两求匹配：

```
相同字符串：19/19 得 1.00
不同字符串：171/171 得 0.00
没有任何例外
```

用户举的四个例子：

| 对 | 分数 | 槽位 |
|---|---|---|
| 周末 vs 工作日白天 | 0.00 | `raw:周末` vs `time:day` |
| 夜间 vs 周末 | 0.00 | `raw:夜间` vs `raw:周末` |
| 华东 vs 华北 | 0.00 | `raw:华东` vs `raw:华北` |
| 大客户 vs 标准合约 | 0.00 | `raw:大客户` vs `raw:标准合约` |

19 个值里 11 个是 RAW（未登记）、8 个是 STRUCTURED。

### 为什么扩词表救不了

不是因为"认不出同义词"，而是因为**每个分支本来就是一个不同的条件值**。
即使把"华东""华北"都结构化，它们也必须是**不同的槽位**（`region:east` vs `region:north`），
而不同槽位就是 Jaccard 0。

**这是数据设计的直接后果：一个 relation 有 N 个分支，就有 N 个互不重叠的条件值。**

所以只要 `query_condition` 是副本，`condition_match` 必然 1.00 / 0.00。
这与词表大小无关。

### 为什么"传文本"比"传 None"更糟

| adapter 传什么 | `condition_match` | 含义 |
|---|---|---|
| `query_condition`（现状） | **1.00** | 条件被告知 |
| `None`（当前消融） | **0.50** | 条件未提及（中性） |
| 查询文本 | **0.00** | **条件明确不符** |

`parse_condition` 对未登记文本返回 `{raw:<全文>}`，不是空集。
所以传文本会得到 0.00——**主动压低 gold 的分数**，比中性更糟。

从文本抽取的实测结果：

| 数据集 | explicit | implicit |
|---|---|---|
| `sample` | 4/6 完全命中 | **0/4** |
| `billing` | **0/3** | **0/6** |

`billing` 的 explicit 也全部抽不出，因为它的条件值是领域实体
（`华北`、`大客户`、`预付`），而 `_ALIASES` 只有通用情境词
（`time:` / `env:` / `activity:`）。

## 3. 消融移除的是"固定 0.25 相对优势"

权重 `w.condition = 0.25`。

| | gold | 兄弟 | gold 相对兄弟 |
|---|---|---|---|
| 有 condition | 1.00 → 贡献 **0.2500** | 0.00 → 0.0000 | **+0.2500** |
| 消融后 | 0.50 → 贡献 **0.1250** | 0.50 → 0.1250 | **+0.0000** |

gold 绝对变化 **−0.125**，兄弟绝对变化 **+0.125**，相对差变化 **0.25**。

> 我上一轮说"差值恒为 0.125"是错的——只算了 gold 一侧，
> 漏掉了兄弟同时在上升。

### 翻转条件

```
有 condition：总分差 = 0.25×Δbase + 0.25
消融后：      总分差 = 0.25×Δbase
```

归一化 base 差 ∈ [−1, 1]。所以：

- **有 condition**：只要 `Δbase > −1.0`，gold 就赢（几乎总是）
- **消融后**：必须 `Δbase > 0` 才赢

**消融移除的是"base 差在 (−1.0, 0) 之间时 condition 的挽救"。**

## 4. 计数分解，不是分数分解

| subject | A 轴 | `base` 独立命中 | `condition` 决定命中 | 未中 |
|---|---|---|---|---|
| `ledger` | 10 | **3**（q6/q9/q10） | **6** | 1（q4） |
| `billing` | 9 | **2**（a1/a4） | **7** | 0 |

加得起来：3+6+1=10、2+7+0=9。

### 两种说法的区别

| 说法 | 读者会想 |
|---|---|
| "condition 贡献了 60% 的分数" | 提高 condition 特征质量就能提升 60% |
| **"6/10 条 case 的胜负由 condition 决定"** | 这 6 条里 base 排错了，condition 纠正了 |

**后者才对。** 而它揭示的分工是：

- `base` 在 A 轴上其实很弱（**30% 和 22%**）
- `condition` 把它拉到了 90% 和 100%

如果 condition 不可用，A 轴的能力会掉到 30% / 22%。那才是"检索能力"的真实水平。

## 5. 两轴的有效特征数不同，分数不可比

| 轴 | `condition_match` | 有效特征数 |
|---|---|---|
| A | gold 1.00 / 兄弟 0.00 | **4** |
| C | **恒 0.50**（`query_condition` 为空） | **3** |

### C 轴消融前后逐条相同

| subject | C 轴 | `SEH@1` with → without | `SEH@5` with → without | 逐条 rank |
|---|---|---|---|---|
| `ledger` | n=2 | 1.0000 → 1.0000 | 1.0000 → 1.0000 | q11=1, q12=1 |
| `billing` | n=3 | **0.0000 → 0.0000** | 1.0000 → 1.0000 | c1=2, c2=2, **c3=3** |

**C 轴不依赖 `condition`**——因为它的 `condition_match` 恒为 0.5，
消融改不动它。这是一条独立结论。

### billing 的 C 轴两个指标给出相反结论

```
SEH@1 = 0/3 = 0.0000   一条都没排第 1
SEH@5 = 3/3 = 1.0000   全部排进前 5
```

**两个都对，说的是不同的事：**

- 系统能找到正确答案（9 条里排进前 5）
- 但排不到第 1（base 分差不够，而 C 轴没有 condition 加成）

这是"**能召回但排不准**"的分离形态。

**A 轴上不会出现这个形态**（condition 能把 gold 推到第 1），
所以 **C 轴是唯一能观测"排序精度不足"的轴**。

### 样本量必须先说清

`billing` 的 C 轴只有 **3 条**：

```
SEH@5 = 3/3 = 1.0000
随机基线 = min(5,9)/9 = 0.5556
```

**n=3 的"高于随机"没有统计意义。** 它只说明"3 条都排进前 5、没有一条排第 1"，
不支撑任何统计结论。

## 6. 结论

| 数字 | 含义 | 不能读成 |
|---|---|---|
| A 轴 `0.9000` / `1.0000` | base 排序 + 条件直通的固定加成 | 条件区分能力 |
| A 轴消融 `0.3000` / `0.2222` | 纯 base 排序（三特征） | 系统的最差情况 |
| C 轴 `SEH@1 = 0` / `SEH@5 = 1` | 能召回、排不准 | 任何单一结论 |
| condition 掉幅 `+0.60` / `+0.78` | 计数分解：6/10、7/9 条翻转 | 分数的 60% |

## 7. 并列的裁决：`SEH@1` 无法表达"同分"

### 7.1 一个不可归因的例子

`billing-c2` 的两条候选四特征**逐位相同**（0.875000 vs 0.875000）。
最终 `d-billing-c2-3` 排第 1，`gold` 第 2。

而这一例**无法归因**：

| 判据 | 结果 |
|---|---|
| tag 字典序 | `d-billing-c2-3` 在前（`d` < `g`） |
| 融合顺序 | `d-billing-c2-3` 位置 0、gold 位置 1 → 也是它在前 |

**两种判据给同一答案，所以观察结果无法区分谁在生效。**

要证明融合顺序真的生效，必须构造两者**相反**的用例
（见 `tests/retrieval/test_rerank_tiebreak.py`）。

### 7.2 "四特征决定 21/22，第 22 条由同分 + 次级判据"

精确表述：

> **21/22** 的名次由四特征加权总分单独决定。
> **第 22 条**（`billing-c2`）的两条候选四特征完全同分；
> 次级判据从中选出第 1，因此该条的 `SEH@1 = 0`
> 是"同分 + 融合顺序"共同的结果，**不是四特征单独的结果**。

为什么这个区分重要：若改成"同分算 0.5 命中"，这条的贡献是 0.5 而不是 0。

### 7.3 `SEH@1` 是二值指标，无法表达"同分"

> `SEH@1` 只有 `{0, 1}`，而实际输出有"并列"这个第三态。
> 当候选完全同分时，它的取值取决于次级判据。
> 本项目观测到 1 例（`billing-c2`），已记录在 `tie_at_top1`。

这是**指标的边界**，不是可修补的缺陷。三条修补路都不可行：

| 修法 | 为什么不可行 |
|---|---|
| 改融合顺序 | 那是 RRF 分的输出，不能为一条 case 特调 |
| "同分时 gold 优先" | 那是身份偏向 |
| "同分算 0.5 命中" | 改变 `SEH@1` 的定义 |

### 7.4 `SEH` 在三种情况下失真

| # | 情形 | 表现 | 性质 |
|---|---|---|---|
| 1 | 池太小（C4） | `SEH@5` 饱和为 1.0 | **分母问题** |
| 2 | 竞争集 < K（v2 A 轴） | `SEH@5` 无定义 | **分母问题** |
| 3 | 同分（`billing-c2`） | `SEH@1` 被迫二选一 | **值域问题** |

前两个是"分母不对"，第三个是"值域不够"——指标只有两个取值，而有三种状态。

### 不做的事

- **不把 `query_condition` 改成 None 就叫修复**：那等于移除一个特征，
  而 v2 的 `without` 列已经是那个结果
- **不扩 `_ALIASES`**：v2 的条件是领域实体，"杭州 → 华东"需要地理知识，
  不是词表能覆盖的
- **不改 billing 数据**：已看到分数，改了就污染（协议 §1.2）

### 要测"条件推断"，需要 v3

1. 条件类型改成**同义表达**（不是实体指代）
2. 实现一个能从文本抽条件的抽取器
3. 这是新数据集，不是 v2 的延续
