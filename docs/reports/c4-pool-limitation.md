# 检索评测的候选池设计：一个必须记录的限制

## 问题

第一次评测得到 SEH@5 = 1.000、SRS = 1.000，看起来检索完美。
诊断后发现这是**任务太简单**，不是检索能力强。

## 诊断过程

### 第一步：检查 query 与 gold 的词汇重叠

| 数据集 | query 含 gold 值 |
|---|---|
| dev | 52% |
| test | 41% |
| independent | 8% |

independent 只有 8%，所以不是查询泄露。

### 第二步：检查干扰项的性质

原方案从**其他场景的 gold** 采样干扰项。实测：

- independent 集有 29 个不同的 `relation`，其中 **28 个只出现 1 次**
- 干扰项的 `relation` 与 gold **必然不同**
- 于是 query 与所有干扰项的词汇几乎零重叠

**结果**：词面召回只要命中 query 里的任何词，就能唯一锁定 gold。
这不是检索，是"在噪声里找信号"。

### 第三步：构造三种难度的池

| 模式 | 干扰项来源 | 物理含义 |
|---|---|---|
| `unrelated` | 任意主题 | 在无关记忆里找相关的那条 |
| `same_relation` | 同 relation、不同 subject | 同一类事实的不同对象 |
| `adversarial` | 同 relation 且与 gold 字符重叠 | 字面很像但答案不同 |

## 实测结果

```
pool=unrelated      n=26/30  skipped=0   SEH@5=1.000  SRS=1.000
pool=same_relation  n=0/30   skipped=26  （无数据）
pool=adversarial    n=0/30   skipped=26  （无数据）
```

**中高难度模式一条都评估不了**——因为独立集里 28/29 个 relation 只出现一次，
`same_relation` 选不出任何干扰项，池退化为只有 gold 一条，
脚本正确地跳过了而不是给出假的 1.000。

## 这个限制意味着什么

**当前所有检索指标只能回答"能不能在无关记忆里找到相关的"，
不能回答"能不能在多条相似记忆里挑对"。**

后者才是真实场景的核心难度：同一个用户有多条关于包管理器的记忆
（pnpm / npm / yarn / 历史版本），查询"我们用哪个包管理器"时，
需要的是**在同一主题内区分**，而不是在一片噪声里找信号。

## 结论与后续

1. **报告必须按难度模式分层**，不能只报 `unrelated` 的 1.000
2. **中高难度需要另建数据集**：至少 20 个 subject，每个 subject 下有
   3–5 条同 relation 的记忆，构成"同主题多条候选"
3. 在那之前，**不宣称检索能力**，只说"跨主题召回可用"

这个限制本身也是有价值的产出：它说明"造一个能测出真实难度的检索数据集"
比"实现检索算法"更难，也更容易被忽略。
