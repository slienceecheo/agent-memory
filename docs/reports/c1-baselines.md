# C1 基线报告：FactConsolidation-6K-SH

> 生成日期：2026-10-24
> 数据：`ai-hyz/MemoryAgentBench` → `Conflict_Resolution` → `factconsolidation_sh_6k`
> 规模：455 条事实（含 156 对冲突），100 个问题
> 模型：DeepSeek V4.1 Flash（本地网关，强制 SSE）
> 复现：`uv run python -m evals.run --baseline <name>`

## 主表

| 基线 | 准确率（官方口径） | 单一答案率 | 单答案时准确率 | reasoning 浪费 |
|---|---|---|---|---|
| `no-memory` | 18.0% | 100% | 18.0% | 93.8% |
| `naive-rag` (top-5) | **87.0%** | 35% | **62.9%** (22/35) | 89.9% |
| `full-context` | 26.0% | 98% | 26.0% | 96.9% |

n = 100，0 个错误样本。

## 最重要的发现：87% 是指标高估，不是真实能力

`substring_exact_match` 的规则是"标准答案是预测的子串即命中"。
而模型在遇到冲突事实时会**把两个候选都报出来**：

```
Q: Which sport is goaltender associated with?
gold: pesäpallo
pred: "ice hockey and pesäpallo"      → 官方口径记为正确
```

拆解 naive-rag 的 87 分：

| 构成 | 题数 | 占比 |
|---|---|---|
| 答对且**只给一个**答案 | 22 | 22% |
| 答对但**同时给出两个冲突值** | 65 | **65%** |
| 答错 | 13 | 13% |

**65 个百分点来自"把候选全说一遍"。** 这类回答在真实场景里是不可用的——
用户问"我们用什么包管理器"，系统答"pnpm 和 npm"没有任何价值。

只看它给出单一答案的 35 题：准确率 62.9%（22/35）。这才是它真实的冲突消解能力。

## 三条基线说明了什么

1. **no-memory = 18%** 与论文里 Mem0 的 18.0% 数量级一致，说明"不给事实时靠
   常识猜"大约就是两成。这个数字可信。
2. **full-context = 26%** 说明 455 条事实里 156 对冲突会把人（和模型）淹没。
   塞得越多不等于越好——这是"需要检索 + 裁决"而非"需要更大上下文"的直接证据。
3. **naive-rag 的高分是假的**。它召回了正确事实，但同时召回冲突的另一半，
   然后用"两个都报"绕过裁决。

## 这对后续变更的直接约束

C3（冲突消解）如果要证明自己有价值，**不能拿 87% 当基线**。必须先补一个
把"多答案"判错的指标，否则会出现"我们做对了反而分数更低"的荒谬结论。

已改写的约束：见 `docs/reports/c1-findings.md` 的四条待办。

## 成本

| 指标 | 值 |
|---|---|
| 推理 token 占生成 token 比例 | 89.9% ~ 96.9% |
| 结论 | 推理内容占了绝大部分生成开销，且我们完全丢弃它 |

这个比例高得离谱。若换成按输出 token 计费的真实场景，成本几乎是纯浪费。
**这条本身值得作为工程结论写出来**：抽取类任务不该用带长推理的模型，
或者应该显式关掉推理。

## 已知偏差与限制

1. **只有 6K + SH 一格**。32K / 64K / 262K 与 MH 未跑（C5 负责）。
2. **单次运行，无重复**。LLM 是随机的，这里的数字是单点估计，
   没有给出置信区间——因为 n=100 且只有一次采样，CI 会低估真实方差。
   正式报告会在 C5 做多次采样并给区间。
3. **`substring_exact_match` 对数字有已知误判**（`42` 是 `421` 的子串）。
   本数据集的答案以实体名为主，影响有限，但已记录。
4. **代理与缓存**：embedding 未参与本变更（基线是词面检索），
   所有 LLM 响应未缓存，因此本表不能被当作"逐位可复现"。
   `--check-cache` 的完整验证在 C4 引入向量检索后再做。
