# C4 报告：三路召回与 fitness-for-use 重排

> 生成日期：2026-10-26
> 数据集：dev 40 / test 20 / independent 30（第三方独立编写）
> 模型：DeepSeek V4.1 Flash（本地网关，SSE 强制分块，响应缓存）

## 0. 结论：检索指标全部满分，但这个满分不能证明检索能力

| split | 可评估 | 跳过 | SEH@5 | SRS |
|---|---|---|---|---|
| dev | 33/40 | 0 | 1.000 | 0.955 |
| test | 17/20 | 0 | 1.000 | 0.971 |
| independent | 26/30 | 0 | **1.000** | **1.000** |

**这组数字说明的是"能在无关记忆里找到相关的那条"，不是"能在相似记忆里挑对"。**

原因见第 1 节与**第 0.1 节**。**本变更不宣称检索能力提升**，只宣称读路径已建成、
指标已可测量、且限制已被量化。

### 0.1 事后发现的缺陷：查询就是答案本身

> 本节在报告交付**之后**补写。缺陷的性质是**测量装置坏了**，不是"发现了一个新限制"。
> 全部数字可复算：`results/c4-query-leak-ablation.json`，
> 生成命令 `uv run python -m evals.tools.diagnose_c4_leak`。

#### 缺陷是什么

`annotate_retrieval.py` 里写的是 `query = row["text"]`；
`run_retrieval._item` 又把同一句 `row["text"]` 当作 gold 条目的索引原文。
于是 **gold 那篇文档就是查询本身**——词面召回在做逐字比对。

同时干扰项的 `text` 是 `None`，`items_fts` 里只剩 `subject/relation/value`，
与一句自然提问几乎零重叠。它们**物理上无法竞争**。

#### 拆掉后剩多少

| 变体 | gold 原文 | 干扰项原文 | dev SEH@5 | test SEH@5 | independent SEH@5 |
|---|---|---|---|---|---|
| V0 现状 | = query | 无 | 1.000 | 1.000 | 1.000 |
| **V1 抹掉 gold 原文** | 无 | 无 | **0.606** | **0.412** | **0.500** |
| V2 干扰项补原文 | = query | 有 | 1.000 | 1.000 | 1.000 |
| V3 两处都拆 | 无 | 有 | 0.606 | 0.412 | 0.500 |

（V2/V3 的 SRS 略有不同：dev 0.576、test 0.382、independent 0.452。
`SEH` 相同是因为排名差异落在 K 以内。）

**读数**：

- **V0 − V1 = 0.394 / 0.588 / 0.500**。抹掉 gold 原文这一处，独立集从 1.000 掉到 0.500，
  **正好掉回 C3 那个数字**。这不是巧合：两者的成因是同一个——字符串方法在
  "表述不同但指同一件事"上无能。
- **V2 与 V0 完全相同**，说明给干扰项补原文**没有改善**。原因在下面的第二个缺陷。
- V1/V3 抹掉 gold 原文后，gold 已经没有正确的原文可用（数据集从未记录"这条记忆
  由哪句话写入"）。所以 **V1/V3 是下界，不是公平基线**。

#### 更严重的一个：排名从未发生

指标算的是"gold 在**召回结果**里排第几"。C4 只检查了"建池后大小 > K"，
没检查"召回后还剩几条"：

| split | 召回集只有 1 条 | 有 2 条 | 有 3 条 |
|---|---|---|---|
| dev | 26/33 | 6 | 1 |
| test | 15/17 | 2 | 0 |
| **independent** | **26/26** | 0 | 0 |

**independent 上 26 条全部只有 1 个候选，排名从未发生，SEH 恒为 1——这不是满分，是空操作。**
`SRS = 1.000` 同理：`1/1 = 1.0`。

这解释了为什么 V2（干扰项补原文）没有改变任何分数：干扰项即便有原文，
词面召回依然一个都没召回上来，候选集还是只有 gold 一条。

#### 第四个缺陷：方差检查查错了对象

`test_rerank_variance.py` 断言"四个特征里至少三个有方差"，
但它检查的是**数据集字段**（`row["authority"]`、`row["condition"]`），
不是**真实候选池里的候选**。实测真实池：

| 特征 | 池内有方差的场景 |
|---|---|
| base（RRF） | 9/76 |
| condition | 4/76 |
| authority | **0/76** |
| status | **0/76** |

`authority` 与 `status` 在候选池里 100% 是常数。测试之所以通过，是因为
`gold.authority` 在 dev/test 全是 `user_direct`、在 independent 有 7 条
`third_party`——**这个方差存在于数据集里，从未进入候选池**。

所以"四个特征"实际上是**两个（且这两个只在 12% 和 5% 的场景上非平凡）**。
这也解释了第 3 节五组权重为何完全相同：三个特征恒为常数时，权重怎么分配都一样。

#### 第五个缺陷：干扰项是文件顺序的前缀

`select_pool_distractors` 用 `others[:limit]`，不是随机采样。实测：

- 76 条场景一共只有 **15 种**干扰项组合
- 其中**一种组合被用了 36 次**
- 前 5 条干扰项的 `relation` 序列在 71 条场景上完全相同

`build_pool` 用 `seed + gold.id` 打乱，所以 gold 的位置会变——
但**池的成员**几乎不变，"每条场景独立建池"这层设计被文件顺序架空了。

#### 第六个缺陷：docstring 与代码不一致

`pool_modes.select_distractors` 的注释写 `same_relation` 是"同 relation、
**不同 subject**"。但代码里只排除了与 gold **同逻辑键**的条目，没有 subject 条件。

实测：`SAME_RELATION` 选出的 142 条干扰项里，**62 条与 gold 同 subject**。

后果不是"分数变差"，而是**报告无法归因**：这个模式同时混进了 A 轴的真兄弟
（同 subject 不同 condition）和非 A 轴（同 relation 的别的对象）。
"中难度"这个标签因此没有确定的物理含义。

这个缺陷本身值得单独记一笔：**报告是按 docstring 写的，不是按代码写的。**
`docs/requirements/retrieval-dataset-v2.md` §14 因此要求所有"现有实现如何"
的判断必须代码实测。

#### 第七个缺陷：三路召回从未联合跑过

`run_retrieval.py` 只 import 了 `recall_by_lexical`（第 37 行）。
`recall_by_vector` 与 `recall_by_adjacency` **一次都没进过评测入口**。

于是第 5 节那张"已建成能力"表把三类东西混在了一起：单元测试、端到端评测、
以及**从未联合执行**。逐项对照实际证据：

| 能力 | 之前的表述 | 单元测试 | 端到端验证过 |
|---|---|---|---|
| 词面召回 | 已建成 | ✅ | ✅ 唯一真正跑过的一路 |
| 向量召回 | 已建成 | ✅ | ❌ 从未进评测（池里也没有向量） |
| 邻接召回 | 已建成 | ✅ | ❌ 从未进评测 |
| RRF 融合 | 已建成 | ✅ | ❌ 只融合过 1 个列表，退化情形 |
| 条件槽位 | 已建成 | ✅ | ⚠️ 仅词典层面，未在联合排序中生效 |
| 四特征重排 | 已建成 | ✅ | ❌ 重排对象在 26/26 条上只有 1 个候选 |
| 语义等价去重 | 已建成 | ✅ | ❌ 见缺陷 8 |

**"实现了三路召回"与"实现了三路召回、但联合评测只跑过一路"，
在可信度上差一个量级。** 报告不得暗示一个没跑过的能力已被验证。

#### 第八个缺陷：去重把重排结果替换成了 UUID 字典序

`run_retrieval.py:228` 构造的是：

```python
texts = [(item_id, item_id, 1.0) for item_id in order]
```

三个字段分别是 `(item_id, text, score)`。于是：

- **`text` 传的是 item_id**（一串 UUID hex），模型收到的是两个 UUID，
  不是两条记忆的内容 → 等价判断在这条路径上**完全没有意义**
- **`score` 全是常数 1.0** → `dedup` 内部 `sorted(ranked, key=lambda e: (-e[2], e[0]))`
  退化为**按 item_id 字典序排序**

后果实测：

| 输入顺序 | 判"无关"后的输出 |
|---|---|
| `zzz, mmm, aaa, bbb` | `aaa, bbb, mmm, zzz` |

**一个从不合并的判定（全部"无关"），本应原样返回，却把顺序整个反转了。**
判"等义"时更糟：4 条被合并成 1 条。

在真实数据上（dev）：dedup 开启后 **3/40 条排名发生变化，SRS 0.955 → 0.939**；
test 上 **1/20 条变化，0.971 → 0.941**。

所以 `results/retrieval-independent-uniform-poolunrelated.json`（dedup 开启）
与 `...-nodedup-...`（dedup 关闭）里，**开启去重那一份的排名不是重排给出的，
是 UUID 序给出的**。而报告第 4 节的"等义判断有消费者"恰恰用这条路径作证据。

> **这一条要特别说明**：`independent` 上两份结果恰好同为 `SEH=SRS=1.000`，
> 因为那里 26/26 条召回集只有 1 个候选，UUID 序无从改变任何东西。
> 也就是说，**缺陷 7 掩盖了缺陷 8**——排名没发生时，把排名打乱也看不出来。

#### 这一节的结论

**C4 的 1.000 是测量装置缺陷的产物，不是检索能力的证据。**

它比"干扰项来自无关主题"更根本：那个解释只说难度低，没说
**查询与答案逐字相同、排名根本没发生、且方差从未进入候选池**。
原先第 1 节的诊断是对的，但不完整。

**八个**缺陷：

| # | 缺陷 | 性质 |
| 1 | `query` = gold 存库原文 | 查询就是答案 |
| 2 | 干扰项无原文 | 物理上无法竞争 |
| 3 | 指标在召回子集上算排名 | 分母为 1 时仍给分 |
| 4 | 方差测试查数据集字段 | 测试通过但性质不成立 |
| 5 | 干扰项取文件顺序前缀 | 池成员几乎固定 |
| 6 | docstring 与代码不一致 | 报告按注释写，无法归因 |
| 7 | 三路召回从未联合跑过 | 三路中只有一路进过评测 |
| 8 | dedup 收到 item_id 与常数分 | 排名被 UUID 序替换 |

**缺陷 7 掩盖了缺陷 8**：排名没发生时，把排名打乱也看不出来。
这类"两层缺陷互相遮蔽"是本轮最难发现的部分——单看任何一层都是"测试通过"。

已在 `docs/requirements/retrieval-dataset-v2.md` 写成可测试的反泄漏条款
（L1–L5）与召回后门禁，作为 v2 数据集的冻结前提。


## 1. 为什么满分不代表能力强

> **先读第 0.1 节。** 那里写的缺陷（查询=答案、排名未发生、方差查错对象、
> 三路从未联合跑过）比本节的"干扰项来自无关主题"更根本。本节保留原样，
> 因为它的诊断本身是对的，只是不足以解释 1.000。
>
> 特别是"第一步：排除查询泄露"这个结论需要修正：它只查了 query 里有没有 gold 的**值**，
> 没查 query 是不是 gold 的**整句话**。后者是 100%（76/76）。

### 诊断过程

**第一步：排除查询泄露**
query 里含 gold 值的比例：dev 52%、test 41%、independent 8%。
independent 最低，所以不是泄露。

> **这一步的结论是错的，见第 0.1 节缺陷 1。** 它只查了"query 含不含 gold 的**值**"，
> 没查"query 是不是 gold 的**存库原文**"。后者在 76/76 条上成立（100%）。
> 8% 这个数字之所以看起来干净，是因为 query 复述的是**整句话**，不是值。

**第二步：检查干扰项性质**
原方案从其他场景的 gold 采样干扰项。实测 independent 集有
**29 个不同 relation，其中 28 个只出现 1 次**。
干扰项的 relation 与 gold 必然不同，于是 query 与所有干扰项的词汇几乎零重叠。

**结论**：词面召回只要命中 query 里任何词，就能唯一锁定 gold。
这不是检索，是"在噪声里找信号"。

## 2. 三种难度的池：两种无法评估

| 模式 | 干扰项来源 | 可评估 | 结果 |
|---|---|---|---|
| `unrelated` | 任意主题（实为文件顺序前 20 条） | 26/30 | SEH=1.000 |
| `same_relation` | 同 relation、**任意 subject** | **0/30** | 全部跳过 |
| `adversarial` | 同 relation 且与 gold 字符重叠 | **0/30** | 全部跳过 |

> `same_relation` 那一行原写"不同 subject"，与代码不符（缺陷 6）：
> 代码只排除与 gold 同逻辑键的条目，实测 62/142 条与 gold 同 subject。
> `unrelated` 那一行原写"任意主题"，实际是 `others[:limit]` 取文件顺序（缺陷 5）。

`same_relation` 与 `adversarial` 在独立集上**选不出任何干扰项**，
脚本正确跳过（`skipped=26`）而不是给出假的 1.000。
详细诊断见 `docs/reports/c4-pool-limitation.md`。

## 3. 五组预注册权重完全无法区分

| 权重组合 | independent SEH@5 |
|---|---|
| uniform | 1.000 |
| base_heavy | 1.000 |
| cond_heavy | 1.000 |
| auth_heavy | 1.000 |
| status_only | 1.000 |

**这个结果本身是有价值的**：在低难度任务上，权重选择不影响任何指标。
审查当初反对 1001 组网格搜索是对的——但那不是因为网格会过拟合，
而是因为**这个任务根本没有区分度可被过拟合**。

> **补充（第 0.1 节缺陷 4/3）**：五组完全相同还有一个更机械的原因。
> `independent` 上 26/26 条召回集只有 1 个候选，排序根本没有余地；
> 而在真正有多候选的 dev 上，池内 `authority` 与 `status` 也是 0/76 有方差。
> 也就是说，四组权重里有三组乘的是常数——**"权重无影响"在数学上是被保证的，
> 不是被测出来的**。这条不能当作"任务无区分度"的证据。

## 4. 语义等价判断：MERGE 达标，NOOP 未达标

> **先读第 0.1 节缺陷 8。** 本节那 10 对样本是用 `evals/run_equivalence.py`
> 直接喂文本测的，那一层是**真的**。但**评测流水线里的去重不是**——
> `run_retrieval.py:228` 传给 `dedup` 的"文本"是 item_id（UUID hex），
> 分数是常数 1.0。所以：
>
> - 本节结论（模型三分类能力）**成立**
> - 但"等价判断有消费者"**不成立**：消费者收到的是 UUID，判断无法影响任何真实排序
>
> 换句话说，模型能判对，但这个能力**没有接进被测量的路径**。

用 C3 独立集推导出 10 对真实样本（6 互补 + 4 等义）：

| 类别 | 正确 | 总数 | 阈值 | 状态 |
|---|---|---|---|---|
| complementary（MERGE） | **6** | 6 | ≥5 | ✅ |
| equivalent（NOOP） | **2** | 4 | ≥3 | ❌ |
| 总体 | 8 | 10 | — | 80% |

### 错的两条及其方向

| 用例 | 期望 | 实际 |
|---|---|---|
| `每周日凌晨` vs `每周日零点` | 等义 | 互补 |
| `下周六去怀柔团建` vs `下周六去怀柔玩` | 等义 | 互补 |

**方向一致：把"等义"判成"互补"。** 模型倾向于保守——它不愿断言
"两者完全相同"，更愿意说"后者补充了前者"。

这个方向**比反向安全**：判成互补只是不合并，判成等义会真的删掉一条。
但代价是去重基本失效（等义类召回率仅 50%）。

### 试过的改进（未采用）

用显式提示词（"问自己：后者的信息量是否严格多于前者"）重测：
`下周六去怀柔玩` 救回来了，`每周日凌晨` 仍是互补。
**只改善 1 条，且样本仅 4 条——继续调就是在 4 条上过拟合。已停止。**

### 一个被修掉的真实缺陷

初版解析器只认 `{"relation": "equivalent"}`。实测模型会返回
`{"关系":"包含"}`、`{"relation":"neutral"}`、`{"label":"..."}`、
`{"answer":"..."}` 等多种键名。

**只认单一格式会让一半以上响应被降级为"无关"，而那个降级看起来像模型判断错了。**
这是最难发现的一类失真。现已改为容错解析（全文找类别关键字，
且 `complementary` 优先于 `equivalent`——宁可少合并，不可错合并）。

## 5. 已建成的能力（与分数无关）

> **这张表按第 0.1 节的缺陷 7/8 重写。** 原表把"单元测试通过"写成了"已建成"，
> 使读者以为三路召回、RRF、四特征重排、语义去重都跑过联合评测。
> 实际只有词面一路进过评测入口（`run_retrieval.py` 只 import 了 `recall_by_lexical`）。

| 能力 | 单元测试 | 端到端验证过 | 证据 / 缺口 |
|---|---|---|---|
| 原文可检索 | ✅ | ✅ | `items_fts` 索引原文；变异验证：改回 `version DESC` 排序后测试失败 |
| BM25 排序 | ✅ | ✅ | 短文档高频词排前；同上变异验证 |
| 三路召回各自可关 | ✅ 14 条 | ❌ | `test_recall.py` 覆盖三路，但评测只跑词面一路 |
| 向量召回 | ✅ | ❌ | 池内条目从未写入向量，评测路径无从调用 |
| 邻接召回 | ✅ | ❌ | 从未进评测入口 |
| RRF 融合 | ✅ | ❌ | 只融合过**单列表**，是退化情形，非多路融合 |
| 四特征值域受控 | ✅ | ✅（值域） | 越界即报错 |
| 四特征有方差 | ❌ | ❌ | 见缺陷 4：测试量数据集字段；真实池内 `authority`/`status` 0/76 有方差 |
| 条件槽位中英双向 | ✅ | ⚠️ 词典层 | 30/30 结构化，但未在联合排序中起作用 |
| 等价判断有消费者 | ✅ | ❌ | 见缺陷 8：评测里 `dedup` 收到的是 item_id，判断无意义 |
| 归因三类互斥完备 | ✅ | ✅ | 且要求保留未截断融合排名，否则"排序过低"与"重排丢弃"无法区分 |
| 池不足 K 时跳过 | ✅ | ⚠️ 建池前 | 守住建池前的门；**召回后的门没守**，见缺陷 3 |

**读法**：`端到端验证过` 一栏为 ❌ 的能力，只能说"有单元测试"，
不能说"已验证"。这两句话在面试里的可信度差一个量级。

`independent` 上 26/26 条召回集只有 1 个候选，因此**任何**针对排序的能力
（RRF、重排、去重）在该集上都未被验证——它们的"测试通过"与"评测通过"
在这里没有区分力。

## 6. 数据限制的量化

> 本表测的是"**数据本身有多难**"。第 0.1 节测的是"**尺子有没有坏**"。
> 两者必须分开读：即使数据更难，尺子坏了也测不出来。

| 指标 | 数值 | 含义 |
|---|---|---|
| 有 gold 的场景 | 76/90 | 14 条 ADD 类无 gold，不计入召回 |
| 有条件场景 | 30/90 | 其余 60 条上 `condition_match` 恒为中性 0.5 |
| independent 的 relation 种类 | 29 种 / 30 条 | 28 种只出现 1 次 → 无法构造同主题干扰池 |
| 同 relation 干扰项均值 | **0.2 条** | 中高难度模式事实上不可评估 |
| query 复述 gold 值 | dev 52% / test 41% / ind 8% | dev/test 的词面召回被系统性高估 |
| **query 逐字等于 gold 存库原文** | **76/76 = 100%** | **第 0.1 节的缺陷 1，比上面那一行根本得多** |
| **召回后只剩 1 个候选** | dev 26/33、test 15/17、**ind 26/26** | **第 0.1 节的缺陷 3，排名未发生** |

最后两行是事后补测的。它们说明：**"query 复述 gold 值 8%"这个看似干净的 8%，
并不意味着没有问题**——因为 query 复述的是 gold 的**整句话**，不是值。

## 7. 要得出可信的检索结论，需要什么

> **已被 `docs/requirements/retrieval-dataset-v2.md` 取代并细化。**
> 那份协议把下面三条变成可测试的冻结门禁（L1–L5、F1–F6），
> 并额外加入 B 轴（历史版本）的明确排除说明。

1. **另建"同主题多条候选"数据集**：至少 20 个 subject，
   每个 subject 下有 3–5 条同 relation 的记忆，
   构成"同一个用户在多条相似记忆里挑对"的真实难度
2. **提高条件覆盖率**：当前 30/90，`condition_match` 在其余 2/3 上无区分度
3. **等义判断需要更多样本**才能判断 50% 是否稳定；
   当前只有 4 条，任何调整都可能是噪声

### 7.1 追加（第 0.1 节的后果）

上面三条是"数据不够难"。第 0.1 节发现的是"**尺子本身坏了**"，必须先修尺子：

4. **query 不得等于记忆原文**，且干扰项必须有原文——否则词面召回在做逐字比对
5. **门禁挪到召回之后**：`recall_size ≥ 2` 才计入排名，否则 SEH 恒为 1
6. **方差检查必须查真实候选池**，不是数据集字段
7. **干扰项不得按文件顺序取前缀**

## 8. 实验纪律：一次需要如实记录的偏差

设计里写的是"权重在 dev 上搜，test 上只跑一次"。实际运行次数（`results/retrieval-run-count.json`）：

| 配置 | 运行次数 | 说明 |
|---|---|---|
| `test` + uniform | **1** | 纪律守住 |
| `dev` + uniform | 1 | |
| `independent` + uniform（低难度池） | **5** | **偏差所在** |
| `independent` + same_relation | 4 | 诊断用 |
| `independent` + adversarial | 4 | 诊断用 |
| `independent` + 其余四组权重 | 各 1 | |

### 偏差的性质

`test` 只跑一次，这一条守住了。**但 `independent` 跑了 5 次，并且我基于它的诊断结论
新增了 `pool_modes`（三种池难度）。**

严格说这是一次**方法泄露**：`independent` 原本是 held-out，我却在它上面发现了
"任务太简单"这个问题，然后据此改了代码。虽然改的是**评测框架**而不是检索算法，
且没有根据它的分数调整任何参数，但边界确实模糊了。

### 影响评估

- **对检索分数无影响**：三种池模式的代码是新增的，`unrelated` 模式的分数
  在加它之前和之后完全相同（都是 1.000）
- **对结论有影响**：我在它上面确认了"同主题干扰池造不出来"，
  这个结论现在写进了报告。若严格按 held-out 纪律，这个发现应该在 test 上做，
  或另找第四个数据集
- **缓解**：`pool_modes` 的引入记录在 `docs/reports/c4-pool-limitation.md` 里，
  时间顺序可追溯，不是事后美化

### 结论

这条偏差不改变任何数字，但它提醒：**`test` 与 `independent` 的角色需要事先分清楚**。
本变更里 `test` 是报告集、`independent` 是诊断集——
如果一开始就这么声明，5 次运行是合规的。问题在于我事后才明确这个分工。

## 10. 一句话总结

**读路径建成了，指标可测了，但测出来的东西还不能支持"检索能力强"这个结论。**

- 三种池难度里，只有最低的那种有数据
- 五组权重完全无差异
- 等义判断的等义类只有 50% 召回

这些不是实现缺陷，是**当前数据的表达能力上限**。
下一步最有价值的工作不是改算法，是造一个能测出真实难度的数据集。

### 补充（事后）

第 0.1 节改变了这句话的分量。原先写的是"这些不是实现缺陷"——
**这个判断错了一半**：

- "两种池无法评估"、"五组权重无差异"确实是数据表达能力的上限
- 但"1.000"本身是**实现缺陷**：查询与 gold 原文逐字相同、干扰项无原文、
  指标在召回后只剩 1 条候选时仍照常计算

所以更准确的一句是：

> **读路径建成了，但 C4 的读数不可用。v2 必须先修尺子，再谈难度。**
