> 生成日期：2026-10-26
> 场景集：60 条（dev 40 / test 20），六类均衡
> 模型：DeepSeek V4.1 Flash（本地网关，强制 SSE，响应缓存）
> 状态：**60/60 已人工确认；第二标注者已完成（κ = 1.000）**

## 标签确认状态（验收前置条件）

```
$ uv run python -m evals.tools.label --split dev summary
dev.jsonl: 40 条，已确认 40 条

$ uv run python -m evals.tools.label --split test summary
test.jsonl: 20 条，已确认 20 条
```

人工标签与机器提案**零分歧**：60 条全部沿用提案标签，包括修正后重新确认的 4 条 CONFLICT。

## 第二标注者与 κ

| 对比 | κ | 不一致 |
|---|---|---|
| 主标注 vs alice | 1.000 | 0 |
| 主标注 vs bob | 1.000 | 0 |
| alice vs bob | 1.000 | 0 |

### 这个 1.000 应当如何解读

**它不能当作"标注标准极其清晰"的强证据。** 三个标注者 20 条零分歧，
更可能是因为三者共享了同一套信息（同一份场景描述、同一套分类定义，
甚至同一批人），而不是因为标准本身无歧义。

真正独立的第二标注者应该会产出**非零分歧**——本次修正前的数据恰好证明了这一点：
bob 最初有 3 条 `ADD → NOOP` 的不同（虽然那 3 条是他标错了）。

诚实口径：**这是一次"同源复核"，不是"独立双标注"**。
报告中不把 κ = 1.000 写进结论，只用它说明"复核未发现分歧"。

### 标注过程中发现并修正的硬错误

`test-add-01/02/03` 曾被标成 `NOOP`，但它们的 `existing_value` 为空。
NOOP 的定义是"与既有值完全相同"，没有既有值时不可能成立。已改为 `ADD`。

**κ 抓不到这类错误**：κ 只衡量两人是否一致，不衡量单条是否合法。
两个人可以一致地都标错。因此新增了独立的逻辑自洽检查
（`tests/resolver/test_label_consistency.py`），对全部标注文件断言：

- `existing_value` 为空时，不得标成 NOOP / MERGE / SUPERSEDE / BRANCH
- candidate 与 existing 完全相同时，不得标成 SUPERSEDE（那应是 NOOP）

## 修正：4 条 CONFLICT 配对不成立

标注过程中发现 9 条 CONFLICT 里有 4 条**不满足 CONFLICT 的前提**
（同一属性、同一对象、同一取值槽位上的两个竞争值）：

| id | 原配对 | 问题 | 修正后 |
|---|---|---|---|
| `dev-conf-01` | 喜欢花生酱 / 对花生过敏 | 偏好 vs 医学限制，维度不同 | 能吃花生 / 对花生过敏 |
| `dev-conf-02` | 能接受海鲜 / 对海鲜过敏 | "能接受"语义模糊，不构成互斥 | 不能吃海鲜 / 能吃海鲜 |
| `dev-conf-05` | 阿里云 / k8s | 云厂商 vs 编排平台，可同时成立 | 阿里云 / AWS |
| `test-conf-01` | 不吃牛肉 / 对乳制品过敏 | 同类不同对象，可并存 | 不吃牛肉 / 吃牛肉 |

**根因**：生成 CONFLICT 时用的是"把 candidate 的 authority 调低"这个语法操作，
没有检查两个值在语义上是否互斥。`lower_authority` 规则会忠实地把它们判成
CONFLICT，所以**这个错误不会让任何测试失败**。

**采取修正而非删除**：删除后 dev 只剩 3 条、test 剩 2 条 CONFLICT，
每类 2~3 条的 F1 方差会大到没有意义。

一个值得记录的事实：**这 4 条正是标注时被跳过的条目**。dev 轮的目的就是
校准标准，它在起作用。

## 0. 先说结论：100% 是训练集成绩，独立场景集上只有 43.3%

这是本报告最重要的一节。

### 独立来源的 held-out 结果

| 数据集 | 来源 | 规模 | accuracy | macro-F1 |
|---|---|---|---|---|
| dev / test（本文其余各处） | **作者自写**，规则也按它设计 | 60 | 100% | 1.000 |
| **独立场景集** | **第三方朋友独立编写**，作者未参与 | 30 | **50.0%** | 0.508 |

**这个 50 个百分点的落差，就是过拟合的量化值。**

前者是"训练集"：场景由我写、规则由我按这些场景设计、标签由我确认。
后者是本项目第一个真正 held-out 的数据：场景与判断全部来自第三方，
我只做了三件必要的结构化补充（见第 6 节）。

### 15 条错误的根因分布

| 根因 | 条数 | 本质 |
|---|---|---|
| MERGE 需要语义判断 | **6** | `"靠窗那一排"` 与 `"C区第三排左数第二个工位"` 是补充关系，但字符串毫不相干 |
| 猜测语句被当成确定新状态 | **4** | `"密码不是那个，应该是87654321吧"` 里的"吧"是推测语气，不该当作确定的新状态 |
| NOOP 需要语义等价判断 | **3** | `"每周日凌晨"` 与 `"每周日零点"` 是同一件事，任何字符串方法都识别不出 |
| 低权威一律判冲突 | **2** | 权威更低不等于矛盾，但影响远小于预期 |

### 最有说服力的一组数字

按原作者标注的把握程度分层：

| 原作者把握 | 错误 | 总数 | 错误率 |
|---|---|---|---|
| 确定 | 10 | 25 | **40%** |
| **不太确定** | **5** | **5** | **100%** |

原作者自己拿不准的 5 条，系统全错。这不是巧合：这些恰好是
"语义等价"、"猜测语气"、"制度与实际冲突"这几类需要真正语义理解的情形。

**它们也正是人类标注者会犹豫的地方——这个重合本身说明系统缺的是语义能力，
不是阈值调参。**

### 两个必须说清的结论

**第一，字符串方法有硬天花板。**
15 条错误里有 **9 条**（6 条 MERGE + 3 条 NOOP）是同一类问题：
两个表述在语义上等价或互补，但字面上毫不重叠。
任何基于子串/词集的方法都不可能识别。这不是调参能解决的，是方法边界。

**第二，"低权威必冲突"的假设虽被证伪，但影响远小于预期。**
我原以为 7 条误判都源于此，修正 `existing_authority` 后只剩 2 条。
对照实验也印证了：完全删掉这条规则只能从 50% 提到 53.3%（修好 1 条），
而代价是丢失安全性（工单备注会覆盖过敏史）。


## 1. 为什么自写场景集的 100% 不可信

| split | 模式 | accuracy | macro-F1 |
|---|---|---|---|
| test | 全量（规则 + 模型） | 1.0000 | 1.0000 |
| test | `--no-llm`（纯规则） | 1.0000 | 1.0000 |
| dev | 全量 | 1.0000 | 1.0000 |
| dev | `--no-llm` | 1.0000 | 1.0000 |

四种组合全部满分，且**模型与纯规则的差异为 0**。这几乎肯定意味着评估本身有问题，
而不是系统真的完美。下面逐条说明为什么。

### 1.1 场景与规则出自同一个人

60 条场景是我写的，七条规则也是我按这些场景设计的。这是**循环论证**：
规则在"我想到的场景"上必然表现良好，但它在新场景上的泛化能力完全没有被测量。

这不是可以通过"再多写几条场景"解决的问题——只要场景和规则出自同一轮思考，
满分就只是自证。

### 1.2 模型被调用 17 次，但一次都没改变结果

实测 `test` 集：

| 来源 | 条数 |
|---|---|
| 规则命中 | 3 |
| 模型判定 | 17 |
| 禁用 | 0 |
| 判定失败 | 0 |

模型确实被调用了 17 次（因为 17 条文本不含正则能识别的变更标记），
但**这些场景的判定类别并不依赖"是否新状态"**：

- `BRANCH` 由条件差异决定
- `CONFLICT` 由权威更低决定
- `MERGE` 由值包含关系决定

只有 `SUPERSEDE` 依赖 `is_new_state`，而 test 集里唯一的 SUPERSEDE 场景
（`test-sup-04 "值班人现在是孙八"`）恰好被规则命中了。

**所以"模型与纯规则差异为 0"是场景设计的产物，不是模型没价值的证据。**

### 1.3 样本量太小，macro-F1 的方差很大

test 集每类只有 3~4 条。单个样本改变就能让某类 F1 抖动 25 个百分点，
进而让 macro-F1 抖动 4 个百分点。这个量级的样本**无法支撑任何显著性声明**。

## 2. 真正可用的信号

### 2.1 归一化覆盖率：19/20 → 20/20

第一轮跑出 `normalized_false = 1/20`，定位到 `dietary_restriction`
（饮食禁忌）这个关系没有登记在别名表里。已补入。

这个指标比 macro-F1 有用得多：它衡量**词表对真实输入的覆盖程度**，
且不依赖谁来写标签。

### 2.2 规则覆盖率：3/20

test 集里只有 3 条文本能被正则识别变更标记，17 条需要模型。

这说明**正则的作用域远比预期窄**。真实用户的表达大多不含"改成/现在"这类显式标记，
所以模型兜底是必需的，不是可选的。这个数字在任何标签方案下都成立。

### 2.3 判定分布的合理性

两种模式给出的类别分布都与期望分布一致（NOOP 3、ADD 3、MERGE 3、
SUPERSEDE 4、BRANCH 4、CONFLICT 3）。这说明**规则没有系统性偏向某一类**，
也没有靠"全判 ADD"这类退化解刷分。

## 3. 修掉的真实缺陷（这些与标签无关）

实现过程中发现并修复了**五个**会导致系统错误的问题：

| 缺陷 | 后果 | 修复 |
|---|---|---|
| `CONFLICTED` 条目与既有 ACTIVE 必然时间重叠 | 冲突候选根本无法落库 | 重叠触发器排除 CONFLICTED（它按定义就是同一时段的竞争说法） |
| `_find_existing` 只按精确 condition 查找 | 带条件的候选看不到同键其他分支，误判为 ADD | 增加 `active_all()`，按"同条件 → 无条件 → 任意条件"三级回退 |
| `resolve_conflict` 用胜者的 valid_from 关闭败者 | 胜者原本是 CONFLICTED 时会产生零长度区间 | 关闭时刻取两者起点的较大值，并把胜者起点推进到关闭之后 |
| 评测复用同一个库 | 场景互相污染，第二条 ADD 撞上第一条的 ACTIVE | 每条场景独立临时库 |
| **否定词被误判成"补充"** | `"吃牛肉"` 是 `"不吃牛肉"` 的子串，规则 4 把语义反转判成 MERGE | 检测值的**开头**是否带否定词；两侧否定状态不同则绝不判 MERGE |

### 第五个缺陷的修复过程本身值得记录

第一次修复用了"前 8 个字符里包含否定词"，结果引入了新回归：
`"张三 周三不在"` 中"不"在中间，被误判成否定，把 MERGE 错判成 SUPERSEDE，
dev 准确率从 100% 掉到 97.5%。

**是评测把这个回归抓出来的**，不是代码审查。修正为只检查开头后恢复 100%。
这个坑现在有专门的回归测试（`test_rule4_mid_value_negation_does_not_block_merge`）。

## 6. 独立场景集的方法说明

这批 30 条由第三方朋友独立编写，包括期望判定与理由。为了让它能被系统消费，
我们做了**三处结构化补充**，每一处都会影响结果，必须如实声明：

| 补充项 | 做了什么 | 影响 |
|---|---|---|
| `subject` / `relation` | 把自然语言描述映射到已有归一化词表 | 若映射错，判定必然错。本批未出现映射错误 |
| `existing_authority` | 把"谁说的"映射为 `user_direct` / `third_party` / `system_inferred` | **必需**。此前的评测把 existing 一律当 `user_direct`，导致"第三方 vs 第三方"被误判成"低 vs 高" |
| `condition` | 从原文提取条件词（如"法定节假日"、"应酬"） | **会高估能力**。真实使用时条件也要靠抽取，而 C3 不做抽取 |

`text` / `existing_value` / `candidate_value` / `expected` / `rationale` / `confidence`
全部保留原作者原文，未做改写。

### 条件抽取对结果的影响

`--with-condition` 只跑显式给出了 condition 的场景（4 条 BRANCH）。
这 4 条全部判对，说明**只要条件被正确提供，BRANCH 判定是可靠的**。
但这不代表系统能自动识别条件——那属于读路径（C4），本变更不覆盖。

### 对照实验：如果改规则会怎样

`evals/ablate_independent.py` 量化了三个候选改动。**结果几乎全部为零**：

| 变体 | accuracy | 说明 |
|---|---|---|
| baseline | 50.0% | 当前规则 |
| authority_updates | 50.0% | 只在有变更标记时允许低权威取代——**那 15 条文本一个标记都没有** |
| drop_lower_authority | 53.3% | 完全删除该规则，只修好 1 条，代价是丢失安全性 |
| semantic_merge | 50.0% | 用模型判断"旧值是否仍成立"——模型也没能救回这 6 条 |

**这三个改动都没有被采用**，因为：

1. 独立集是 held-out，在上面调规则会让它退化成第二个 dev 集
2. `drop_lower_authority` 的 +3.3pp 是用安全性换来的（会让工单备注覆盖过敏史）
3. 真正的修法是让模型参与"是否仍成立"的判断，但这需要重做规则架构，属于 C4 范畴

**这个对照实验本身是有价值的结论**：它证明"调规则"不是瓶颈。
6 条 MERGE + 3 条 NOOP 共 9 条错误，任何规则层面的改动都动不了它们。

## 8. 一句话总结

**实现是对的，评估刚刚才开始作数。**

六类判定、规则顺序、状态映射、归一化边界都有测试锁定，五个真实缺陷已修复。
自写场景集上 100%，**独立来源场景集上 50.0%**——这 50 个百分点的落差
才是这个系统真实的位置。

错误是结构性的，不是 bug：

- **字符串方法有天花板**：9/15 条错误（6 MERGE + 3 NOOP）需要语义理解，
  任何子串或词集方法都做不到
- **"拿不准"的样本全错**：原作者标"不太确定"的 5 条，系统 5 条全错。
  这个重合说明缺的是语义能力，不是阈值
- **"低权威必冲突"被证伪但影响有限**：修正 `existing_authority` 后只剩 2 条

下一步不是调参（对照实验证明调规则只能修好 1 条），
是让模型参与"旧值是否仍成立"的判断，并用第二个独立来源验证增益保持。

### 这批数据的方法学价值

它做成了此前的数据做不到的事：**证明 100% 是假的**。

在此之前，"场景由我写、规则由我设计、标签由我确认"这个闭环无法自证有问题。
第三方独立编写后，落差立刻显现。这是本项目最有价值的一次测量。
