## 0. 这份协议解决什么

C4 的 `SEH@5 = 1.000` 不是检索能力，是三个构造缺陷叠出来的：

1. `query` 与 gold 的存库原文**逐字相同**（`annotate_retrieval.py` 里 `query = row["text"]`，
   `run_retrieval._item` 又把同一句 `row["text"]` 当作 gold 的索引原文）
2. 干扰项的 `text` 为 `None`，索引里只剩 `subject/relation/value`，物理上无法竞争
3. 排名只在**被召回的子集**里计算。该子集在 independent 上 26/26 条只有 1 个元素，
   排名从未发生，`SEH` 恒为 1

所以 v2 的第一目标不是"更难"，是**让排名有机会发生，并且让答错可能发生**。

## 1. 角色：报告集，预注册，冻结

| 数据集 | 角色 | 允许的运行次数 | 用途 |
|---|---|---|---|
| `dev`（C3/C4 旧集） | 调参集 | 不限 | 调规则、调权重 |
| `test`（C3/C4 旧集） | 报告集 | **1** | 报告里的主数字 |
| `independent`（C3/C4 旧集） | 诊断集 | 不限 | 发现问题，不用于宣称能力 |
| **`retrieval-v2`** | **报告集** | **系统分数 1 次**（合格性检查不限，见 §1.1） | v2 的全部主数字 |

`retrieval-v2` 一旦冻结：

- **不许**再改数据、权重、提示词、池构造规则
- **不许**为了"看看效果"重跑；重跑即失去报告集资格
- 结果 JSON 必须带 `run_count`，且测试断言它为 1
- 必须改时开 `dataset-v2.1`；v2 的数字留在报告里，**不许覆盖**

### 1.1 什么算"跑":造数据期间的可见性边界

造数据必然要反复调试。**如果不说清哪些运行算数，"只跑一次"会被解释成
"只要不把结果写进报告就算没跑"**——这正是 C4 §8 那次偏差的形状
（跑了 5 次，辩称"只用来诊断"）。所以按"看的是什么"划界，而不是按"跑了几次"：

| 类别 | 允许次数 | 可以看吗 | 举例 |
|---|---|---|---|
| **合格性检查** | 不限 | ✅ 随便看、看到什么改什么 | L1–L8 反泄漏、F1–F11 门禁、池成员构成、随机/零召回/洪水基线 |
| **系统检索分数** | **1** | ❌ 全过之前不许看 | `SEH@1` / `SEH@5` / `MRR` / `SRS` 在 v2 数据上的实际值 |

判定边界只有一条：**输出里有没有"系统在 v2 上答对了几条"这个量。**

- 随机基线、零召回基线、洪水基线**不算系统分数**——它们不含被测系统的判断，
  可以反复跑。它们是"尺子是否活着"的检查，不是"系统有多强"的读数
- F1–F11 全部通过之前，**禁止运行被测系统**在 v2 上的评测
- 第一次运行被判为报告运行。**若它失败，不改数据、不重跑**，按 §1 记为
  "v2 首次运行结果"，然后开 `dataset-v2.1`

**为什么洪水基线可以看、系统分数不能看**：洪水基线（只做 BM25）是**下限参照**，
它告诉你"不用我们的方法能拿多少"。看到它不会诱导你调系统。
而系统分数一旦可见，后续任何"再改一点池构造"都会变成对着测试集调参。

### 1.2 如果门禁失败怎么办

F1–F11 任一条不过 → **改数据，不改阈值**。这是合格性检查，允许反复迭代。

但要注意一条纪律：**改数据时不许参照系统分数**。因为系统分数此时不可见，
这条自然成立——只要守住 §1.1 的表格。

C4 的问题恰恰是反过来的：先在 `independent` 上看清分数（1.000），
然后才发现任务太简单，并据此新增了 `pool_modes`。那一步之后，
`independent` 就不再是 held-out 了。

## 2. 难度轴：三条，v2 只覆盖两条

| 轴 | 数据形态 | 现有召回能否覆盖 | v2 是否覆盖 |
|---|---|---|---|
| **A** | 同 subject、同 relation、**不同 condition** 的多条 ACTIVE | 能（邻接） | ✅ |
| **B** | 同 subject、同 relation、同 condition、**不同时间**（1 条 ACTIVE + N 条 SUPERSEDED） | **不能** | ❌ 明确排除 |
| **C** | 同 subject、**不同 relation** 的多条 ACTIVE | 能 | ✅ |

### 2.1 B 轴为什么本期不做（两条结构性阻塞，不是"没排期"）

两条都要说，缺一条就会被读成"改个指标就能上"。

**阻塞一：池构造层就装不进去。**
`build_pool` 与 `select_pool_distractors` 都按逻辑键
`(subject, relation, condition)` 排除与 gold 同键的条目。历史版本与 gold
**恰好同键**，因此在池构造的第一步就被过滤掉，一条都进不来。

**阻塞二：就算装进池里，指标也永远是满分。**
三路召回全部写死 `status = 'ACTIVE'`。SUPERSEDED 永远不会成为候选，
于是 gold 永远排第 1。**这会复现一模一样的假满分**——只是换了个池子。

**这两条缺一不可**：

| 只写阻塞二 | 会被读成"换个指标就行" |
| 只写阻塞一 | 会被读成"改一下过滤条件就行" |
| **两条一起写** | 才说明这是 `ux_active` 索引设计决定的**结构性不可能** |

**还有一个物理事实**：`ux_active` 唯一索引是
`(owner, scope, subject, relation, IFNULL(condition,'')) WHERE status='ACTIVE'`，
所以 B 轴的形态必然是"1 条 ACTIVE + N 条 SUPERSEDED"，而
**只要召回只看 ACTIVE，N 条历史版本就是不可见的**。

### 2.2 因此

- v2 **不宣称覆盖 B 轴**
- **B 轴不支持，因为现有召回在历史不可见时 SEH 恒饱和——那是 B 轴真正的难点，
  不是造数据能解决的。** 造一份"看似有历史版本"的数据集，只会得到第三个假满分：
  三路召回写死 `status='ACTIVE'`，SUPERSEDED 永不成为候选，gold 永远排第 1
- B 轴要单独开变更，且必然修改 `memory-retrieval` 的既有 requirement
  （"三路召回"当前写死 ACTIVE），属于 MODIFIED，需要自己的设计与验收
- B 轴还需要一个**不会饱和的新指标**（例如"陈旧值泄漏率"），而不是复用 SEH@K
- v2 的数据**仍然记录** `valid_from` / `supersedes` / `status`，
  使将来加 B 轴时不必重造数据——这是"这次不做"与"这次做不了"的分界证据：
  数据形态已经就位，缺的是召回能力与新指标

### 2.3 A 轴与 C 轴分别测什么

- **A 轴**：同一实体的同一属性有多个条件分支（`写代码时` vs `开会时`）。
  测的是"查询带着条件时，能否挑中对应分支"。
- **C 轴**：同一实体的不同属性（`包管理器` vs `测试命令`）。
  测的是"能否在同一个人的多条事实里挑中问的那一条"。
- **混合池**：A 的兄弟与 C 的同主体异关系同时存在。这是最接近真实的情形，
  也是唯一能同时考验 `condition_match` 与主题相关的模式。

## 3. 数据形态：记忆库 + 查询，不是场景对

C4 的形式是"一条场景自带一条 gold"，导致每条场景的候选池只能从别处凑。
v2 改成**记忆库 + 查询**，池由规则从库里构建。

```
data/retrieval-v2/
  memories.jsonl    # 记忆库：一个 subject 的全部事实，含条件分支与历史
  queries.jsonl     # 查询：自然提问 + 指向 gold_memory_id
```

**为什么这样改**：池构造变成**函数**而不是手工挑选。
手工挑干扰项等于把答案喂进去；函数化的池可以被测试，也可以被检查
"是不是又用了文件顺序的固定前缀"（C4 就是这么做的：76 条场景只有
15 种干扰项组合，其中一种被用了 36 次）。

### 3.1 `memories.jsonl` 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `memory_id` | ✅ | 库内唯一 |
| `subject` | ✅ | 归一后的实体，如 `project:ledger` |
| `relation` | ✅ | 归一后的属性，如 `package_manager` |
| `condition` | ◯ | 条件槽位；无条件为 `null` |
| `condition_slots` | ◯ | 结构化槽位，如 `["activity:coding"]`，供 `condition_match` 直接使用 |
| `value` | ✅ | 记忆值 |
| `memory_text` | ✅ | **产生这条记忆的原话**。不许为 `null`，不许等于任何 query |
| `authority` | ✅ | `user_direct` / `user_document` / `third_party` / `system_inferred` |
| `status` | ✅ | v2 只产 `ACTIVE`；B 轴预留 `SUPERSEDED` |
| `valid_from` | ✅ | 带时区 |
| `supersedes` | ◯ | 指向被取代的 `memory_id`，为 B 轴预留 |

**`memory_text` 必填是本协议的第一条硬规则。**
C4 的干扰项 `text=None`，索引里没有一句自然语言，词面召回无从匹配——
这不是"数据不完整"，是**测量装置坏了**。

### 3.2 `queries.jsonl` 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `query_id` | ✅ | |
| `axis` | ✅ | `A` / `C` / `mixed` |
| `subject` | ✅ | |
| `query` | ✅ | **自然提问**，问句，不是记忆原文 |
| `query_condition` | ◯ | 查询携带的条件，用于 `condition_match` |
| **`cue_type`** | ✅ | **`explicit` / `implicit`**，见 §3.3 |
| `gold_memory_id` | ✅ | 必须存在于记忆库 |
| `expected_value` | ✅ | 用于人工复核 |
| `author` | ✅ | `primary` / `independent` |

### 3.3 `cue_type`：A 轴难度的真正来源

**A 轴的难度不在"有几个分支"，在"查询有没有直接说出条件"。**

| `cue_type` | 形态 | 测的是 |
|---|---|---|
| `explicit` | 查询里直接命名了条件（"开会的时候我几点到"） | **条件词表覆盖** |
| `implicit` | 条件要从情境推断（"下周客户过来，中午带他们吃什么"→ 客户应酬） | **能否从情境推出该用哪条记忆** |

如果所有 A 轴查询都是 `explicit`，这一版就退化成"测中英词表"，
与 C4 的"测字符串包含"是同一类自证。

**这比缺陷 1–8 更隐蔽**：指标不会满分，看起来"有难度"，所以满分自检抓不到它。

因此：

- 每个 subject 的 A 轴查询**必须两种都有**
- 报告必须**分开出 `explicit` 与 `implicit` 两行分数**，不得合并成一个 A 轴数字
- `implicit` 的比例必须 ≥ 40%，分母是**A 轴查询**（不是全部查询）——
  因为 C 轴查询天然是 `explicit`（"这个仓库用什么包管理器"没什么可隐的），
  用全部查询做分母会把 C 轴算进 implicit 缺口里，逼着人去编造 C 轴的隐含问法
- **每个 subject 单独算，且每 subject 的 A 轴 `implicit` 占比 ≥ 50%**
- `implicit` 的条件**不得在 query 里出现同义词**（由 L9 机器检查）

**两条阈值不冲突，它们管不同的层级**：

| 层级 | 阈值 | 抓什么 |
|---|---|---|
| 数据集整体（A 轴分母） | ≥ 40% | 全局不要退化成测词表 |
| **每个 subject（A 轴分母）** | **≥ 50%** | 防止"有些 subject 20%、有些 60%，平均 40%"掩盖退化 |

逐 subject 的门槛比整体更严，因为**平均值会掩盖退化**：样例是 40.0%，
正好压在及格线上，没有余量。铺开时按 subject 拉到 ≥ 50%，
整体自然高于 40%。

**分母怎么定是一次真实的判断，不是笔误**：样例里 A 轴 10 条、4 条 implicit，
按 A 轴分母正好 40.0%（整体达标），按全部查询分母 33.3%（不达标）。
两种口径都能自圆其说，所以必须在冻结前钉死，否则事后可以挑好看的那个。
定成 A 轴分母的理由：C 轴根本没有"条件是否说破"这个维度，把它计入分母是无意义的分母。

### 3.4 `branch_nature`：不许为了凑分支编造条件

`ux_active` 决定了"同 relation 多条 ACTIVE"只能靠 `condition` 区分。但**天然多分支的
relation 有限**：

| 天然多分支 | 天然单值 |
|---|---|
| `meeting_time`、`code_style`、`deploy_target`、`oncall_owner`、`test_command` | `wifi_password`、`phone_number`、`seat`、`birthday` |

给 `wifi_password` 编出"在家 / 在公司 / 在客户现场"三个条件是**假的**，
而且这类假数据会让 `condition_match` 看起来有效——实际只是记住了编造的词。

`memories.jsonl` 增加一个字段：

| 字段 | 必填 | 值 |
|---|---|---|
| **`branch_nature`** | ✅ | `natural` / `forced` |

门禁：**`forced` 的 subject 占比 ≤ 20%**（F12）。
这个字段本身也是给未来的人看的：它记录了哪些难度是真实的、哪些是构造的。

## 4. 反泄漏条款（可测试，不可商量）

这五条每一条都对应 C4 的一个真实缺陷。

| 编号 | 规则 | 判定 | 阈值 |
|---|---|---|---|
| **L1** | query 不是记忆原文 | `normalize(query) != normalize(gold.memory_text)` | **100%**，零例外 |
| **L2** | query 不含 gold 值 | `gold.value` 不出现在 `query` 中（子串，折叠大小写） | **100%** |
| **L3** | query 与原话的字符重叠受限 | 字符 bigram Jaccard(`query`, `gold.memory_text`) | **≤ 0.50**，逐条检查 |
| **L4** | 每条记忆都有原文 | `memory_text` 非空 | **100%** |
| **L5** | 干扰项确实进得了池 | 每条 case 的同主题干扰项数 ≥ 3 | **100%** |
| **L6a** | 三路召回都被**调用** | 源码里 `recall_by_{lexical,vector,adjacency}(` 三者都作为调用出现（排除 import 行） | 三者齐全 |
| **L6b** | 池里真的有向量 | 建池时 `embedding=` 的写入次数 ≥ 池大小 | **100%** |
| **L6c** | 三路召回**返回非空** | 至少一条 A 轴查询上，三路的 `len(result) > 0` | **全部三路** |
| **L7** | `dedup` 收到的是文本 | 传入 `dedup` 的第二个字段等于 `item.text`，不是 `item.id` | **100%** |
| **L8** | `dedup` 收到的是真实分数 | 传入的分数不是常数 | **方差 > 0** |
| **L9** | `implicit` 查询里不出现条件的同义词 | `query_condition` 的已登记别名（`condition.py` 的 `_ALIASES`）不得出现在 query 文本中 | **100%** |

L2 会排除一类真实存在的问法（"用 pnpm 还是 npm？"）——这类问法把候选写进了
问题里，词面召回白送分。**排除它们是有意的**，并在报告里写明被排除了多少条。

### 4.1 L6–L8 为什么必须单独列

它们不是"数据"问题，是"评测入口"问题，但后果与数据泄漏同级：

| 规则 | 对应缺陷 | 后果 |
|---|---|---|
| L6a | C4 缺陷 7 | 三路召回只跑了一路，"融合"是在融合单列表 |
| L6b | C4 缺陷 7 | 即使调用了 vector，池里没向量 → 该路返回空，仍在空转 |
| **L6c** | **C4 缺陷 7** | **L6a 与 L6b 各自成立、合起来仍可能空转**（例如向量写进去了但维度不符，全部被跳过） |
| L7 | C4 缺陷 8 | 等价判断收到 UUID，判断能力与测量路径断开 |
| L8 | C4 缺陷 8 | 分数全为常数，`dedup` 内部排序退化为 **UUID 字典序**，把重排结果整块替换 |

**为什么 L6c 不能省**：L6a 判"调用了"，L6b 判"有数据"，但两者都对时仍可能
"调用了、有数据、却一条都没返回"。`recall_by_vector` 在维度不符时会报错，
但若向量维度与查询维度恰好一致而内容全为零向量，余弦相似度会全部相等甚至全被过滤——
那时"跑了"和"没跑"在结果上完全一样。

**只有 L6c 直接测"返回了什么"，而不是"做了什么"。** 这与本项目的一条通用教训一致：
*检查动作*（有没有调用、有没有写入）永远比*检查结果*（返回了什么）更容易自欺。

**L6 必须是两条，不能是 `grep -c "recall_by_"`。**
`run_retrieval.py` 第 37 行有 `from memory.retrieval.lexical import recall_by_lexical`，
按字符串计数会把它算进去——**那正是"断言查错对象"的老毛病又犯一次**。
判定必须看**调用位置**：

```python
called = {
    name
    for name in ("lexical", "vector", "adjacency")
    if f"recall_by_{name}(" in source
}
assert called == {"lexical", "vector", "adjacency"}
```

而"调用了"和"有东西可召回"是两件事：当前池构造里 `embedding=` 一次都没出现，
所以就算接上 vector 一路，它也只会返回空列表。**L6a 与 L6b 同时过才算数。**

**L8 的实测后果**：一个"全部判为无关"的判定，本应原样返回，
却把 `zzz, mmm, aaa, bbb` 变成了 `aaa, bbb, mmm, zzz`。
在 dev 上让 3/40 条排名改变，SRS 0.955 → 0.939。

这类缺陷的共同点：**每一层的单元测试都是绿的**。只有把流水线拼起来看，
才发现被测量的东西根本不是报告里写的那个。

（缺陷 8 就是典型：`dedup` 有 13 条单元测试，输入是手造的
`(id, text, score)`；`run_retrieval` 有 8 条入口测试，但不断言 `text` 的内容。
**两层各自自洽，接缝处断的。**）

## 5. 池构造：与轴对齐，且不许用文件顺序

当前 `pool_modes.py` 的两个模式与三条轴**不对齐**：

- **`SAME_RELATION` 实际是"同 relation、任意 subject，只排除与 gold 同逻辑键的条目"。**
  它的 docstring 写"不同 subject"，但代码里没有这个条件——实测选出的 142 条干扰项里
  有 **62 条与 gold 同 subject**。
  于是它**同时混进了两类东西**：A 轴的真兄弟（同 subject 不同 condition）
  和非 A 轴（同 relation 的别的对象）。测出来的分数无法归因到任何一条轴。
- `ADVERSARIAL` 用"与 gold 值有字符重叠"筛选，同样跨 subject、同样混轴。
- `UNRELATED` 用 `others[:limit]`，取的是文件顺序的前 20 条。

> 这一条本身就是 C4 的第六个缺陷：**docstring 描述的行为与代码不一致，
> 而报告是按 docstring 写的**。协议里所有"现有实现如何"的判断都必须实测，
> 不能引 docstring。

v2 定义三个**按轴命名**的模式，取代按难度命名的模式：

| 模式 | 干扰项来源 | 对应轴 |
|---|---|---|
| `sibling` | **同 subject、同 relation、不同 condition**（全部取，不采样） | A |
| `co_entity` | **同 subject、不同 relation**（全部取，不采样） | C |
| `mixed` | 上面两者并集 | A + C |

补齐到 20 条的填充项：**按 `sha256(seed + query_id)` 稳定排序后取前 N**，
不得使用文件顺序、插入顺序或任何"看起来自然"的序。
（C4 的 `others[:limit]` 就是文件顺序，必须修掉。）

每个模式都必须断言**成员构成**，而不是只断言数量：

- `sibling` 模式下，每条干扰项满足 `subject == gold.subject`、`relation == gold.relation`、
  `condition != gold.condition`
- `co_entity` 模式下，每条干扰项满足 `subject == gold.subject`、`relation != gold.relation`

**同主题干扰项全部取用而非采样**：A 轴的难点是"分支有 3–5 个，必须挑对"，
采样会把真实难度随机地调低或调高。

## 6. 有效候选数：C4 缺的那道门禁

C4 只检查"池大小 > K"，但**排名发生在召回之后**。池有 21 条、召回只返回 1 条时，
排名没有发生，SEH 恒为 1。

v2 引入两个必须报告的量：

| 量 | 定义 |
|---|---|
| `pool_size` | 建池后的条数（名义池） |
| `recall_size` | **实际进入排名的候选数**（召回 + 融合之后） |

**门禁**：`recall_size ≥ 2` 的 case 占比必须 **≥ 80%**。
不足 80% 时，报告里那组数字只能叫"未发生排名的比例"，不能叫检索分数。
这条在冻结前必须实测，达不到就改数据，**不许事后放宽**。

同时保留 C4 已有的 `skipped_small_pool` 纪律，但把判定位置从"建池前"移到
"召回后"——因为问题从来不在池，在召回。

## 7. 指标：分轴报告，A 轴主指标是 SEH@1

**K=5 与 3–5 个兄弟分支会饱和。** A 轴一个 relation 只有 3–5 个分支，
`SEH@5` 在池 21 条时几乎必然为 1——哪怕排在第 5 名。这正是 C4 的教训换了个地方重演。

### 7.0 竞争集：指标有没有意义的前提

"池大小"与"排名空间"是两件事。C4 只检查了池大小 > K，没检查召回后还剩几条，
于是 26/26 条 case 的召回集只有 1 个候选，排名从未发生（缺陷 3）。

v2 因此显式定义**竞争集**（唯一实现：`evals/metrics/v2_baselines.py::competing_set`）：

| 轴 | 竞争集 | 语义 |
|---|---|---|
| **A** | 同 subject、**同 relation** 的全部记忆 | 多个条件分支里挑对那一条 |
| **C** | 同 subject 的**全部**记忆（跨 relation） | 这个人多条事实里挑中问的那条 |
| **mixed** | 与 C 相同（C 已含全部同 subject） | — |

报告、门禁、随机基线**必须都用这个函数**。任何地方另算一套"池大小"，
都会重新制造 C4 的问题。

### 7.0.1 两个排名空间：系统分数在整池，随机基线在竞争集

**这不是笔误，是两个不同的量。**

| 口径 | 定义 | 用在哪 |
|---|---|---|
| **整池** | harness 的候选池（gold + 全部干扰项） | 系统实际排名 |
| **竞争集** | `competing_set()` 返回的同主题候选 | 随机基线、§7.1 的饱和判据 |

**实测证据（`data/retrieval-v2/sample`）**：`ledger-q4` 整池名次 **6**，
而它的竞争集只有 **4** 条。名次超过容量，所以两者的分母必然不同。

复算需要结果 JSON 里的 `rerank_order_tags` 与 `pool_tag_meta` 两个字段
（见 §7.0.2）。没有它们只能推断出名次范围，不能给出确切值。

### 7.0.2 `SEH@5` 在竞争集口径下**无定义**，不是 1.0000

| 指标 | 整池口径（池 12） | 竞争集口径（3–4） |
|---|---|---|
| A 轴 `SEH@1` | **0.9000** | **0.9000** |
| A 轴 `SEH@5` | 0.9000 | **不适用** |
| A 轴随机 `SEH@1` | 0.0833 | **0.3000** |

**A 轴 `SEH@5` 在竞争集口径下恒等于 1.0**，因为 K=5 大于最大竞争集 4——
"前 5 名"包含全部候选，与系统行为无关。

**所以不能写"竞争集口径 `SEH@5` = 1.0000"。** 它会读成一个满分成绩。
协议 §7.1 早就说过这件事（A 轴 `SEH@5` 数学上恒为 1），这里是同一件事的第二个口径。

三次同型事故：

| 场景 | 数字 | 实际含义 |
|---|---|---|
| C4 `SEH@5` | 1.000 | 池太小，召回只有 1 条 |
| v2 融合前 `SEH@5` | 1.000 | 融合只看 1 条 |
| **A 轴竞争集口径 `SEH@5`** | **1.0000** | **K > 竞争集，指标饱和** |

三次都不是成绩，三次都以合法形式出现。

**报告规则**：

- A 轴主指标是 `SEH@1`（两个口径一致，0.9000）
- A 轴 `SEH@1` 的随机基线**必须注明是哪个口径**：整池 0.0833 / 竞争集 0.3000
- A 轴**不得引用 `SEH@5` 作结论**；整池口径的 0.9000 只能标为"参考，整池口径"
- 竞争集口径写"不适用"，不写 1.0000

### 7.0.3 结果 JSON 的两个新字段

| 字段 | 内容 | 为什么需要 |
|---|---|---|
| `rerank_order_tags` | 完整 rerank 顺序（tag 形式） | 只有 gold 的名次时，无法算"竞争集内名次" |
| `pool_tag_meta` | `{tag: {subject, relation}}` | tag 不含 relation，没有它就分不清哪些候选是同 relation 的 |

只记 `subject` 与 `relation`，不记 `condition`——竞争集判定用不上，
而 20 个 subject × 每池 12 条 × 多一个字段会让结果文件多出上万个小对象。

一致性由 `tests/retrieval/test_rerank_order_tags.py` 保证：
顺序里 gold 的下标必须等于 `rank_after_rerank`。

### 7.1.0 `SEH@1` 满分同样是失败信号（F24）

§7.1 管的是 `SEH@5` 饱和（池小于 K 时恒为 1）。但那只是**指标无定义**。
`SEH@1 = 1.0000` 是另一种失败：**指标有定义，而数据测不到区分能力。**

| 现象 | 原因 | 性质 |
|---|---|---|
| `SEH@5 = 1.0000` | K 大于竞争集 | 数学恒等，与系统无关 |
| **`SEH@1 = 1.0000`** | **数据太简单** | **实验设计失败** |

实测两个 subject：

| subject | A 轴 `SEH@1` | 随机基线 | 判定 |
|---|---|---|---|
| `project:ledger` | 0.9000 | 0.3000 | 有区分空间 |
| `project:billing` | **1.0000** | 0.3333 | **F24 失败** |

billing 的满分不是装置问题：9 条 A 轴查询的 gold 与第二名加权总分差
全部为正（0.085–0.253），A 轴 0 条并列。

**根因**：`condition_match` 命中给 1.0、不命中给 0.0，权重 0.25。
只要 base 分差 < 0.25，condition 命中就必然排第 1。
而同一 subject 同 relation 的分支 base 分天然接近（共享 subject/relation 词面）。

**这意味着所有 A 轴 subject 都可能容易满分**，必须在铺开时逐 subject 检查。

### 7.1 A 轴必须用 SEH@1，因为 SEH@5 在数学上恒为 1

**这不是"可能饱和"，是恒等。** A 轴分支数 3–5 ≤ K=5 时，随机排序的
`SEH@5 = min(K,N)/N = 1.0`。

要在 K=5 上让随机基线低于 0.95，竞争集至少要 **6** 条
（`required_pool_size_for(5, 0.95) == 6`）。A 轴天然只有 3–5 个分支，
**永远到不了**——这不是数据不够多，是这条轴的性质。

样例实测（`data/retrieval-v2/sample`，12 条记忆 / 12 条查询）：

| 轴 | 平均竞争集 | 随机 `SEH@1` | 随机 `SEH@5` | 判定 |
|---|---|---|---|---|
| A | 3.40 | **0.3000** | **1.0000** | `SEH@5` 无区分力 |
| C | 12.00 | 0.0833 | 0.4167 | 两指标都有空间 |

Monte Carlo 复核（每查询 20000 次重排）：A 轴 `SEH@1`=0.3013 / `SEH@5`=1.0000；
C 轴 0.0852 / 0.4163。与公式一致。

因此**分轴定主指标**：

| 轴 | 主指标 | 次指标 |
|---|---|---|
| **A** | **`SEH@1`** + MRR（随机基线 0.3000） | `SEH@5` 仅作参考，**不得作为结论** |
| **C** | **`SEH@5`**（随机 0.4167）与 `SEH@1`（随机 0.0833）并列 | — |
| mixed | 同 C | — |

### 7.2 禁止合并成一个数字

A 轴的 `SEH@5` 恒为 1，把它混进总分等于**换一种方式重复 C4 的错误**：
总分会被 A 轴的饱和拉高，看起来"整体很强"，而实际上 A 轴一个字都没测出来。

- **禁止**报"A+C 合并的 SEH@5"
- 每个轴的分数**单独一行**，且必须带上该轴自己的随机基线
- 跨轴比较时只能比**同一种指标**（A 的 `SEH@1` 对 C 的 `SEH@1`）

### 7.3 随机基线（每条查询单独算，再平均）

**不套用单一"池 21 条"的常数。** 竞争集大小随查询变化，
必须先按 §7.0 算每条查询的竞争集，再逐条取期望、最后平均。

公式（`evals/metrics/v2_baselines.py`）：

| 指标 | 公式 |
|---|---|
| 随机 `SEH@1` | `1/N` |
| 随机 `SEH@5` | `min(K,N)/N` |
| 随机 MRR | `H_N / N` |

**实际数字必须在冻结前实测并写进报告**，不得沿用本节样例的 A=0.3000 / C=0.4167。

### 7.4 两道读数门（按轴分别适用）

| 门 | 阈值 | 适用 | 含义 |
|---|---|---|---|
| `SEH@1` **< 0.5** | 判为"没能同主题里挑对" | **A 轴必用** | 随机 0.30 时，0.5 不到两倍随机 |
| `SEH@5` **< 0.5** | 判为"系统没学到东西" | C 轴 | 随机 0.417 时，0.5 只略高于随机 |

**注意 A 轴的门槛必须单独校准**：A 轴随机基线是 0.30 而不是 0.048，
所以"低于 0.5"在 A 轴上只意味着"略高于随机"。A 轴要求 `SEH@1 ≥ 0.5`
是**两倍随机**的下限，不是强证据；报告里必须同时给配对 bootstrap 区间。

#### 7.4.1 三档判定（分轴适用，照此出数字）

| 轴 | 观测 | 判定 | 允许的表述 |
|---|---|---|---|
| A | `SEH@1 ≥ 0.5` 且区间下界 > 随机基线 | 通过 | "能在条件分支里挑对" |
| A | `SEH@1` 落在 [随机, 0.5) | 部分通过 | "略优于随机，证据不足" |
| A | `SEH@5 = 1.0` **且**竞争集 ≤ K | **不是成绩** | `SEH@5` 在此轴上无定义，只报 `SEH@1` |
| C | `SEH@5 ≥ 0.5` 且 `SEH@1 > 0.083`（随机） | 通过 | "能在多条事实里挑对" |
| C | `SEH@5 = 1.0` | **实验设计失败** | 先查测量装置 |

#### 7.4.2 `SEH@5 = 1.000` 的代码门禁

不能靠人记得去看，要在评测入口直接拦住。**但门禁必须按轴判断**——
A 轴的 1.0 是几何必然，不是缺陷：

```python
baseline = axis_baseline(dataset, axis)
if result["seh_at_k"] >= 1.0 and baseline.seh_at_k < 1.0:
    raise SystemExit(
        "SEH@5 = 1.000：这个轴本不该饱和，先排除测量缺陷。"
        "查 query 是否等于 gold 原文、召回后是否只剩 1 个候选、"
        "干扰项是否有原文。见 docs/reports/c4-retrieval.md 第 0.1 节。"
    )
if baseline.saturates_at_k:
    raise SystemExit(
        f"{axis} 轴的随机 SEH@5 已是 1.0，该指标在本轴无区分力。"
        "改用 SEH@1，或增大竞争集。"
    )
```

理由：C4 里 `SEH@5 = 1.000` 出现过三次（dev/test/independent），
**每一次都被当成"指标满分"记录下来，没有一次被当成"哪里错了"**。
满分是唯一不能自证的读数——它的成因可能是"系统完美"，也可能是"题目不存在"，
而后者的概率高得多。

这是本项目积累的**第二条硬规则**（第一条是"自写场景不能自证"）：
**看到满分默认判为失败，先排除测量缺陷。**

**但第二条规则要加一个限定**：先比较**该轴的随机基线**。
若随机基线本身就是 1.0，满分说明的是"这个指标在这条轴上没有定义"，
而不是"系统出错"。不做这一步区分，门禁会把 A 轴的正确行为误判成失败。

### 7.2 洪水基线（难度门禁）

朴素词面基线：只做 BM25，不做融合、不做重排、不做去重，取前 5。

| 判定 | 含义 |
|---|---|
| 洪水基线 `SEH@1` > 0.45 | **数据太简单**，同主题干扰项没起作用，回去改数据 |
| 洪水基线 `SEH@1` < 0.10 | 干扰项与 gold 词面过近，人也不好区分，怀疑构造有误 |
| 落在 `[0.10, 0.45]` | 合格 |

这条门禁的作用：**确保"系统赢"不是"任务本身不难"**。

## 8. 规模

**本表的所有数字都是算术结果，不是独立目标。** 只有「relation 数」和「分支数」是输入，
其余由它们推出。写死的总量会在参数变化后失效——§8.0 记录过两次这种情况。

| 项 | 值 | 来源 |
|---|---|---|
| subject 数 | **≥ 20** | C4 报告定下的下限 |
| 每个 subject 的 relation 数 | **2–3** | 输入（F21a）。下界 2：1 个 relation 无法产生跨 relation 的 C 轴竞争 |
| 其中多分支 relation 数 | **≥ 1** | 输入。0 个则 A 轴无查询可造 |
| 每个多分支 relation 的 condition 分支 | **3–5** | 输入（F5） |
| **A 轴查询** | **= Σ(多分支 relation 的分支数)**，每 subject **6–15** | 算术（F23 要求 ≥6） |
| **C 轴查询** | **= relation 总数**，每 subject **2–3** | 算术（F17b 要求每 relation 一条） |
| **记忆条目** | **= A 轴查询数 + 单值 relation 数** | 算术 |
| **合计可评估查询** | **≥ §9 反推的最小 n** | 由分项算术决定，见 §8.1 |

### 8.1 "合计"这一行为什么不写死数字

上一版写"合计 ≥ 160"，而它只是分项的加总。§9 的 MDE 依赖 n：

| n | 随机基线半宽 | 配对 MDE（p_d=0.3） |
|---|---|---|
| 120 | ±8.9pp | 14.0pp |
| 160 | ±7.7pp | 12.1pp |

20 个 subject × (2–3 relation) × (3–5 分支) 展开后是 **160–360 条查询**，
下界恰好等于 §9 表里的 120 之上。**所以"≥160"不是目标，是算术下界。**

若铺开后 n 只有 120，MDE 必须按 120 重算并写进报告，不许沿用本表。

### 8.0 一次口径修正：三个数字原本用了三套算法

上一版表格里：

| 行 | 写法 | 实际算法 |
|---|---|---|
| A 轴查询 | "每个分支一条"，"分支数合计 ≈ 80" | 按分支数 |
| 记忆条目 | "≥ 80"，"20 × 平均 4" | 按 subject × 4 |
| 合计可查询 | "≥ 120" | 80 + 40 |

"分支数合计 ≈ 80" 是从上一行的"平均 4 条"抄过来的，而那 4 条是**记忆条目**的口径，不是分支数。三个数字用三套算法，恰好凑成 120。

**后果不是工作量估错，是门禁失效**：

按旧口径（每 subject 4 条 A 轴查询），一个有 4 个 relation 的 subject 只有 4 条查询 → **每 relation 1 条**。其余 2–4 个分支：

- 会进池 → **L5"竞争集 ≥ 3"通过**
- **永远不会成为任何查询的 gold**

**池里有 3 条 ≠ 有查询在考这 3 条。** L5 检查的是"池里有几条候选"，不是"有几条被查询指向过"。所以它会绿，而 A 轴的真实难度完全没被测到。

这是 C4 缺陷 3 的精确重演，只是发生在数据构造阶段。

**因此按口径 1 执行**：每个分支都要有一条查询指向它。

### 8.2 F13 的实际工作量

每个 subject 的 A 轴查询数 = `Σ(多分支 relation 的分支数)`，落在 **6–15** 条。
按 ≥50% 算，**每个 subject 需要 `max(⌈A/2⌉, 5)` 条 implicit**：

| A 轴条数 | 最少 implicit | explicit | 占比 |
|---|---|---|---|
| 6 | 5 | 1 | 83% |
| 9 | 5 | 4 | 56% |
| 12 | 6 | 6 | 50% |
| 15 | 8 | 7 | 53% |

**下界是 6 不是 5**：A=5 时 implicit 占满 5 条、explicit=0，
而 F13 要求每 subject 两种 `cue_type` 都存在——A=5 本来就非法。
所以 F23 写 `A ≥ 6`。

**这是本数据集最大的工作量**，而且要按 subject 估，不是按总数估。

若某个 subject 天然写不出足够的隐含问法（例如某个 relation 只有单值、
没有条件维度），协议 §3.3 允许**减少该 subject 的 A 轴查询数**，
但该 subject 的 implicit 占比仍须 ≥ 50%，且 A 轴条数仍须 ≥6（F23）。
**这个调整必须写进铺开记录**，否则会被当成凑数。

### 8.3 四个必做的消融（造完数据后）

**每份数据集必须能回答四个消融问题：**

| 消融 | 做法 | 它回答什么 |
|---|---|---|
| 去掉词面 | `--paths vector,adjacency` | 词面贡献多少 |
| 去掉向量 | `--paths lexical,adjacency` | 向量贡献多少 |
| **去掉邻接** | `--paths lexical,vector` | **邻接是帮忙还是有害** |
| **去掉 condition** | 全部查询的 `query_condition` 置空 | A 轴是否真的在测条件区分 |

**若某个消融后分数不变，说明该部件在这份数据上无法测量，
必须写进报告的局限，不能算作"该部件无效"。**

**若"去邻接"后分数变好，说明邻接在这份数据上有害**——
那就该在用它评测时关闭邻接，并记录原因。

实测样例：

| 消融 | 结果 |
|---|---|
| 词面 `lex+vec` → `vector` | **12 条逐条相同**（词面增量 0） |
| 向量 `lex+vec` → `lexical` | 0.9167 → 0.6667（向量增量 +0.25） |
| **邻接** `3paths` → `lex+vec` | 0.9167 → **1.0000**（**去掉邻接后变好**） |
| **condition** | A 轴 `SEH@1` 0.9000 → 0.3000（**掉幅 +0.60**） |

第三行说明邻接在本样例上**有害**（`q4` 从 3 掉到 6）。这条要写进局限，
并在用此数据集评测时明确记录"邻接已关闭及原因"。

第四条是 A 轴成立的关键证据：消融后 **`never_recalled` 仍为 0**，
说明变的是名次而不是召回——**A 轴测的是"区分"，不是"召回覆盖"**。

实现：`evals/tools/ablate_condition.py`（condition 消融）。
词面/向量/邻接消融用 `--paths` 直接跑。

#### F17 为什么必须单独一条

L5 检查的是"竞争集 ≥ 3"，也就是**池里有几条候选**。
它不检查"这些候选有没有被查询指向过"。

按旧口径（每 subject 4 条 A 轴查询）构造数据时，一个有 4 个 relation 的
subject 只有 4 条查询 → 每 relation 1 条。其余 2–4 个分支会进池（L5 绿），
但**永远不会成为任何查询的 gold**。

**这是 C4 缺陷 3 的精确重演：池里有 3 条 ≠ 有查询在考这 3 条。**

F17 的判定：对每个 `(subject, relation)`，其每个 condition 分支
都必须至少是一条 `queries.jsonl` 里某条查询的 `gold_memory_id`。

> 这条与 §8.0 的口径修正是一对：口径修正规定了"每分支一条查询"，
> F17 把它变成可检查的断言。没有 F17，口径会重新漂回去。

#### F16 为什么需要

随机基线是唯一能证明"指标有区分力"的参照。C4 从来没有算过它，
所以"池大小 > K"被当成了"排名有意义"，而实际上 26/26 条召回集只有 1 条。

F16 的判定方式必须是**期望命中率 vs 精确公式**，不能用"多数试验是否命中"：

| 错误写法 | 后果 |
|---|---|
| 200 次里超过一半命中就算 1 | A 轴 0.30 被压成 0.00 |
| 打乱前取 gold 下标、打乱后按下标取 | 恒为 0（实测抓到） |

第二种错误本轮真的写出来过，由 `test_formula_matches_monte_carlo` 抓到。
**这与 C4 缺陷 2 同源：数字看起来正常，测的不是它声称的东西。**

#### F11 为什么不比数量

"用例数 = 缺陷数"是个陷阱：`authority`/`status` 那条有 3 个 parametrize 分支，
缺陷 8 有两条互补证据（入口传参 + 排序退化）。**直接比 12 == 8 会永远失败**，
然后人会去改数字——那就变成让测试迁就现实。

真正的判据是**覆盖关系**，由 `tests/retrieval/test_locked_defect_manifest.py` 执行：

| 断言 | 抓的是什么 |
|---|---|
| 报告列出且仅列出缺陷 1..8 | 报告表格被改动却没同步 |
| 每个缺陷至少一条锁定测试 | 修了缺陷、删了测试、忘了更新报告 |
| 无孤儿 `locked_defect` 测试 | 缺陷修好后测试留下但映射没清 |

```bash
uv run --no-sync pytest tests/retrieval/test_locked_defect_manifest.py -q
uv run --no-sync pytest -m locked_defect -q
```

> `--no-sync` 是必要的：改 `pyproject.toml` 会让 `uv` 触发重新构建，
> 而本环境无外网，`hatchling` 拉不下来。这是环境坑，不是测试问题。

| F10 | 全返回基线 `SEH@5` = 1.0 | 池上限或 K 设错 |

### 10.1.2 F9 抓不到缺陷 3（一条必须改正的推断）

交接时提出的判断是"若有 F9，就会立刻发现召回集只有 1 个候选"。
**实测证明这个推断不成立**，不能写进协议当作理由：

| 情形 | gold rank | `SEH@5` | F9 判定 |
|---|---|---|---|
| A. 三路全关，召回为空 | `None` | 0.0 | ✅ 通过 |
| B. C4 的实际情形：召回只返回 1 条且正好是 gold | 1 | 1.0 | ✅ **也通过** |

缺陷 3 的形态是"召回返回了 1 条，且恰好是 gold"。**零召回基线永远碰不到这个情形**，
因为它连那 1 条都不返回。所以 F9 通过与否与缺陷 3 无关。

真正能抓缺陷 3 的是两条：

| 门 | 为什么有效 |
|---|---|
| **F2**：`recall_size ≥ 2` 的 case 占比 ≥ 80% | 直接数"进入排名的候选数"，不靠指标间接反映 |
| **F8**：随机排序 `SEH@5` < 1.0 | 候选集只有 1 条时，随机排序无法改变结果，`SEH@5` 必然 1.0 |

F9 仍然保留，但它防的是另一类错（空召回被算成命中），**不能拿它当缺陷 3 的证据**。
把三条分开写、各管一件事，比"三条一起通过就说明指标是活的"更准确。

### 11.2 打 tag 之后

第一件事是**跑一次真实系统分数并入库**，不许在看到分数后回头改数据。
看到分数之后产生的任何"这里调一下会更好"，一律进 `dataset-v2.1`。

### 11.3 `locked_defect` 标记的用途

"锁定缺陷"的测试（断言现状是坏的）会被标上 `@pytest.mark.locked_defect`：

```bash
pytest -m locked_defect      # 列出所有"锁定现状"的测试
pytest -m locked_defect -q   # 冻结前跑一次，核对清单与报告一一对应
```

**修复提交才是改成正向断言的时机**，不是打 tag 的时候。
tag 只冻结数据与协议，不冻结代码状态——缺陷还在，测试就该红。

- 第 4 步之后，数据、权重、提示词、池规则**全部锁定**
- 需要修正时：开 `dataset-v2.1`，v2 的数字**原样保留**
- 报告必须能回答"这份数字是哪一次运行、哪一版数据"

## 12. 本协议明确不做

- **不做 B 轴**（历史版本），理由见 §2.1：池构造与召回两层都结构性阻塞，
  强行做会得到第二个假满分
- **不改 `src/`**：v2 只新增数据、池构造函数、评测入口与测试；
  不修改三路召回的 ACTIVE 过滤，不修改重排公式
- **不调权重**：五组预注册值保持不变；若 v2 上五组仍然无差异，那本身是结论
- **不做答案生成**（C5 范畴）
- **不重跑旧集**：`dev` / `test` / `independent` 的数字不动

## 14. 协议自身的可证伪性

本协议里每一条"现有实现如何"的判断，都必须在造数据前**用代码实测**，
不能引 docstring（§5 那条错误就是引 docstring 引出来的）。

造数据前的自检清单：

| 检查 | 命令 |
|---|---|
| 池模式的实际成员构成 | 逐条断言 subject/relation/condition，见 §5 |
| 现有池的干扰项是否随机 | 统计不同组合数与最高复用次数 |
| 指标在池上会不会饱和 | 用随机排序跑一遍，核对 §7.1 的表 |
| 方差是否真的在候选里 | 查池内候选，不查数据字段 |
| **三路召回是否都进了评测** | 调用位置判定，见 §4.1：`recall_by_{x}(` 三者都在 |
| **池里是否真有向量** | `embedding=` 的出现次数 ≥ 池大小（当前为 0） |
| **下游拿到的是文本还是 id** | 打印 `dedup` 的入参，确认第二字段是 `item.text` |
| **常数分数是否让排序退化** | 给 `dedup` 全常数分，断言输出顺序等于输入顺序 |

任一项与预期不符 → **先修协议，再冻结**。
