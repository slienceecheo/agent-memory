## 项目是什么

冲突感知的长期记忆层。核心主张：**抽取交给 LLM，"哪条记忆现在有效"由符号化状态跟踪裁决。**

求职作品集项目，用 OpenSpec 管理变更。

## 已完成（四个变更，全部归档）

| 变更 | 交付 | 关键结论 |
|---|---|---|
| **C1** 评测骨架 | 三条基线 + embedding/LLM 缓存 + 指标 | naive-rag 的 88% 里 66 个百分点来自"把冲突答案都报出来" |
| **C2** 双时态存储 | 唯一不变量 + 区间不重叠 + 审计只追加 | 四个 SQLite 坑（NULL 绕过索引、`t < NULL`、`REPLACE` 绕过触发器、FTS 无中文分词）全部实测验证 |
| **C3** 六类判定 | 规则状态机 + 60 条场景 + 标注工具 | **自写场景 100% / 独立场景 50.0%**，9/15 错误是字符串方法的天花板 |
| **C4** 检索层 | 三路召回 + RRF + 四特征重排 | **指标满分但不证明能力**，同主题干扰池造不出来 |

## 下一步：二选一

### 选项 A：开 C5（答案策略）

复用现有基础设施，接上 C3 的冲突判定，做"四种动作"：
直答 / 带前提回答 / 降置信+追问 / 明确无记录。

因为候选池只能造出"无关主题"这一种难度。

### 选项 B（推荐）：先造"同主题多条候选"数据集

C4 暴露的核心限制：`independent` 集 29 个 relation 里 28 个只出现一次，
无法构造"同一个用户在多条相似记忆里挑对"的候选池。

**需要什么**：
- 至少 20 个 subject
- 每个 subject 下有 3–5 条同 relation 的记忆
- 让"同一主题内的区分"成为真实难度

**为什么先做这个**：它决定后面所有评测有没有意义。
C4 的满分是因为干扰项毫不相干，C5 会重蹈覆辙。

一天能造完。

## 环境与纪律

**环境**（详见 `AGENTS.md`）

- Python 3.12 + uv，`uv run` 执行一切
- 本地 LLM 网关 `127.0.0.1:3211`，**强制 SSE**，`stream=false` 也没用
- 访问本地网关必须 `NO_PROXY=127.0.0.1,localhost`，否则被代理劫持
- Embedding 用阿里云 `qwen3.7-text-embedding-flash`，**仅北京端点**
- 所有 LLM 与 embedding 调用必须走缓存（上游不确定，缓存是可复现的前提）

**纪律**

- 产物用中文，代码与标识符用英文
- 每个变更：`/openspec-propose` → 审稿 → `/openspec-apply` → 归档
- 先写失败测试，再写实现
- **报告里的数字必须能从 `results/*.json` 复算**（有测试强制）
- `test` 集是报告集，只跑一次；`independent` 是诊断集

## 一个必须知道的教训

C3 的独立场景集是本项目最有价值的测量，因为它**证明了自写场景的 100% 是假的**。

在此之前，"场景由我写、规则由我设计、标签由我确认"这个闭环无法自证有问题。
第三方独立编写后，落差立刻显现（100% → 50%）。

**任何新结论都应该先问：这个数字有没有可能只是自证？**
