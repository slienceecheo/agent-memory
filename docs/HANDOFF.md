### v3 的轴判定与 F21a 约束（写在这里，因为它们决定数据怎么造）

**轴的判据是"取值集合"，不是中位数、不是有序列表、不是标签集合**：

```
n_competitors(query) = 池中与 gold 同 relation 的候选数（不含 gold）
policy = set(within) == set(cross) ? merged : two_axes
         只有一轴有查询 -> single_axis；两轴都空 -> no_axis
```

| 判据 | 失效处 |
|---|---|
| 中位数 | 1（尾部不同但中位数相同） |
| 有序列表（含长度） | 2（混入样本量） |
| 标签集合（within/cross） | 2（`{1}` 与 `{7}` 都判 merged） |
| **取值集合 `set`** | **0** |

**实测（v2 数据，可复算）**：

| subject | 派生 within 取值 | 派生 cross 取值 | policy |
|---|---|---|---|
| `ledger` | `{2,3}` | `{0}` | `two_axes` |
| `billing` | `{2}` | **不存在**（0 条） | **`single_axis`** |

**`billing` 那 3 条 C 标注是错的**：它们的 gold relation 在池中各有 2 个对手，
池结构上是 `relation_within`。标注与派生不一致 **3/12**（`ledger` 是 0/12）。

**`single_axis` 与 `merged` 必须分开**：两者报告轴数都是 1，
但前者是"只有一轴存在"，后者是"两轴同构、合并后仍代表两轴"。
用同一个值会让报告写出"两轴合并"，而事实是没有第二轴可合并。

**F21a 约束下的数据形状**（这是造数据前必须知道的）：

> `cross` 查询存在 <=> 该 subject 至少有一个"池中只有 gold 一条"的 relation。
> 而 F21a 要求 relation 数 ∈ [2, 3]。
> **所以有 cross 轴的 subject，形状必须是"1 个单值 relation + 1–2 个多分支"，
> 总数 ≤ 3。**

| 操作 | 结果 |
|---|---|
| `billing` 新增第 4 个单值 relation | relation 3 → 4 -> **F21a 由绿变红** |
| `billing` 把 3 个多分支中的 1 个改成单值 | 仍是 3 个 -> F21a 保持绿，且产生 cross 轴 |

**v3 走"允许 subject 无 cross 轴"（路 2）**，不为凑 cross 去改 F21a 的上界——
F21a 正是在 v2 里抓到 `ledger` 5 个 relation 的那条门禁。

### 0.1 为什么结果指纹（`47e4785-dirty`）与 frozen tag（`5a55620`）不同

**复算时一定会撞上这个问题，所以先写在这里。**

15 份结果文件是在 `47e4785` 的**工作区**上跑的（因此带 `-dirty`），
而 `dataset-v2-frozen` 指向其后的 `5a55620`。两者相差 3 个 commit。

区间内改了什么（**如实列出，不要以为"只有文档"**）：

| 文件 | 有改动吗 | 影响 |
|---|---|---|
| `evals/run_retrieval.py`（评测入口） | **无** | 评测数字有效 |
| `evals/datasets/*`、`src/**` | **无** | 同上 |
| **`evals/tools/check_v2_dataset.py`** | **有**（加 gates 指纹） | **只影响输出格式，判定不变**（已实测重跑一致） |
| 文档 | 有 | 无影响 |

**复算方式**（二选一）：

```bash
git checkout 47e4785          # 直接用结果文件对应的 commit
# 或确认区间内没碰评测路径：
git diff 47e4785..dataset-v2-frozen -- evals src
#   只应有 evals/tools/check_v2_dataset.py 一处
```

**根因**：`code_version` 混了两件事——commit 与工作区是否干净。
只要跑的时候工作区不干净（这一路几乎每次都是，因为改完就跑、跑完才提交），
它就一定对不上 tag。

→ **v3 待办**：结果文件加 `git_commit`（干净 hash）与 `git_tag`，
把"哪个 commit"和"哪个 tag"分开记。

### 0.3 `results/` 里的 gates 是 tag 时的产物，文案可滞后但判定不可变

F24 的 detail 在 tag **之后**改进过：现在分两段写
`[数据侧通过] ... [结果侧失败] ...`，而 `results/v2-*-gates.json` 里仍是旧文案。

**为什么允许这个不一致**：两个要求互相冲突——

| 要求 | 后果 |
|---|---|
| 结果文件必须对应 tag | 不能重跑 gates |
| detail 要能看出两段 | 必须重跑 gates 才会更新 |

选择**保 tag、保数字、允许文案滞后**，因为：

- 判定完全相同（21/27、24/27，失败项相同）——**重跑验证过**
- 文案滞后不影响任何结论
- 而重跑会让指纹脱离 tag，那是更严重的不一致

**若某天 gates 文件里的 F24 由红变绿（或反过来），那是真问题**，
不是文案滞后。`test_gates_result_f24_detail_may_lag_but_verdict_must_match` 守这条线。

> **`frozen` 不等于合格。** 它表示"这是 v2 的最终版，5 处数据缺陷已登记、已锁定"。
> 5 处是 F13 / F17b / F18 / F21a / F24，见 `docs/reports/v2-what-it-measures.md` §0.1。
> 它们**不修**——修就是改已有数据，而分数已经看过（协议 §1.2）。

> ⚠️ **`billing` 的 A 轴 `SEH@1 = 1.0000` 是保留的实验设计失败（F24），不是成绩。**
> 它看起来像满分，实际含义是"这份数据测不到区分能力"。
> 保留它是为了让"干净的高分可能是设计失败"这个形态可见。


### 0.4 工具选择依据是**样本规模匹配**，不是方法先进性

**这一条来自一次具体的失败**：`bootstrap.py` 的百分位区间在 v2 的样本量上失效。

| 工具 | 在什么规模上可靠 | v3 需要的 n=9–20 |
|---|---|---|
| `proportion_ci`（百分位 bootstrap） | `p` 不接近 0/1，n 足够大 | ❌ `2/2`、`9/9` 坍缩成零宽 |
| `wilson_interval` | **n ≥ 5 稳定** | ✅ |

实测：

```
6/9  bootstrap [0.3333, 1.0000]   ← 下界恰好落在 k/n 网格上，判不通过
     Wilson    [0.3542, 0.8794]   ← 判通过
9/9  bootstrap [1.0000, 1.0000]   ← 零宽，等于没有区间
     Wilson    [0.7008, 1.0000]
```

**`bootstrap.py` 的退化在设计时是已知且有意为之**（docstring 明写"不做平滑"，
因为对"100 条全对"报 [0.97, 1.0] 才是假的不确定性）。问题不在实现，
而在于**它没有声明适用规模**。

所以选 Wilson 的理由不是"它更先进"，而是"它的适用规模匹配"：

> **工具的选择依据是样本规模匹配，不是方法先进性。**


### 0.5 v3 必须先做的选择：区间用什么方法（这是 spec 变更）

`evaluation-harness` 第 91 行的原文是：

> 系统 SHALL 用**配对重采样**计算指标差异的 95% 置信区间

所以 Wilson（解析解，不重采样）**不满足 spec 的字面要求**。

**四个选项，都不能在数据阶段决定**：

| 选项 | 内容 | 代价 |
|---|---|---|
| 甲 | 用 bootstrap，接受小样本退化并说明 | 得到"形式达标但无信息"的区间 |
| 乙 | 改 spec 允许解析解 | spec 变更 |
| 丙 | spec 只要求"给出区间"，不规定方法 | spec 变更，最宽松 |
| **丁** | **双报**：bootstrap 为主（满足字面要求）+ Wilson 为辅（小样本可用） | 报告里多两列 |

**倾向丁**，理由：

- 甲正是这一路最警惕的形态：门禁绿了、要求满足了，但测的东西是空的
  （同 `SEH@5 = 1.000`、`paths_unwired = []`）
- 乙/丙的动机会是"bootstrap 在小样本上退化"——那是**看到结果后改标准**的弱版本
- **丁不改 spec，且两个区间的差异本身是信息**：
  "bootstrap 说 `[0.333, 1.0]` 而 Wilson 说 `[0.354, 0.879]`"这个对照，
  比任一单独区间都更能说明该样本量下区间估计有多不确定

### 双报的判据：用差距标记"bootstrap 是否可信"

**差距本身就是"bootstrap 在这个 n 上是否可信"的指标**——
不需要预先判断 `n` 够不够，数据自己会说。

| 情形 | bootstrap 下界 | Wilson 下界 | 差 | 解读 |
|---|---|---|---|---|
| 6/9 | 0.3333 | 0.3542 | **0.021** | 一致，bootstrap 可用 |
| 9/9 | 1.0000 | 0.7008 | **0.299** | 分歧，bootstrap 坍缩 |
| 2/2 | 1.0000 | 0.3424 | **0.658** | 严重分歧，bootstrap 无意义 |

**报告规则**：

> 报双区间；当两者下界差 **> 0.1** 时，必须标注
> "bootstrap 在此样本量上不可信，以 Wilson 为准"。

这比"选一个方法"更好，因为它把"需要判断 n 够不够"变成了"看一个可观测的量"。

### 抽查 10 个 scenario：不是"A 有测试没标"，也不是"B 没测试"

按能力分层抽 10 个（每能力 2 个），逐条去 `tests/` 找"THEN 的每一段是否都被断言过"。

**判定规则**（先定规则，再看结果）——**五类，不是三类**：

| 类型 | 定义 | 下一步动什么 |
|---|---|---|
| ✅ **直接覆盖** | 有断言直接触碰该行为 | 不用动 |
| 🔒 **间接锁定** | 测试断言了该行为的**后果**，但不解释它 | **补注释**，不是补断言 |
| 🧩 **parametrize 分支** | 多个断言属于同一个测试函数，各自只覆盖一半 | 引用该函数即可，但要知道它是"多分支" |
| ⚠️ **部分覆盖** | THEN 的某几段有断言，其余段没有 | **补断言** |
| ❌ **无覆盖** | 没有任何断言 | **补测试** |

**为什么必须把 🔒 和 ⚠️ 分开**：两者的处置相反。间接锁定**不需要补断言**（删掉逻辑它会红，这是测试的主要目的），它要补的是"为什么 1.0 是对的"这层解释。混成一类会让下一步动作不明确。

### `Test:` 引用列的第三个盲区：它不是"已验证"，是"由谁负责"

`#8` 暴露的问题和"一个测试填给多个 scenario"不同：**parametrize 的多分支算一条测试，还是多条？**

写 `Test: test_known_expressions_map_to_slots` 一条，它其实覆盖了 14 个槽位断言。而某个 scenario 可能只对应其中一项。

所以引用列的语义只能是：

> **"这条 scenario 由哪个测试函数负责"**

而不是：

> ~~"这条 scenario 已被验证"~~

前者是结构事实，后者是语义判断。两者的差别在于：`Test: xxx` 填上之后，检查能断言"xxx 存在"，不能断言"xxx 覆盖了这个 scenario 的每一段"。

### `expected_slot in parsed.slots` 是子集断言，看不见多出来的槽位

`#8` 还暴露一个更隐蔽的问题：那条 parametrize 用的是

```python
assert expected_slot in parsed.slots   # 子集
```

不是相等。所以当解析**多给了槽位**时它仍然绿。

实测：

```
parse_condition("holiday").slots   == {'time:day', 'time:holiday'}
parse_condition("节假日").slots    == {'time:holiday'}
```

原因：`_ALIASES` 里 `"day" → time:day` 是 `"holiday"` 的子串，子串匹配把两个槽位都给了。

**所以 `holiday` 与 `节假日` 这一对"中英对照"实际并不相等，而 4 条 parametrize 全绿。**

| 短别名 | 被它误命中的词 | 结果 |
|---|---|---|
| `开发` (`activity:coding`) | `开发环境` | 同时给 `env:development` |
| `开发` (`activity:coding`) | `功能开发` | 同时给 `activity:feature` |
| `day` (`time:day`) | `holiday` | 同时给 `time:holiday` |

共 **3 对**，全部是"长别名包含短别名、槽位不同"。

> 这是第五类覆盖：**测试断言了"包含"，而 scenario 要求"相等"**。
> 它同时说明为什么"有测试"和"测试通过"都不足以回答"scenario 成立吗"。

### spec 自己举的例子，实测跑不通

`memory-retrieval` 的这条 scenario 原文（`spec.md:163-165`）：

```markdown
#### Scenario: 中英表达归一到同一槽位
- **WHEN** 同一条件以中文与英文分别表达（如"应酬"与"client dinner"）
- **THEN** 归一到相同的槽位键
```

实测：

```
应酬  vs  client dinner   -> condition_match = 0.000
应酬  vs  client_dinner   -> condition_match = 1.000
```

`_ALIASES` 里只有 `client_dinner`（下划线），没有 `client dinner`（空格）。

**spec 用来解释这条规则的例子，是这条规则唯一不成立的形式。**

这比 #8 的判定严重：**如果只按 spec 的例子写测试，测试会红；而写的测试换了例子（`写代码`/`coding`），它不会红。** 于是"这条 scenario 有测试吗"的答案，取决于你用哪个例子去问。

### 修 spec 例子会让一条失败的 scenario 变成通过——而实现没变

这是这一节最重要的一条，因为它长得像"修文档"。

| 状态 | spec 写的例子 | 实测 | scenario |
|---|---|---|---|
| 现在 | `"应酬"` vs `"client dinner"` | **0.000** | 失败 |
| 改例子后 | `"应酬"` vs `"client_dinner"` | **1.000** | 通过 |

**它通过不是因为实现变好了，是因为标准降低了。**

同一种形态在本项目已经出现过三次：

| 位置 | 标准怎么被降低 |
|---|---|
| 协议 §1.2 | 看到分数后不许改数据——防的就是这个 |
| 缺陷 20 | `query_condition` 是答案副本，把条件匹配拉低到"字符串相等" |
| **本条** | **spec 的英文例子从"空格分隔的短语"降到"带下划线的标识符"** |

所以处置顺序必须是：

1. **修 spec 例子**（`client dinner` → `client_dinner`）——便宜、无争议、不动 `src/`
2. **同时登记"子串误命中"为新缺陷（缺陷 23）**——不能让第 1 步造成"这条已经好了"的错觉
3. **修匹配算法**——独立变更，需要设计决策

### 缺陷 23：子串匹配把「误命中」与「多命中」混在一起

`parse_condition` 的匹配是 `if alias.casefold() in folded`（子串包含，不是词边界、不是精确）。

**但"子串匹配坏了"这句话不准确。** 它同时产生两种后果，性质不同：

| 类型 | 定义 | 例子 | 是否错 |
|---|---|---|---|
| **误命中** | 长词里**包含**短别名，但语义上短别名不成立 | `day` 命中 `holiday` | **一定是错的** |
| **多命中** | 两个**不重叠**的别名各自独立命中 | `本地开发` = `本地`+`开发` | **可能都对** |

**实测判据**：看两个命中区间是否重叠。

| 文本 | 命中别名 | 区间 | 重叠？ | 类型 |
|---|---|---|---|---|
| `holiday` | `day` `holiday` | `[4,7)` `[0,7)` | **是**（被包含） | **误命中** |
| `开发环境` | `开发` `开发环境` | `[0,2)` `[0,4)` | **是**（被包含） | **误命中** |
| `功能开发` | `开发` `功能开发` | `[2,4)` `[0,4)` | **是**（被包含） | **误命中** |

### 引用列记录的是会随实现翻转的映射

把上面两件事合起来看：

```
现在：  scenario 用 spec 的例子   -> 红
修词表：scenario 用 spec 的例子   -> 绿（测试名没变）
```

**`Test:` 引用列填的是测试名，而测试的红绿会随实现变化翻转。** 所以那句"引用是结构事实"要再退一步：

> 引用关系是稳定的（测试名不变），
> 但**"这条引用代表通过还是失败"是不稳定的**。
> 引用列能回答"谁负责"，不能回答"现在成立吗"。

### 这个分布推翻了 A/B 二选一

原先是二选一：

- **A**：大部分有测试但没标 → 加引用列，纯记录工作，收益高
- **B**：大部分没测试 → 缺口 200 量级，要么补测试要么承认

实测是**第三种**：**有测试的 8 条里，4 条只覆盖了 THEN 的一部分。**

这个分布决定了两件事：

**1. `Test:` 引用列的真实收益比 A 情况低。**

它不是"把已有的证明写下来"，因为已有的证明只到"一半"。填引用时会出现这样的条目：

```
#### Scenario: 缓存损坏
Test: test_llm_cache.py::test_corrupt_row_is_treated_as_miss
```

引用检查全绿，但这个测试只验证"视为未命中"，**没验证"重新请求"和"记录警告"**——THEN 有三段，断言只覆盖一段。

**2. 一个测试可以支撑多个 scenario 的引用，而检查看不出来。**

引用检查只能断言"这个名字存在"，不能断言"它覆盖了这个 scenario 的每一段"。

### 所以：引用列能保证"有引用"，不能保证"引用覆盖了该 scenario"

**这是必须写下来的一句**：否则下一次会有人以为"加 `Test:` 列就能解决"。

> 引用列能保证"有引用"，不能保证"引用覆盖了该 scenario"。
> 一个测试填给多个 scenario 时，引用检查仍会全绿。
>
> 所以 **"291 → 291 有引用"这个目标，不等于"291 条行为都有验证"**。
> 前者是记录问题，后者是工程问题。

### 更根本的：这个项目的测试是"问题驱动"的，不是"spec 驱动"的

```
370 个 scenario    vs    1322 个测试
```

测试比 scenario 多得多。所以**问题不是"没有测试"，而是"测试和 scenario 之间没有映射关系"**。

而 1322 个测试大多围绕**缺陷、指标、数据结构**写的（29 条 `locked_defect`、各种 `evidence_lock`、一致性检查），不是围绕 scenario 写的。

| 组织方式 | 保证什么 |
|---|---|
| **问题驱动**（现状） | 每个 bug 有回归测试 |
| **spec 驱动**（缺失） | 每条 scenario 有测试 |

所以这不是"补一列元数据"，而是**组织方式的改变**。它必须在变更的 proposal 里说清楚，不能当成格式工作。

### 为什么这次改动 0 条红，而 `condition.py` 有 7 条

差别在于**测试是否引用产品的符号**：

| 测试 | 引用产品的什么 | 改产品会红吗 |
|---|---|---|

**所以"锁代码"的判据是：测试必须引用产品的符号，而不是复制产品的数值。**
引用符号还不够，断言的量也必须真的随它变化——见下。

### 断言类型的选择：结构断言 vs 数值断言

前面把"引用符号但断言有余量 → 仍绿"写成"层 2 没满足"，**这个框架是错的**。
它把两种**目的不同**的断言混成了一种的两种写法。

| 类型 | 写法 | 目的是 | 参数变动时该不该红 |
|---|---|---|---|
| **结构断言** | `assert auth_penalty > advantage` | 锁"关系成立" | **不该**（关系还成立就是没修） |
| **数值断言** | `assert diff == approx(0.1025)` | 锁"参数取值" | **该**（算术变了就要重算） |

**它们的失效条件相反**，所以不是"谁更好"，是"回答不同的问题"。

实测缺陷 19 在 authority 权重下降时两道断言各自何时红
（权重和保持 1.0，base 与 condition 平分剩余）：

| authority | 罚分 | 优势 | 不等式 | 差值 | `== 0.1025` |
|---|---|---|---|---|---|
| 0.25 | 0.2500 | 0.1475 | 成立 | 0.1025 | **是** |
| 0.20 | 0.2000 | 0.1623 | 成立 | 0.0378 | 否 → **数值断言先红** |
| 0.15 | 0.1500 | 0.1770 | **不成立** | −0.0270 | 否 → 结构断言才红 |
| 0.05 | 0.0500 | 0.2065 | 不成立 | −0.1565 | 否 |

**临界点精确值**：不等式失败于 `a > (0.75−a)×0.295/1.0`，即 `a ≈ 0.1709`。

> **0.170849 有两个前提，缺任一个就要重算**：
>
> | 前提 | 值 | 有产品依据吗 |
> |---|---|---|
> | (a) `status` 权重不变 | 0.25 | 是（`uniform` 里就是 0.25） |
> | (b) `base` 与 `condition` **等分**剩余权重 | 各 50% | **没有**——`spec` 从未规定两者相等 |
>
> 通式（不假设等分）：
>
> ```
> 设 k = base_share × d_base + (1 − base_share) × d_cond
> crit = (1 − w_status) × k / (1 + k)
> ```
>
> 当 `base_share = 0.5` 时化简为 `(1 − w_status) × S / (2 + S)`，`S = d_base + d_cond = 0.59`，
> 即 `0.75 × 0.59 / 2.59 = 0.4425 / 2.59 = 0.170849`。
>
> 前提变动时临界点会移动（实测）：
>
> | 改动 | 新临界点 |
> |---|---|
> | `w_status = 0.20` | 0.182239 |
> | `w_status = 0.30` | 0.159459 |
> | `w_status = 0.35` | 0.148069 |
> | `base_share = 0.6` | 0.151914 |
> | `base_share = 0.4` | 0.188623 |
>
> **而缺陷 19 的判据不受影响**——它问的是"auth 罚分能否推翻 base+cond"，
> 只要 `auth` 权重没降下来，缺陷就在。`0.170849` 只是它在当前权重下的取值。
>
> 而这个前提最可能被 v3 动到：`spec` 没规定 `base == condition`，
> 调这两个的分配是改权重时最自然的动作。

### 这一层不是"引用 vs 抄写"的第五次

前四次的共同点是"用一个不更新的来源代替会变的来源"：

| # | 来源 | 错误 |
|---|---|---|
| 1 | 字面量 `0.25` | 测试抄常量 |
| 2 | 记忆 | 差值 0.1016 |
| 3 | 口径 | 41 vs 39 |
| 4 | 假设 | `base_share = 0.5` |

**而 `0.170849` 三者都不是**：它从产品权重算出来、有测试重算、与文档逐位一致。
三道检查全过，而它仍然是错的——**不是数值错，是用途错**。

| 用它回答 | 对不对 |
|---|---|
| "当前缺陷的临界点是多少" | ✅ 对 |
| "v3 该把 authority 降到多少" | ❌ **错，差 2.76 倍** |

**而第二问才是它被写进文档的目的。**

### 由此补一条判据

> **如果结论是"某参数必须低于 X"，那 X 必须是所有可能情形下的下确界，
> 而不是某一种情形下的临界值。**

项目里已有先例：`SEH@5` 的随机基线是逐查询算再平均（`v2_baselines.axis_baseline`），
不是"平均池大小套公式"——同一个道理：**一个代表值会掩盖分布的宽度。**

**所以数值断言早红，结构断言晚红。** 而"晚"在这里有代价：
authority 从 0.25 降到 0.20 时，罚分已经不再"恰好"推翻优势，
只是还大于优势——**缺陷被削弱但没被修**，结构断言看不见。

### 但 `0.170849` 是个点，而"该降到多少"要的是下确界

上面那个 0.170849 是 `base_share = 0.5` 时的值。而**安全阈值必须取所有分配下的下确界**。

`crit` 对 `base_share` **单调递减**（`k/(1+k)` 关于 `k` 单调增，而 `k` 随 `share` 线性减），
所以对 `base_share` 的极值在端点：

| `base_share` | `crit` | 含义 |
|---|---|---|
| **0.0** | **0.250000** | 全给 condition（`d_cond = 0.50` 大）→ 上确界 |
| 0.5 | 0.170849 | 等分（**文档原先只写了这一个**） |
| **1.0** | **0.061927** | 全给 base（`d_base = 0.09` 小）→ 对 `base_share` 的下确界 |

**闭式**：`crit = (1 − w_status) × d_base / (1 + d_base)`

在 `w_status = 0.25` 下：`0.75 × 0.09 / 1.09 = 0.061927`

**后果很具体**：

| 读到什么 | 会得出什么结论 | 实际 |
|---|---|---|
| "临界点是 0.1709" | 降到 0.15 就安全 | 在 `base_share=1` 时 **0.15 > 0.062，缺陷仍在** |

实测三种分配下的 `authority = 0.15`：

```
base_share=0.0  crit=0.250000  安全
base_share=0.5  crit=0.170849  安全
base_share=1.0  crit=0.061927  **不安全（缺陷仍在）**
```

**点估计让安全区看起来是 `authority < 0.1709`，实际是 `authority < 0.0619`——差 2.76 倍。**

### 但这个下确界只对 `base_share` 取，`w_status` 仍是固定的

`0.061927` 也通过了三道检查：从产品常量算出、有测试重算、与文档逐位一致。
**它仍然只对一个变量取了下确界。**

`w_status` 同样是可调参数（它就是 `uniform.status`），而它在公式里是**乘性**的：

```
crit = (1 − w_status) × k / (1 + k)
```

扫 `w_status`（`base_share = 1`，最不利分配）：

| `w_status` | `crit` | `authority = 0.05` 安全吗 |
|---|---|---|
| 0.20 | 0.066055 | 是 |
| **0.25** | **0.061927** | 是 ← 文档的前提 |
| 0.30 | 0.057798 | 是 |
| 0.35 | 0.053670 | 是 |
| **0.394444** | **0.050000** | **临界** |
| 0.40 | 0.049541 | **否** |
| 0.50 | 0.041284 | 否 |

**精确临界值**：`w_status* = 1 − 0.05 / (d_base/(1+d_base)) = 1 − 0.05/0.082569 = 0.394444`

**所以 0.05 只在 `w_status < 0.394444` 时安全，不是无条件安全。**

### 联合下确界是 0——不存在固定阈值

`(1 − w_status)` 可以任意小，所以：

```
w_status=0.25 -> 0.061927
w_status=0.60 -> 0.033028
w_status=0.80 -> 0.016514
w_status=0.95 -> 0.004128
w_status=1.00 -> 0
```

**在"所有可能的权重分配"这个论域里，不存在一个固定的 `authority` 阈值能保证安全。**
任何正数都能被某个 `w_status` 打败。

**而"不存在"本身是一个结论，且比"存在但不能用"更诚实。**

### 三个变量里，只有 `d_base` 不是配置也不是常量

式子是 `w.authority × auth_gap > w.base × d_base + w.condition × d_cond`。
把每个符号查一遍来源：

| 符号 | 值 | 性质 | 能写进文档固定住吗 |
|---|---|---|---|
| `auth_gap` | 1.0 − 0.0 | **常量**（`_AUTHORITY_SCORE` 两端点差） | ✅ |
| `d_cond` | 1.0 − 0.5 | **常量**（`condition_match` 的中性值，一边没说条件） | ✅ |
| `w.*` | 各 0.25 | **配置**（`PREREGISTERED_WEIGHTS`） | ✅ 写明前提 |
| `base_share` | 0.5 | **假设**（`spec` 未规定 `base == condition`） | ✅ 写明前提 |
| **`d_base`** | **0.09（q4）** | **运行时算出来的检索分差，逐 case 不同** | ❌ |

`d_base = 1.000 − 0.910`，其中 `1.000` 是 gold 归一化分（恒为 1），
`0.910` 是**某条 case 里最强竞争者的分数**（`c4-retrieval.md:341` 第 1 名 `pytest -q`）。

**所以前四个可以"在文档里固定"或"写明前提"，`d_base` 不行——它随数据变。**

### 方向容易搞反：`d_base` 越大，缺陷越**容易**存在

gold 领先越多，需要越大的 auth 罚分才能翻盘。所以**最容易被推翻的是 `d_base` 最小的那条 case**。

在 `w.base = w.condition = 0.25` 固定时：

| `d_base` | 需要 `authority >` |
|---|---|
| 0.000 | 0.1250 |
| 0.090（q4） | 0.1475 |
| 0.500 | 0.2500 |

而 `0.05 < 0.1250`——**所以在"base/cond 权重不变"的前提下，0.05 对任何 `d_base` 都安全。**

### "降 authority"必须把权重分给别人，而分给谁决定边界

`RerankWeights` 要求四个权重和为 1，所以"只降 authority"在实现上不成立。

**q4 的对决**（实测特征，`ledger-q4`）：

```
gold       = ledger-oncall-4   cond=1.00  auth=0.00  status=1.00
竞争者     = ledger-pkg-1      cond=0.50  auth=1.00  status=1.00
```

**竞争者不是 `oncall-3`（`cond=0.00`）——`pkg-1` 的 `cond=0.50` 让它在加权后更高。**
gold 赢的条件：

```
w_base × d_base + w_condition × 0.50 > w_authority × 1.00
```

（status 项两边都是 1.00，抵消。）

三种分法：

| 情形 | 公式 | `d_base=0`（下界） | `d_base=0.09`（q4 实测） | 前提自洽？ |
|---|---|---|---|---|
| **A** 给 `status` | `0.25×(d_base+0.5)` | **0.1250** | **0.1475** | ✅ |
| **B** 平分 | `0.375k/(1+k/2)`，`k=d_base+0.5` | **0.1500** | **0.1708** | ✅ |
| **C** `condition` 归零 | `0.75×d_base/(1+d_base)` | **0.0000** | 0.0619 | ❌ |

三档都对 `d_base` **单调递增**（0→1 扫 1000 点）,所以下确界在 `d_base=0`。

### 结论：只有 A 和 B 是候选，C 的前提与缺陷本身矛盾

| 情形 | 下确界 | `0.05` 安全 | 是否候选 |
|---|---|---|---|
| A | 0.1250 | ✅ | ✅ |
| B | 0.1500 | ✅ | ✅ |
| **C** | **0** | ❌ | ❌ **前提不自洽** |

**C 不是"更保守的方案"，是错的方案**：它要求 `w_condition = 0`，而那会抹掉
`q4` 赖以成立的那 `0.125` 优势。用一个消掉缺陷成因的设定去讨论"缺陷是否被修"，
是循环论证。

**所以"`authority` 降到 0.05"在 A/B 下都安全，而下界是 0.125（A）与 0.150（B）。**

### 但 `billing` 永久失败，与三档都无关

实测：`billing` 的 `c1/c2/c3` 在 `authority` 从 0.25 降到 0.0 时**始终失败**。

原因：`billing` 没有 `third_party`（0/9），所以 `auth_gap ≡ 0`。
**缺陷 19 在 `billing` 上不可触发——降 `authority` 不改变这三条的名次。**

这是"缺陷的触发条件"问题，不是"阈值该取多少"问题。两者不能混。

### 穷举：`a = 0.05` 时，多大比例的参数组合下缺陷仍在

扫 `w_base ∈ [0, 0.95]`、`w_cond ∈ [0, 0.95]`、`d_base ∈ [0, 0.5]`（41×41×21 网格）：

```
缺陷仍存在：975 / 18081 = 5.4%
```

**所以"0.05 安全"不是无条件的，但失败区域只有 5.4%——而且集中在 `w_cond` 很小的一端。**

### 正确表述：不是阈值，是逐 case 判据

文档之前给的是"一个数，照着设"。而实测表明这个数的适用范围依赖具体 case 的 `d_base`。

**所以正确形式是判据，不是阈值**：

> 对每条 case，若
> `w.authority × auth_gap > w.base × d_base + w.condition × d_cond`
> 则该 case 上权威罚分能推翻检索+条件优势——**缺陷 19 在该 case 上成立**。

要"修好"缺陷 19，需要使**没有任何一条 case 满足**这个不等式。
而那需要扫全部 case 的 `d_base`，并取其中的最小者——**不是 q4 的 0.09**。

**注意方向的修正**：`d_base` 越小，缺陷越容易存在（gold 领先少也需要更小的罚分就翻盘）。
所以要求的是 `a < min(a_crit(d_base))`，即按**最小的 `d_base`** 取界，不是最大的。

### 所以正确表述是"条件安全"，而且要写明是对哪条 case

**三层前提，缺一不可**：

| # | 前提 | 性质 |
|---|---|---|
| (a) | `status` 权重 = 0.25 | 配置 |
| (b) | `base/condition` 的分配已取最不利（`base_share`） | 假设 |
| **(c)** | **该 case 的 `d_base` 落在使边界低于 `authority` 的区间内** | **数据属性** |

**(c) 是最隐蔽的**：它不是产品参数，是运行时算出来的检索差距。
换一个 `d_base = 0.02` 的 case，情形 C 的边界降到 `0.0147`，`0.05 > 0.0147`，缺陷在该 case 上仍然存在。

**所以"`authority = 0.05` 是安全的"这句话，严格说只能表述为**：

> 在 `status = 0.25`、权重分配为情形 A/B、且
> `d_base > 0.0714`（情形 C）或任意 `d_base`（情形 A/B）时，`0.05` 不会让缺陷 19 成立。

**若 v3 要改权重，不能只降 `authority`——必须联合声明四个权重的取值，
并扫全部 case 的 `d_base` 后重算。**

**共同点是都没问"这个符号可调吗、逐 case 变吗"。**

**恰恰是"有对应物"的那个变量，最容易被认为已经处理过了。**

### 判据要补到最后一句

> 如果结论是"某参数必须低于 X"，那 X 必须是**所有可调参数最不利组合**下的下确界。

而实测表明：当可调参数包含 `status` 权重时，这个下确界是 **0**——
也就是说**不存在一个固定阈值**。

**而"不存在"也是一个结论。**

项目里已有同类先例：`SEH@5` 的随机基线是逐查询算再平均（`v2_baselines.axis_baseline`），
不是"平均池大小套公式"——同一个道理：**一个代表值会掩盖分布的宽度。**

### 所以"降到 0.05 以下"这个建议值是对的，但理由原来写错了

```
0.05 < infimum 0.061927  ->  True
```

**所以 0.05 对任何 `base/condition` 分配都安全。**

但若把理由写成"0.05 < 0.17"，读者会以为降到 0.10 也行——而 `0.10 > 0.062`，
在极端分配下缺陷仍然存在。

**真实依据是"0.05 < 下确界 0.062"，不是"0.05 < 某个临界点"。**


### 但数值断言也有反方向的代价

它会因为**与缺陷无关**的权重调整而红。例如 base 0.25→0.26、condition 0.25→0.24
（和仍为 1.0）：

```
advantage = 0.26 × 0.09 + 0.24 × 0.50 = 0.0234 + 0.1200 = 0.1434
diff      = 0.25 − 0.1434 = 0.1066     ≠ 0.1025
```

数值断言红——**而缺陷 19 一点没变**（`0.25 > 0.1434` 仍成立，结构断言绿）。

所以完整的表述是：

| 断言 | 红的含义 | 误报场景 |
|---|---|---|
| 结构 | **缺陷被修了** | 缺陷被削弱但未修时漏报 |
| 数值 | **算术变了，报告需重算** | 无关权重调整时误报 |

**两者都留，但红的时候要读不同的信息。** 当前缺陷 19 的测试两者都有：

```
assert advantage == approx(0.1475)        # 数值：报告里的数字
assert auth_penalty > advantage           # 结构：缺陷存在
assert auth_penalty - advantage == approx(0.1025)   # 数值：净差
```

### 缺陷 19/21 为什么需要数值断言

因为它们的结论**是关于特定参数取值的**：

> "在 `uniform` 权重（四特征各 0.25）下，auth 的罚分恰好能推翻 base+cond 的双重优势。"

而如果只写结构断言，它测的其实是另一个命题——"auth 罚分**总能**推翻 base+cond"——
那个命题在 authority 降到 0.17 以下就不成立，而"降到 0.05 修好"之前一直成立。

**结构断言会把"部分削弱"读成"还没修"。**

**所以本节现在有一条测试**（`test_section_0_8_arithmetic_numbers_are_recomputable`），

1. 从 `d_base`/`d_cond` 重算 0.1475 / 0.1025 / 0.1516 / 0.0984 / 0.1434 / 0.1066 / 0.170849
2. **从本文档里用正则抓出这些数字，与重算结果比对**

第 2 条是关键：只验算不读文档，文档写错了测试也不会红。

#### 为什么账本必须单列

`retrieval-run-count.json` 是**唯一一个"本来就不该有指纹"的文件**——
它记录"哪个文件跑了几次"（31 个键，值是次数），那不是运行结果。

**若把它算进"无指纹的结果文件"，任何"给全部结果补指纹"的批量动作都会去改它。**
而它的格式被 3 处依赖：

```
run_retrieval.py:829          _bump_run_count 读写它
test_report_consistency       test_run_count_is_recorded 等 2 处
test_archive_evidence         断言归档 run_count == 1
```

**给它加字段会破坏这些测试。**

#### 第 D 类：它看起来像有指纹

`code_version` 与 `code_diff_hash` 是**两个独立可用**的字段：

| `version` | `hash` | 能回答什么 |
|---|---|---|
| ✅ | ✅ | 哪个 commit **+ 工作区是否干净** |
| **✅** | **❌** | **只有 commit，不知有无未提交改动** |
| ❌ | ❌ | 完全不可追溯 |

**判据是"两个字段都齐才算可追溯"，不是"有 version 就算"。**

#### 由此补一条：`per_case` 没存特征分

v3 若要离线复算"改权重后某条 case 会怎样"，需要逐条的四特征分。
而实测 `per_case` 只有：

```
rank_after_rerank, rerank_order_tags, pool_vectors, dedup_input_scores,
tie_at_top1, tie_at_k_boundary, pool_tag_meta, ...
```

**没有 `base` / `condition` / `authority` / `status` 的逐条取值。**

> **v3 前置缺口**：`per_case` 必须存四个特征分。否则每次问"权重降一点会怎样"
> 都得重跑一次，而 v2 已冻结、重跑会产第二批指纹。

**九类，覆盖全部 48 个文件。** 实测九类之间**无重复命中**，
所以这个加总是干净的分类计数，不是重复计数。

#### "九"这个数字的来源：它也依赖一份预设的字段清单

原先写的是"九来自结构签名的自然分组"。**这个说法过强了。**

签名的定义里有一项：

```
首个 list 字段名（per_case / samples / checks / rows / cases / 无）
```

**这五个名字是从九类表里取来的。** 所以这不是"规则让数据自己分组"，
而是"先有九类，再写一条规则让结果等于九"。

#### 实测：换一种签名写法，分组数就变

| 签名写法 | 分组数 |
|---|---|
| 预先写入 5 个字段名，取首个匹配 | **9** |
| **所有 list 字段名的集合**（不预设名字） | **12** |
| **只保留"有无 list 字段"这一位** | **5** |

**同一个数据集，三种签名，三个答案。**

12 组的来源是多字段文件被拆开了：

```
('dict', ('paths_enabled','paths_unwired','per_case'), ...)   20
('dict', ('per_case',), ...)                                  11
('dict', ('absent_classes','low_support_classes','per_case'), ...)  4
('dict', ('low_support_classes','per_case'), ...)              1
```

**这 4 组的文件其实都是"有 per_case 的评测结果"**，只是附属 list 字段不同。
9 类的定义把它们合并了，而"取首个匹配"这个规则恰好也合并了它们——
**但那是我的规则和我的类表同源的结果，不是数据的自然结构。**

#### 所以"九"是什么

**它是"按我写的这条规则分组得到的组数"，而那条规则里有一份从九类表取来的字段清单。**

| 说法 | 是否成立 |
|---|---|
| "48 个文件分成 9 类" | ✅ 成立（关于快照，按给定规则） |
| "结构签名自然分成 9 组" | ❌ **不成立**（换签名就不是 9） |
| "结果文件有 9 种形态" | ⚠️ 取决于怎么定义"形态" |

**这比原来的说法弱，但它是真的。**

#### 那"九"还有没有价值

有，但价值变了：

| 原来的理由 | 实际的理由 |
|---|---|
| 规则算出九组，所以九有依据 | **分组规则与九类表一致，所以表是自洽的** |

**自洽 ≠ 有依据。** 一张表与生成它的规则一致，只说明表没写错，
不说明类的划分是最优的或唯一的。

#### 但两种新增情形的处置仍然不同

这个区分不依赖"九是否自然"，它只依赖"签名是否变化"：

| 情形 | 签名组数 | 类数断言 |
|---|---|---|
| 新文件签名与已有组相同 | 不变 | 绿 |
| 新文件签名与所有组都不同 | +1 | 红 |

**实测已验证**（见 `test_result_shapes.py`）：加一个 `per_case` 文件，
类数断言绿、精确字典红；加一个 `timeline` 字段的文件，类数断言红。

**所以"类数断言 vs 精确字典"这个拆分是有效的，与"九是否自然"无关。**

#### 第 9 类是怎么被发现的

我原先写的是「八类，覆盖 48 个文件」，而八类的数值加总是 **47**。

**差的 1 个我是在被指出后才去查的**，而 `48 - 47 = 1` 这个减法我本可以自己做。

`c4-query-leak-ablation.json` 的结构：

```
顶层键: caveat, purpose, k, generated,
        variants                        (dict: dev/test/independent)
        feature_variance_v0             (dict: dev/test/independent)
        distractor_sampling             (dict: 指标)
        condition_supplied_vs_extracted (dict: 指标)
```

**它的 `variants` 是 `{variant_name: {指标...}}`，不是 `{case_id: rank}`**，
所以它既不落入第 6 类，也不落入顶层 list 或账本。

**而它是缺陷 1（`query == gold` 原文）的消融数据来源**，存着
抹掉 gold 原文后分数掉多少的三个数字。只认前 8 类的扫描脚本会漏掉它。

#### 第 6 行最关键：消融的逐条名次存成嵌套 dict

```
v2-sample-condition-ablation.json
  with_condition:    {"ledger-q1": 1, "ledger-q2": 1, "ledger-q4": 6, ...}
  without_condition: {...}
```

**这是 `{case_id: rank}`，与 `per_case` 里的 `rank_after_rerank` 是同一类信息，
只是形状不同。**

**所以"拿逐条名次"的脚本要处理两种形状，不是两种字段名。**

而这三个消融文件恰好是 §0.5 与缺陷 19/21 结论的输入——
**只认 5 种 list 字段名的脚本会跳过它们，且不会报错。**

#### 一个正在发生的例子

我第一版扫描脚本只认 list 字段，覆盖了 43 个文件，
而我在**没有检查"48 − 43 = 5 去了哪"**的情况下就写了结论。

**"覆盖了多少"这个数字，只有在和总数比对时才有意义。**

#### 这是"混淆"的第八次，而且它连"用什么判据"都错了

| # | 标签/类别 | 盖住或混入的两种 |

| 7 | "无指纹" | 有 version 无 hash / 两字段都缺 |

**第 8 次比前七次多一层**：前七次是"标签覆盖不全"，

#### 实测成立的三条

**1. 无 gold 与 skipped 互斥**

`has_gold=False` 且带 `skipped` 字段的组合：**空**。
代码侧印证：无 gold 是提前返回，那个分支里没有 `skipped`。

**2. `skipped=True` 只出现在 10 键**

52 条全部是 `has_gold=True` + 10 键，且只在两个池模式文件：

```
retrieval-independent-uniform-nodedup-pooladversarial.json
retrieval-independent-uniform-nodedup-poolsame_relation.json
```

**3. 主干是 7 → 8 → 13 → 20 → 25，旁支是 8 → 10**

| 步 | 包含关系 |
|---|---|
| 7 ⊂ 8 | ✅ |
| 8 ⊂ 13 | ✅ |
| 13 ⊂ 20 | ✅ |
| 20 ⊂ 25 | ✅ |
| 8 ⊂ 10 | ✅（旁支起点） |
| 10 ⊄ 13 | ❌ **所以 10 不在主干上** |

**`skip_reason` / `skipped` 不是"演化出来的字段"，是"另一种记录"的标记。**
把它们当链条上一步，会让人以为"13 键版本删掉了 skipped"——
而**主干从来没有它**。

> **"删掉了什么"和"从来没有"是两件事。**

#### 最关键的一处：8 键有两个来源，且在同一个文件里

| `has_gold` | 记录数 | 文件数 |
|---|---|---|
| `False` | 91 | 17 |
| `True` | 206 | 8 |

**而 `has_gold=True` 的那 8 个文件，全部包含在 `has_gold=False` 的 17 个文件里。**

也就是说，8 键文件里，**同一个文件同时产生两种记录**：

```
完整记录（8 键，has_gold=True）   -> "该版本的完整格式"
无 gold 记录（8 键，has_gold=False） -> "无 gold 分支的格式"
```

**所以"8 键"甚至不是"一种格式"，它是两个来源产生的同一个键集合。**

原因：`run_retrieval` 的无 gold 提前返回**手写了 8 个字段**，
而最早那版完整记录**也只有这 8 个字段**。

> **两个来源产生同一个形状——这是最难发现的一类，因为形状检查永远不会红。**

#### 键数的等式：`key_count = f(code_version, branch)`

`branch ∈ {no_gold, skipped, normal}`：

| 分支 | 判据 |
|---|---|
| `no_gold` | `has_gold is False` |
| `skipped` | `skipped is True` |
| `normal` | 其余 |

**在指纹可用的文件上，这个函数是 1:1 的**（**6 个组合，0 例外**）：

| `code_version` | 分支 | 键数 | 条数 | 按哪个口径可归因 |
|---|---|---|---|---|
| `47e4785-dirty` | `normal` | 25 | 132 | 两个 |
| `5e8a3d6` | `no_gold` | 8 | 7 | **仅格式分析** |
| `5e8a3d6` | `normal` | 20 | 33 | **仅格式分析** |
| `899e2b6-dirty` | `no_gold` | 8 | 28 | 两个 |
| `899e2b6-dirty` | `normal` | 20 | 132 | 两个 |
| `8b1b600-dirty` | `normal` | 20 | 24 | 两个 |

**6 个组合里有 2 个只对"格式分析"可归因**——`5e8a3d6` 缺 `code_diff_hash`，
所以它能证明 commit、不能证明工作区干净。**而键数只需要 commit。**

### 两个覆盖率，因为"可追溯"对两个用途要求不同

| 用途 | 需要什么 | 可归因文件 | 覆盖率 |
|---|---|---|---|
| **格式分析**（键数） | 只需 commit | **18** | **50%** |
| **数字复算**（指标准确） | commit **+** 工作区是否干净 | **17** | **47%** |

差异只有 1 个文件：`5e8a3d6`（有 `code_version`、无 `code_diff_hash`）。

**键数由代码逻辑决定，`-dirty` 与否不影响字段表；而数字会受影响。**
所以它能为格式作证，不能为数字作证。

**把同一批数据对一个用途的覆盖率，当成对所有用途的覆盖率——这是本轮第七次"数字 + 用途 + 分母"没同时写明。**

### 但"无指纹"不等于"不可归因"

**一个属性在无指纹数据上能否归因，取决于它由什么决定：**

| 分支 | 键数由什么决定 | `<none>` 下的分布 | 可归因 |
|---|---|---|---|
| **`skipped`** | **硬编码 10** | **`{10: 52}` 单一** | ✅ **能** |
| `no_gold` | 版本 | `{7: 4, 8: 56}` 两种 | ❌ |
| `normal` | 版本 | `{6,7,8,12,13,20}` 六种 | ❌ |

**所以"25 个文件无指纹所以无法归因"这个说法过强**——
只有**依赖版本**的属性失去归因能力，而硬编码的分支不会。

### 覆盖率的另一半是无法补的

19 个文件（36 − 17）没有完整指纹。**它们的代码状态无法从产物反推**——
没有 `code_version` 就没有线索。所以 50% / 47% 不是"暂时没做"，是**上限**。

**这与 §0.1 那条是同一个问题的第三次出现**：

| 次 | 表现 |
|---|---|
| 1 | 11 份结果混三次代码状态 |
| 2 | 消融文件无指纹 |
| 3 | **19 个评测文件无法归因，格式分析只剩 50%** |

#### 修正后的事实

| 说法 | 状态 |
|---|---|
| 检索评测有 5 种主干格式（7/8/13/20/25 键），4 次纯增字段 | ✅ |
| 旁支 1 种（10 键，含 `skipped`），只 2 个文件 | ✅ |
| `has_gold=False` 的记录键数**跟随文件版本**（7 或 8），不是固定 8 | ✅ |
| `has_gold=False` 与 `skipped` 互斥 | ✅ |
| "三个正交变量" | ❌ 已推翻 |

**而"键数"不是独立维度**——它是"文件版本"的属性，
无 gold 分支只是**复用了同版本的键集合**（因为它手写了 8 个字段）。

#### 为什么 15 这个数字特别容易被误引

因为它在 HANDOFF **顶部摘要**里，而摘要的作用就是"让人不必往下读"。
一个只覆盖 15/48（31%）的数字放在摘要里，读者会把它当成全部。

**所以第 14 行现在明写"只强制这 15 份"，并指向本节。**

### 第 D 类最危险：它看起来像有指纹

`code_version` 与 `code_diff_hash` 是**两个独立可用**的字段：

| `version` | `hash` | 能回答什么 |
|---|---|---|
| ✅ | ✅ | 哪个 commit **+ 工作区是否干净** |
| **✅** | **❌** | **只有 commit，不知有无未提交改动** |
| ❌ | ❌ | 完全不可追溯 |

**"无指纹"这个标签盖住了第 2、3 两种状态**，而第 2 种会被人当成"有指纹"。
判据应该是**两个字段都齐才算可追溯**，而不是"有 version 就算"。

### 这是"一个标签盖住两种东西"的第七次

### 一个绕过检查的文件名，比一个失败的检查更难发现

### 0.9 数字的三层防护，以及各层抓不到什么

这一轮出现了 **8 次"分类错误"** 与 **5 次"数字错误"**。它们不是同一类，
而防护手段也不同。

#### 层 1：数字必须有可复算载体

**做什么**：任何进入文档的数字，必须有一条测试从**源头**重算它。

**这层是主线**，因为大多数错误是"数字从来没被算过"：

| 错误 | 能不能被层 1 抓住 |
|---|---|
| `0.1016`（实为 `0.1066`） | ✅ |
| `4` 个有效特征（实为 `3`） | ✅ |
| `15` 份统一指纹（只是子集） | ✅ |
| `d_cond = 1.0`（实为 `0.5`） | ✅ |
| **41 vs 39（口径）** | ❌ 那是对"数什么"的分歧，不是算错 |

#### 层 2：文档里的数字必须被读回比对

**做什么**：测试不仅从源头算，还要**把文档里的数字读回来**比。

**这层只是补一道**，而且我做了三次、**三次都是第一次忘了做**：

| 场景 | 第一次的结果 |
|---|---|
| `test_locked_defect_collected_count` | 断言写死 `35`，文档改 34 仍绿 |
| 算术可复算测试 | 只验算不读文档，文档改回 `0.1016` 仍绿 |
| 五类分布测试 | `expected` 是测试里的字面量，文档改 14 仍绿 |

**共同形态**：测试算得对，但它算的是"我以为文档写了什么"，不是"文档写了什么"。

#### 层 3：推导里的每个符号，问"可调吗 / 逐 case 变吗"

**做什么**：把结论涉及的符号逐个列出来，问三件事：

1. 它是常量、配置、假设，还是**运行时算出来的**？
2. 它逐 case 变吗？
3. 如果它变，结论还成立吗？

**这层没有自动检查，只能靠列清单——而它错得最多。**

| 错误 | 漏掉的符号 | 为什么没被层 1/2 抓住 |
|---|---|---|
| `0.061927` 只是对 `base_share` 的下确界 | `w_status` | 数字本身算对了 |
| `0.170849` 只是点，不是界 | 用途 | 数字本身算对了 |
| `d_cond = 1.0` | 选错对手 | **数字本身"算对了"，只是对手错了** |

**第三条最典型**：`d_cond = 1.0` 是对 `oncall-3` 的正确计算，
而 `oncall-3` 根本不是最强竞争者。**层 1 和层 2 都会通过，因为 1.0 与 1.0 一致。**

#### 三层的能力边界

| 层 | 能抓 | 抓不到 | 可自动化 |
|---|---|---|---|
| 1 | 算错、抄错 | 口径分歧 | ✅ |
| 2 | 文档与计算不一致 | 推导错但数字一致 | ✅ |
| 3 | 符号漏辖、判据选错 | — | ❌ **只能列清单** |

**所以"1419 条测试通过"这句话的含义是**：层 1 和层 2 覆盖的部分都通过了。
**它不覆盖层 3**，而这一轮 8 次错误里有 **5 次是层 3**。

#### 附：这一轮 8 次分类错误的清单

| # | 标签/类别 | 盖住或混入的两种 |
|---|---|---|
| 1 | `path == name + ".jsonl"` | 单文件 / 目录 |
| 2 | "MUST 含符号" | 函数名 / 元组写法 |
| 3 | "有反引号" | 可检查符号 / 非符号 |
| 4 | "spec 有测试" | 函数存在 / 行为符合 |
| 5 | "数据锁" | 纯数据 / 数据×评测代码 |
| 6 | "下确界" | 对 `base_share` / 对 `w_status` |
| 7 | "无指纹" | 有 version 无 hash / 两字段都缺 |
| 8 | "结果文件" | 评测结果 / 账本与分析产物 |

**八次都是通过"数一遍"发现的，不是通过推理。**
而第 8 次还多一层：**判据本身选错了**（用 `per_case` 这个形状代替"是不是评测产物"）。

#### 窄版规则：运行时数值必须标 case id

这一轮 8 次错误里，**3 次是同一个原因**：

| 错误 | 用了哪条 case | 该用哪条 |
|---|---|---|
| `d_cond = 1.0` | `oncall-3`（`cond=0.00`） | `pkg-1`（`cond=0.50`，最强竞争者） |
| `d_base = 0.09` | `q4` | 全池最小者（待 v3 扫） |
| `auth_gap = 1.0` | `q4` | `billing` 是 0 |

**三次都是"选了一条 case，但没写为什么是它"。**

所以规则是窄的，只要求一件事：

> **任何"运行时"数值进文档时，必须写明它取自哪条 case。**

**不做全版**（每个数值结论一张符号表）的理由：40+ 个结论里大多数全是常量，
表里全是"—"。**样板会让人跳过它，而跳过的规则等于没有。**

#### 这条规则现在的状态：结论区内只有 **1** 处运行时数值

实测：把范围限定在**结论区**（§0.8 的符号表那一段），
含"运行时"与数值的行**只有 1 行**——

```
| **`d_base`** | **0.09（q4）** | **运行时算出来的检索分差，逐 case 不同** |
```

**它已经标了 `q4`，所以 0 处违例。**

**这个"1"必须写出来**，否则读者会以为这条规则守着一大片，
而实际上只要那 1 处合规，它就永远是绿的。**绿得没有信息。**

#### 为什么范围要外置，而不是扫全文

扫全文时，**这条规则自己的说明文字也会含"运行时"与数字**，
于是它把自己的描述算成输入。实测：N 从 1 变成 4，
而 3 个增量全是规则自身的文字。

**一条会改变自己输入的检查，比没有检查更糟**——它让"违规数"
随规则写法的变化而变，而读者会以为那个数在描述文档。

所以范围必须由外部常量指定（`CONCLUSION_SECTION_MARKER`），
而不是由内容模式识别。

#### 自检不碰磁盘

验证规则有效用的是**内存里的样例**，不是在文档里造临时违例再删：

```python
assert violations("该值是运行时算出的 d_base = 0.09。")        # 抓得到
assert not violations("该值是运行时算出的 d_base = 0.09（q4）。")  # 不误报
```

**理由是这一路已经出过"变异脚本把产品文件写成 CRLF"的先例**——
手工造违例再还原，是同一模式的第二次。

#### 这条规则抓不到"可调性漏辖"

`w_status` 漏辖（`0.061927` 只是对 `base_share` 的下确界）**不属于这条规则的范围**：

| 错误类型 | 有无正确答案 | 可否检查 |
|---|---|---|
| 运行时量选错 case | ✅ 有（`q4` 的 `d_base` 就是 `0.09`） | ✅ 查"有没有写 case id" |
| 可调性漏辖 | ❌ 没有（问题是"该不该考虑它"） | ❌ 只能列清单 |

**把两者混成一条规则，会让可自动化的部分被不可自动化的部分拖累**——
人看到规则里有做不到的部分，就整体跳过了。

#### 分母缺失，这一轮出现了 4 次

| 次 | 报出的数 | 缺的分母 |
|---|---|---|
| 1 | `41` | 那是 6 个文件的条数，不是 `-m locked_defect` 的收集数（39） |
| 2 | `15 份统一指纹` | 全部结果文件是 48 个 |
| 3 | `5 种字段名` | 覆盖 43/48 |
| 4 | `八类` | 相加 47，总数 48 |

**四次都是"一个数 + 一个范围，而两者不匹配"。**

#### 这个"4"的可穷尽分母是什么

三段各管一件事：

| 说法 | 含义 | 可验证性 |
|---|---|---|
| **4 次** | 本轮对话中**被记录下来的**次数 | ✅ 在这一轮内可查 |
| **≥ 4** | 严格说法：没逐句扫过所有报数的句子 | ✅ 诚实 |
| **这一类错误的全部** | 未发生的错误不会留下记录 | ❌ 不可知 |

**4 的可穷尽分母是「本轮所有"报数"的句子」，而它未被执行。**
所以 **4 是「至少 4」，不是「恰好 4」**。

**若要把 4 变成恰好值**，做法是明确的：把这一轮所有含数字的陈述句列出来，
逐条问「这个数的分母是什么」。**它没被执行，所以 4 保持为下界。**

**而「这一类错误的全部」不可知**——不是因为无法穷举，
是因为口径不同：前两个说法在数「本轮记录」，第三个在数「所有可能发生」。

#### 而这四次里有三次发生在"已经建立了检查"之后

| 次 | 当时已有的检查 |
|---|---|
| 1 | `test_locked_defect_collected_count_matches_the_document` |
| 2 | `test_unified_fingerprint`（只管 15 份） |
| 3 | 无（新写扫描脚本，没有总数比对） |
| 4 | `test_result_shapes` 之前 |

**检查的存在反而让人放松了对分母的敏感度。**

一个通过的检查会制造"这件事已经有人管了"的印象，
而它管的往往只是总数的一部分。

> **每当一个检查通过，要问：它检查了总数里的多少。**

这条比 §0.9 的三层判据更靠上，因为它是**流程层面**的，
而三层判据是**单条结论层面**的。

#### 第 4 次是怎么被发现的

我在 `§0.8` 写了"八类，覆盖 48 个文件"，然后确认那三条 §0.9 断言生效、测试全绿。
**而八类的数值加总是 47。**

`48 - 47 = 1` 这个减法我可以自己做，但**直到被指出才去做**。

**所以"分类表"和"加总校验"必须是同一件事**：
只写分类不写加总，等于不检查穷尽性。

现在 `test_shape_counts_sum_to_total` 同时断言两件事：

```python
assert counts == expected            # 每一类的数量
assert sum(counts.values()) == len(files) == 48   # 加总等于总数
```

**第二个断言是关键**：只写第一个，分类表可以"每类都对，但没有穷尽"。

#### 两套独立判据：能证明什么，不能证明什么

`test_result_shapes.py` 的判据与本文档的九类表格是**按同一逻辑写的**。
若那个逻辑有一处判错，文档与测试会一起错，而彼此一致——所以测试通过。

**这正是"测试和文档共享同一个错误来源"的形态。**

所以新增 `test_result_shapes_two_criteria.py`，用**判据 B** 重算一遍：

| | 判据 A | 判据 B |
|---|---|---|
| 优先级 | list 字段名 → dict → 账本 → 分节 | **账本优先** → list → 条件消融 → 分节 |
| 账本识别 | 键以 `.json` 结尾 **且** 值全 int | **只看值全 int**，不看键名 |
| 分节报告 | 兜底：`any(isinstance(v, (dict, list)))` | **要求 `variants` 键恰为** `{dev,test,independent}` |
| list 字段扫描顺序 | 正序 | **反序** |

**两套判据对 48 个文件给出完全一致的分类。**

### 但这不能证明"分类逻辑本身正确"

**如实记录一个限制**：两套判据虽然路径不同，但**在真实 48 个文件上从不分歧**。

| 能证明 | 不能证明 |
|---|---|
| 分类不依赖某一个判据的**写法** | 分类**逻辑本身**是否正确 |
| 换一种优先级顺序结果不变 | "该有几类"这个前提是否正确 |

**若"该有几类"前提错了（例如某两类本该合并），两套判据会一起错**，
正如文档与单套测试会一起错。

**真正独立于"分类逻辑"的验证只有一种**：拿一个不看本文档、自己数一遍的第三方。
而那不是测试能做的——**所以这条限制只能写下来，不能自动化。**

### 一个可执行的判据

> 任何"分类必须穷尽"的检查，应该有两套**结构不同**的判据，
> 断言它们对同一批对象给出同一分类。
>
> **但这只排除"判据写法"这一层错误，不排除"分类框架"本身的错误。**

两者的区别值得记住：**写法错会被两套判据抓住，框架错不会。**

#### 可执行的部分

三条可以现在就用的检查：

1. **数字进文档前，先写测试**——层 1
2. **测试从文档读回数字**——层 2，写时就加上，不要事后补
3. **出现"N 都是 X"时，先按"什么改动会让它变"分组**——层 3 的最小形式

第 3 条的具体做法见 §0.8 的四步清单。

### 为什么还没修：`blocked_by` 字段

"未修复的缺陷"不等于"能修的缺陷"。清单里 18 条未修复缺陷分三种处置：

| `blocked_by` | 条数 | 含义 | 下一步动作 |
|---|---|---|---|
| `None` | **12** | 待修 | 改代码 |
| `"dataset-frozen"` | **5** | 数据集已冻结 | 换数据，需 v3 或 v2.1 |
| `"needs-design"` | **1** | 修法有多个方案 | 先定方案 |

**为什么不用"能不能修"的分类**：那会让"修不了"的缺陷从清单消失，
而清单的价值正是"还剩多少没修"。

**所以"还剩多少能修"是一个可查询的过滤条件**：

```python
actionable = [d for d, reason in BLOCKED_BY.items() if reason is None]  # 12 条
```

**这不改变 `locked_defect` 的语义**——标记仍然是"锁住现状，修复那刻变红"。
只是"修复"的含义对不同缺陷不同：12 条是改代码，5 条是换数据。

`tests/retrieval/test_locked_defect_manifest.py` 有 5 条测试守着这个字段：
每条未修复缺陷必须声明、取值必须来自固定词表、`dataset-frozen` 集合必须是那 5 条、
`needs-design` 只能是缺陷 23、三组之和必须等于 `DEFECT_TESTS` 的条数。

```
pytest              -> 1486 passed, 1 skipped
ruff / mypy         -> clean
locked_defect       -> 36 条收集（34 个标记，parametrize 展开 2 条）
plan_check          -> 3 条（方案论证，不随修复变红）
evidence_lock       -> 6 条（读 git 归档，只有历史被改写才红）
integrity_check     -> 1 条（工作区归档被覆盖时红，动作是还原）
```

> **`mypy -> clean` 必须带范围**：`pyproject.toml` 里 `files = ["src"]`，
> 且 `evals.*` / `tests.*` 被设了 `ignore_errors = true`。
>
> | 命令 | 实际检查 | 结果 |
> |---|---|---|
> | `mypy`（无参数） | **38 个 src 文件** | clean |
> | `mypy src evals tests` | 232 个文件，但 evals/tests 的错误被**关掉** | 显示 clean，**实为假绿** |
> | 临时删掉 `ignore_errors` | 232 个文件 | **492 个错误**（tests 431 / evals 61） |
>
> **所以报"232 files clean"是错的**。正确说法：src 的 38 个文件 clean，
> evals/tests 的 492 个错误被配置屏蔽。
> 实测：往 tests 里塞一个明显的类型错误，`mypy tests/...` 仍报 `Success`。

**下一步**：v2 作为报告集的工作已完成。若要继续，需要 v3。

**v3 有三个候选，推荐顺序 A → B → C，理由不是"重要性"而是依赖**：

| 序 | 候选 | 为什么在这个位置 |
|---|---|---|
| **A** | **修 A 轴难度** | **阻塞一切能力结论**：现在 `condition` 权重 0.25 让同 relation 内几乎自动满分（billing 1.0000，F24）。在它修好之前，任何"A 轴能力"数字都测不出东西 |
| **B** | 测条件推断 | **依赖 A**：v2 的 `condition` 是领域实体（`华东`、`大客户`），无法从文本推断。若先做 B 而不做 A，新的条件类型仍会被 `query_condition` 直通（缺陷 20）绕过 |
| **C** | B 轴（历史版本） | **有两层阻塞**，不是一个：召回层不返回历史版本（协议 §2.1）+ **池构造层同 key 最多一条（缺陷 13）**。两层都要修 |

**没有 A 就做 B，会重复 v2 的错**：换了条件类型但没堵住直通，结果仍然满分。

**不能先做 C 的理由**：B 轴看起来最独立，但它有**两层阻塞**，
而第二层（缺陷 13，池构造）之前只被记成"丢了 147 条干扰项"，
实际是"同 key 一条都进不来"——即使召回层修好，池里也放不下。

### A/C 两轴的区别不是池大小，是"可利用信号不同"

**这一条纠正了我自己先前的判断**（原以为"去掉 condition 后两轴只剩池大小不同，应该合并"）。
实测表明前提不成立。

| 轴 | 候选与 gold 的关系 | 可用信号 | 实测 |
|---|---|---|---|
| **A** | 同 subject **同 relation**，只在 `condition` / `value` 上不同 | `value`（`relation` 恒定，零信息）+ `condition` | 同 relation 兄弟：ledger 24/24、billing 18/18 |
| **C** | 同 subject **不同 relation** | `relation` + `value` | 异 relation：ledger 22/22、billing 18/24（**75%**） |

`_embedding_text` = `subject + relation + value`。所以：

- **A 轴**：`relation` 恒定 → 该字段零信息，向量只能靠 `value` 区分
- **C 轴**：`relation` 大多不同 → 该字段是可用的区分信号

**但 C 轴是混合候选**：它的竞争集是"同 subject 全部记忆"，
所以**必然包含同 relation 兄弟**。billing 有 3 relation × 3 分支，
C 轴竞争集里 6/24 是同 relation 兄弟（25%）——那部分 `relation` 信号无效。

**因此即使去掉 `condition` 特征，两轴仍测不同的东西**：

```
A 轴 = 同属性多值的选择（relation 恒定）
C 轴 = 跨属性的选择（relation 是主要信号，但有 25% 混合）
```

**不要因为"评分函数相同"就合并两轴**——那会让"同属性 vs 跨属性"这个对照消失，
而它是 A/C 分轴的全部意义。

### billing C 轴 0/3 的归因：三个层次

**两个竞争解释都有部分证据，但只有合起来才完整。**

| 层次 | case | 问题 | 能否修 |
|---|---|---|---|
| **查询设计** | `c1`、`c3` | 查询没提 `value` | ✅ 改查询 |
| **向量能力** | `c2` | 提了 `value` 仍分不开 | ❌ 向量的固有局限 |
| **数据表示** | `c2` | `value` 是 `T+1`/`T+7` 这种短同构串 | ⚠️ **修了就是迁就** |

实测证据：

```
把查询改成含 value（只读探针，不改数据）：
  c1 "国内客户开的发票是人民币吗？"      rank 2 → 1   ✅ 改善
  c2 "北京的分部在哪申报税务？"          rank 2 → 2   ❌ 无变化
  c3 "标准合约的回款要等一天吗？"        rank 3 → 1   ✅ 改善
```

`c2` 的失败是**系统性偏差**不是噪声：

```
连跑 5 次：rank 恒为 2，第 1 名恒为同一条兄弟（d-billing-c2-3）
billing 池 9 条，随机排序下 gold 排第 1 的概率 = 1/9 = 0.111
=> 5/5 稳定输给同一条，不是随机
```

三条同 relation 兄弟的余弦（`c2`）：

| 候选 | 余弦 |
|---|---|
| gold（北京税局） | 0.4351 |
| 上海税局 | **0.4553** ← 赢 |
| 深圳税局 | 0.4338 |

**差 0.02，但方向稳定**——说明有一条稳定的信号指向了错误答案，
而不是"分不开所以随机"。

### 不做的：不要为了"让向量能分"而把 value 写长

**这是本轮最容易写错的一条规范。**

若 v3 规定"同 relation 的 value 不能只差两个字"，会有一个直接后果：

> 真实系统里 `T+1 / T+7 / T+0`、`CNY / USD / EUR`、`华北 / 华东` 这类值**最常见**。
> 数据规范禁止它们，等于让 v3 **系统性避开真实世界最常见的形态**。
> 于是分数会好看，而好看的原因是"数据避开了向量不擅长的部分"。

**这与 C4 的 `SEH@5 = 1.000` 同类：通过设计数据让指标好看。**

正确做法是**承认向量的边界**，并写进报告：

> 向量在"短同构串"上区分度不足（实测余弦差 < 0.02，且方向可能稳定错误）。
> 遇到这类查询需要**精确匹配**（字段级 / 枚举），而不是指望语义相似度。

**这条比"改数据"有用**，因为它指向一个真实的产品决策：
什么时候该用向量，什么时候该用精确匹配。

### A 的第一步是改装置，不是改数据

**这一条是从实测推翻的一个方案。**

原先的想法是"造 base 分接近的干扰项，看 condition 的 0.25 是否还赢"。
实测不可行，因为**缺陷 13 让同 key 的干扰项一条都进不了池**：

```
_key = (owner, scope, subject, relation, condition)   # 不含 value
build_pool(gold, [同 condition 的 A, B]) -> 池大小 1，只剩 gold
```

三条约束合起来，A 轴满分**无法靠造数据消除**：

| # | 约束 | 后果 |
|---|---|---|
| 1 | 每条 A 轴查询都要指定 `query_condition` | — |
| 2 | 而它必须等于 `gold.condition`，否则 gold 在 condition 上就输了 | 等于则 `condition_match = 1.00` |
| 3 | base 分要 > 0.25 才能让 condition 不决定胜负，而 base 分由 value 决定，同 key 的 value 相近项进不了池 | **base 差 < 0.25 是结构性的** |

所以 v3 的第一步是**改装置**（三选一），不是改数据：

| 选项 | 做法 | 代价 |
|---|---|---|
| **a** | 部分匹配：`condition_match` 改成"槽位有交集即得分" | 要重设计槽位（"华东"和"华北"需共同父槽位 `region`） |
| **b** | 文本推断：从查询文本抽条件 | 需要抽取器 + "杭州 → 华东"这类世界知识 |
| **c** | 不参与排序：去掉 `condition` 特征，只做召回过滤 | 简单诚实，但 A 轴与 C 轴的区别消失 |

### v3 的装置选项（待变更确认）

| 选项 | 做法 | 数据侧成本 | 查询侧成本 | 代价 |
|---|---|---|---|---|
| **a** | 部分匹配：`condition_match` 改成"槽位有交集即得分" | 19 个值 → 7 个槽位（实测可分：`region`/`customer`/`time`/`env`/`activity`/`scale`/`contract`） | **查询文本里的"杭州"要落到 `region:east`** | 需要"杭州 → 华东"这类世界知识 |
| **b** | 文本推断：从查询文本抽条件 | 同 a | 同 a，外加抽取器（`src/`） | 同 a |
| **c** | 不参与排序：去掉 `condition` 特征 | **0** | **0** | A 轴退化为"同 relation 多值选择"，与 C 轴的差别只剩 relation 信号 |

**倾向 c，理由三条**：

1. **a 与 b 的差别比看起来小**——两者都要求"查询文本指向条件值"。
   a 是"查询侧也用槽位匹配"，b 是"查询侧从文本抽槽位"，
   而 **v2 的 implicit 查询恰好不含条件词**（实测 0/10 含金标 condition）。
   所以两者都要解决同一个问题：**"杭州 → 华东"是语义理解，不是词表**。
2. **c 是唯一不需要为 19 个条件值做任何设计的方案**，而 v3 的第一件事应该是
   "让 A 轴测得出东西"，不是"同时重做条件体系"。
3. **c 的代价（A 轴退化）是可接受的**——"同 relation 多值选择"本身就是可测的能力，
   而 v2 已经证明"带 condition 的 A 轴"测不出东西（billing 1.0000）。

**不倾向 a/b 的关键理由**：它们都需要"查询 → 条件值"的语义映射，
而这与 v2 的 implicit 定义（不说破条件）**结构性冲突**——
要么 implicit 失效，要么映射出错。

> **这不是决定。** 若 v3 变更时发现"查询侧映射"有廉价解法
> （比如查询由生成器产出、天然带槽位），那 a 可能更优。
> 但按 v2 的数据形态判断，c 是当前证据下的最优选择。

### v3 的验收判据（待 v3 变更确认）

**三条，都不含魔数**：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 随机基线 < `SEH@1` < 1.0 | 下界防明显无效，上界防饱和（F24 已有） |
| 2 | 每轴 `SEH@1` 的 **Wilson 95% 下界 > 该轴自己的随机基线** | 统计判据；无固定效应量 |
| 3 | 报告给出：`n`、命中数、Wilson 区间、**该 `n` 下通过所需的最小命中数** | 让读者看到门槛有多严 |

**为什么用 Wilson 而不用 bootstrap 百分位区间**：

后者在 `p≈0/1` 且 `n` 小时坍缩成零宽。实测：

| 情形 | bootstrap | Wilson |
|---|---|---|
| `2/2` | `[1.0, 1.0]` 宽 0 | `[0.342, 1.0]` |
| `9/9` | `[1.0, 1.0]` 宽 0 | `[0.701, 1.0]` |
| `6/9` | `[0.333, 1.0]` ← 下界恰好等于基线 | `[0.354, 0.879]` → **通过** |

`6/9` 这一行是分水岭：bootstrap 判不通过，Wilson 判通过。而 bootstrap 的 `0.3333`
正是 `k/n` 网格的量化产物（第 5 百分位落在 `3/9`），不是统计事实。

> **工具选型错，不是工具实现错。** `proportion_ci` 是通用函数；
> 百分位 bootstrap 不适合 `n=9` 且 `p≈1` 的比例区间。

**不设 `n` 的硬下限**：

| `n` | 通过所需最小命中数 | 能"通过且不满分"吗 |
|---|---|---|
| 4 | **4/4**（满分） | ❌ 与 F24 冲突 |
| 5 | 4/5 | ✅ |
| 6 | 5/6 | ✅ |
| 9 | 6/9 | ✅ |
| 10 | 7/10 | ✅ |
| 20 | 11/20 | ✅ |

理论硬下限是 `n ≥ 5`，而 F23 要求 A 轴 ≥ 6，**所以实际不会触发**。

**为什么"不设下限"比"设 n ≥ 10"更诚实**：

```
设下限      n=9 的报告写"样本不足，统计判据不适用"  -> 读者以为"没有结论"
不设下限    n=9 的报告写"6/9 通过，所需最小命中数 6" -> 读者知道"通过了，但门槛更高"
```

**"n 小所以不适用"是把"更严"说成了"无定义"** —— 与本项目
`0 vs null`、`实测 vs 未跑`、`无定义 vs 饱和` 是同一条原则。

**两条被实测推翻的依据**（不要写进报告）：

| 依据 | 为什么不成立 |
|---|---|
| "`n=10` 时区间宽度 < 0.5" | 实测 `n=10`、`p=0.5` 时宽度是 **0.527** |
| "最小命中率收敛到 0.600" | 实测不收敛：`n=15` 是 0.600，`n=20` 是 0.550，`n=25` 是 0.520 |

### C 轴：不判通过/失败，只报数字

**A 轴的判据不能直接套到 C 轴**，因为两者的基线差 3–4 倍：

| 轴 | 竞争集 | 随机基线 |
|---|---|---|
| A | 3–4 条 | 0.29–0.33 |
| **C** | **9–12 条** | **0.083–0.111** |

后果：同一个 Wilson 下界，在 A 轴上勉强，在 C 轴上远远够。

| k/n | Wilson 下界 | vs A 基线 0.3333 | vs C 基线 0.0833 |
|---|---|---|---|
| 1/1 | 0.2065 | 不通过 | **通过** |
| **1/2** | **0.2065** | 不通过 | **通过** |
| 2/2 | 0.3424 | 通过 | 通过 |
| 6/9 | 0.3542 | 通过 | 通过 |

**`1/2` 就能通过 C 轴的 Wilson 判据**——所以"C 轴 2/2 通过"这个结论不支撑任何东西。

各 n 下的最小命中数（基线 0.0833）：

| `n` | 最小命中 | 命中率 |
|---|---|---|
| 1 | 1/1 | 满分 |
| **2** | **1/2** | **0.500** |
| 3 | 2/3 | 0.667 |
| 6 | 2/6 | 0.333 |

**所以 C 轴的统计判据待定，原因两条**：

1. **基线低**（0.083–0.111），Wilson 容易通过
2. **`n` 小**（2–3），任何判据都不可靠

**在那之前，C 轴只报数字，不判通过/失败。**
v3 若按 §8 把 C 轴扩到每 subject 20–60 条，再定判据。

> 这比"给 C 轴也加 `n ≥ 6`"更诚实：那个门槛会让 v3 得到一个
> "样本不足"的红，而实际是"这个量级的样本无论多少都对不上任何统计判据"。

`n=0` 的语义也要分开：

| 情形 | `minimum_hits_to_beat` 的行为 |
|---|---|
| `n == 0` | **抛 `ValueError`**——没有分母，参数非法 |
| `n ≥ 1` 但无解 | 返回 `None`——该 `n` 下不可达 |
| `n ≥ 1` 有解 | 返回最小命中数 |

### v3 的数据纪律（待 v3 变更确认后生效）

**v3 的数据在冻结前不看 v3 自己的系统分数。**
判据与 v2 的 `dataset-v2-protocol` 相同：协议先定、数据后造、分数最后跑。

**已知边界**：v3 的作者已经知道 v2 的 `1.0000`（那是 v3 的起因），
所以"不知道分数"只能指"不知道 v3 自己的"，不指"不知道 v2 的"。

> 这条现在只是一条判断，**还没有被任何一次 v3 决策检验过**。
> 所以写在这里而不是写成规范——若 v3 真开变更，它需要重新论证一次。

冲突感知的长期记忆层。核心主张：**抽取交给 LLM，"哪条记忆现在有效"由符号化状态跟踪裁决。**

### v2 的四条结论各有其限定

见 `docs/reports/v2-what-it-measures.md`。**三条最容易误读的**：

| 数字 | 不能读成 | 原因 |
|---|---|---|

### C4 的 `SEH@5 = 1.000` 不可用

它不是检索能力，是三个测量缺陷叠出来的：

- `query` 与 gold 的存库原文逐字相同（查询就是答案）

### 坏断言的四种形态（都实测过）

前三种已在多处记录，**第四种是 2026-11-05 新增**。

| # | 形态 | 谁在撒谎 | 怎么发现 |
|---|---|---|---|
| 1 | **永远绿**（`or True`、逻辑蕴含） | 断言：说检查了，实际没有 | 推导：找不出让它红的输入 |
| 2 | **永远红**（`assert False`） | 断言：说检查了，实际必然失败 | 回读：找不出让它绿的输入 |
| 3 | **误报**（名字说 A，实现测 B） | 名字 | 看红的**原因**，不只看红没红 |
| 4 | **注释与实现不符** | **注释** | **读得懂结果**：值与样本量是否自洽 |

**第四种为什么最难**：

- 它也出现在正常代码里，写法看起来完全正确
- 注释更短、更像结论，所以读代码时会把它当成"已经处理了"
- **它无法被自动化检测**：断言、证伪、双向检验都只检查代码行为，**不检查注释**

**实测案例**（`lexical-provenance` 归档，第二十次）：

```python
# A 组与 B 组做检验（C 组与重叠无关，单独报）      <- 注释
_, p = _perm_test(a_vals, b_vals + list(groups["C"].values()))   # <- C 混进来
```

后果：`sample` 的 p 从 **0.3333** 变成 **0.0079**，
并据此得出一个**完全错误的结论**（"结论分裂"）。

**发现路径不是证伪，是算术**：`sample` 只有 `C(6,5)=6` 种组合，
可能的 p 只有 `1/6`、`2/6`… 这些离散值——**0.0079 不在可能取值里**。
它来自 `C(10,5)=252`，也就是 C 组混入后的组合数。

**所以证伪的定义要扩展**：

> 旧：证伪 = 构造输入，看断言红不红
> 新：证伪 = 构造输入，看它**红在哪个值、报什么、**以及**那个值本身是否自洽**

第三项无法自动化，但有一条可执行的自检：
**精确检验的 p 值必须是 `k/组合数` 的离散值——对不上就说明样本被污染了。**

## 一个必须知道的教训

C3 的独立场景集是本项目最有价值的测量，因为它**证明了自写场景的 100% 是假的**。

在此之前，"场景由我写、规则由我设计、标签由我确认"这个闭环无法自证有问题。
第三方独立编写后，落差立刻显现（100% → 50%）。

**任何新结论都应该先问：这个数字有没有可能只是自证？**

### 对"听起来合理"的判断要格外警惕

**这一条是从四轮判断被推翻里提炼出来的，不是原则推演。**

实测记录：

| 判断 | 为什么听起来合理 | 探针成本 | 实测结果 |
|---|---|---|---|
| "两轴只剩池大小不同，应合并" | 评分函数确实相同 | 一条分布统计，1 分钟 | ❌ A 轴 relation 恒定、C 轴大多不同 |
| "value 太短导致向量分不开" | `CNY`/`USD` 确实只差三字 | 一次余弦计算，1 分钟 | ❌ 5/5 稳定输给同一条，是系统偏差 |
| "v3 数据不要造只差两字的 value" | 避开向量弱项确实能提高分数 | 无需探针（纯判断） | ❌ 那是让数据迁就向量 |
| "c2 是层级错位" | 原查询确实没提 value | 改查询重跑，1 分钟 | ⚠️ 只对 2/3，c2 是反例 |

**共同点：四个判断都能用一句话说清，且都不需要数据就能讲通。**

而四个里三个错、一个只对 2/3。

所以判据不是"要跑探针"（太笼统），而是：

> **一个判断如果"不需要数据就能讲通"，那它最可能没被验证。**
>
> 因为"能讲通"来自叙述的连贯性，不是来自数据。
> 而叙述连贯的判断，恰恰是最容易被直接写进报告、跳过验证的那类。

**成本对比**：上面四次探针各 1 分钟，而其中任意一个错误判断写进报告，
代价是一轮返工（这一路每一轮的返工都是一个完整对话）。

### 表述的模板：§0.1 那种写法

这一路积累了不少"结论对，但表述的范围比证据大"的句子，每次都要事后收窄：

| 说法 | 实际 |
|---|---|
| "只有文档改动" | 区间内 `evals/tools/check_v2_dataset.py` 也改了 |
| "池 100% 来自 dev" | 要分三层分母 |
| "向量救回 4/4 implicit" | 只在条件直通下成立；无条件信息时 0/4 |
| "A 轴 0.9000" | base 30% + 条件加成，不是条件区分能力 |

**而 §0.1 的写法是全项目里最接近"完整表述"的一段**，值得作为模板：

1. **先说差异存在**（"两者相差 3 个 commit"）
2. **逐项列出改了什么、没改什么**（表格，不概括）
3. **给出每一项的影响判断**（"只影响输出格式，判定不变"）
4. **给出验证方式**（"已实测重跑一致" + 复算命令）
5. **写根因**（`code_version` 混了 commit 与 dirty 两件事）

**关键是第 4 步**：不是"应该没问题"，而是"重跑验证过"。

而这一步有自动化的边界：

> 自动化的边界在**结构性事实**（哪个 commit、有没有 diff、是否为祖先），
> 而"**这个 diff 影不影响数字**"必须人来判断，且必须写下来。
>
> 因为前者是 `git diff` 能回答的，后者需要知道哪些文件在评测路径上。


### 补充：C4 的 1.000 不是"难度不够"，是"尺子坏了"

上面那句"先问是不是自证"还漏了一种更坏的情形：**测量装置本身出错**。
C4 事后查出八个缺陷（见 `docs/reports/c4-retrieval.md` 第 0.1 节，
可复算于 `results/c4-query-leak-ablation.json`）：

1. `query` 与 gold 的存库原文**逐字相同**——查询就是答案本身
2. 干扰项 `text=None`，索引里没有自然语言，物理上无法竞争
3. 指标在**召回结果**上算排名，而 independent 的 26/26 条召回集只有 1 个候选，
   排名从未发生，SEH 恒为 1
4. 方差测试查的是**数据集字段**，不是真实候选池——
   `authority` / `status` 在池内 0/76 有方差
5. 干扰项按**文件顺序取前缀**，76 条场景只有 15 种组合
6. **docstring 与代码不一致**：`SAME_RELATION` 声称"不同 subject"，
   实测 62/142 条同 subject；报告是按注释写的，不是按代码写的
7. **三路召回从未联合跑过**：`run_retrieval.py` 只 import 了 `recall_by_lexical`，
   向量与邻接一次都没进过评测入口。报告第 5 节的原表把"单元测试通过"
   写成了"已建成"——这是最影响对外可信度的一条
8. **`dedup` 收到的是 item_id 与常数分**：等价判断收到两个 UUID，
   排序退化为 UUID 字典序，**把重排结果整块替换**。
   实测"全判无关"也能让 `zzz,mmm,aaa,bbb` 变 `aaa,bbb,mmm,zzz`

抹掉 gold 原文后：dev 1.000 → **0.606**，test → **0.412**，independent → **0.500**。
independent 正好掉回 C3 的 50%——**同一个病：字符串方法在"表述不同但指同一件事"上无能**。

**缺陷 7 掩盖了缺陷 8**：排名没发生时，把排名打乱也看不出来。
单看任何一层都是"测试全绿"。

**所以以后看到满分，先查五件事：**

1. 查询里有没有答案（query 与 gold 原文/值的关系）
2. 分母是不是只有 1（排名有没有真的发生）
3. 断言有没有查错对象（测试通过 ≠ 被测性质成立）
4. 报告是不是照着注释写的（docstring ≠ 代码）
5. **这条路径在评测里真的被调用过吗**（import 了 ≠ 跑过了；
   下游拿到的是文本还是 id）

第 3 条最隐蔽：`test_rerank_variance.py` 一直是绿的，因为它量的是数据，
不是系统在候选池上的实际行为。第 4 条最容易被忽略，因为注释与代码都"看起来对"。
第 5 条是 C4 里最影响对外可信度的：三路召回写了两路，但从没联合跑过。

## 两条硬规则（看到数字之前先过这两关）

这个项目积累了两条规则，都不是"注意事项"，是**门禁**：

### 第一条：自写场景不能自证

场景由我写、规则由我按场景设计、标签由我确认——这个闭环永远得满分。
C3 的 100% → 独立 50% 就是它的代价。**任何自写数据集上的高分，先假设是自证。**

### 第二条：看到满分默认判为失败

C4 的 `SEH@5 = 1.000` 出现过三次，**每一次都被当成"指标满分"记录，
没有一次被当成"哪里错了"**。

满分是唯一不能自证的读数：它的成因可能是"系统完美"，也可能是"题目不存在"，
而后者概率高得多。所以 v2 协议把它写成**代码门禁**（`docs/requirements/retrieval-dataset-v2.md` §7.1.2）：

```python
if result["seh_at_k"] >= 1.0:
    raise SystemExit("SEH@5=1.000：先排除测量缺陷，再谈能力")
```

**这条规则的价值在于它不依赖记性。** 报告里写"满分不能证明能力"是事后解释；
写成门禁之后，任何新数据集都会先自检一遍。

**C4 里"这些不是实现缺陷，是数据表达能力的上限"这句话错了一半**——
前两条限制是数据问题，1.000 本身是实现缺陷。

## 34 个 `locked_defect` 标记不许删（收集为 36 条）

C4 的 19 条 + v2 的 4 条缺陷（20/21/22/23）现在由 **34 个 `@pytest.mark.locked_defect` 标记**锁着，
收集时展开为 **36 条测试**（`test_authority_and_status_have_no_variance_in_pool`
的 `parametrize` 有 3 个 split，占 3 条而只算 1 个标记）。

```bash
uv run --no-sync pytest -m locked_defect -q                        # 36 passed
uv run --no-sync pytest -m locked_defect --collect-only -q         # 看清单
uv run --no-sync pytest -m evidence_lock -q                        # 6 条，读 git 归档
uv run --no-sync pytest -m integrity_check -q                      # 1 条，检测归档被覆盖
```

**它们锁定的是"现状是坏的"，不是期望行为。** 造完 v2、跑出真实分数之后，
这 34 个标记**不应该被删**——它们记录的是一次真实的测量失败，
比任何"我们做得很好"的叙述都有价值。

- 改成正向断言的时机是**修复提交**，不是新数据上线时
- 冻结 tag 只冻结数据与协议，**不冻结代码状态**：缺陷还在，测试就该红

### 只有"可修复的违规"能进 `locked_defect`

**观测结论不是缺陷。** 这条界限必须守住，否则清单会混入永远无法结案的条目。

| 类型 | 例子 | 能否进 |
|---|---|---|
| 装置/数据违反应有性质 | 缺陷 1：`query == gold` 原文 | ✅ 修法是换数据 |
| 装置/数据违反应有性质 | 缺陷 19：`authority` 权重错配 | ✅ 修法是调权重 |
| **观测结论** | **"词面在 A 轴无增量"** | ❌ 没有"修好"这个状态 |
| **观测结论** | **"authority 临界点 = 0.25"** | ❌ 同上 |

判据：**问"这个条目怎样才能变绿"**。若答案是"改数据让它有增量"，
那不是修缺陷，是换实验。

`tests/retrieval/test_locked_defect_manifest.py` 的 `DEFECT_TESTS`
维护"缺陷编号 → 测试"映射，孤儿测试会红。所以把结论登记成缺陷
会在那里暴露——**但前提是有人真的去登记**。

### 三个 marker 的语义各不相同

| marker | 锁什么 | 变红时该做什么 |
|---|---|---|
| `locked_defect` | 当前代码里的缺陷 | 翻面成正向断言 + 更新 C4 报告 |
| `evidence_lock` | git 归档里的历史数字 | **只有 git 历史被改写时才红**，核对 commit，不要改测试 |
| `integrity_check` | 工作区文件是否被覆盖 | `git show <rev>:<path>` 还原 + 修回 run_count |

混淆这三种会浪费大量时间。本项目踩过一次：把 integrity 类的断言
标成 `evidence_lock`，结果它变成了"禁止跑实验"。
